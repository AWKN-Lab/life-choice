## 1. 目标

本作战图只解决一件事：

`问事与取名必须共用一套对话前台能力，不再演化成两套流程壳子。`

Q3 内，统一对话前台需要同时满足：

1. 首页点击入口后，在当前语境内承接用户。
2. 支持自然语言首问，而不是先铺重表单。
3. 支持按需补问，而不是一口气收全字段。
4. 支持结果承接、重试、追问和历史回看。
5. 与后端记录、积分、会员和结果页口径一致。

---

## 2. 当前事实

基于现有工程文档和代码探查，当前已知事实如下：

1. `FrontdeskChat.tsx` 已经承担 `naming` 与 `question` 两种模式。
2. 首页、兼容路由、旧前台页面之间仍存在双入口甚至三入口并存。
3. `question` 模式仍偏“输入后跳转”，不是完整状态机。
4. `naming` 与 `question` 在收集字段、补问方式、成功回调、失败回调上仍有散落逻辑。
5. `ResultPage.tsx` 责任过重，前台状态与结果状态仍没有彻底分离。

这意味着：

1. 现在不是从零做一个“统一前台”。
2. 而是对已有 `FrontdeskChat` 做收口，建立统一壳层、统一状态机、统一回调协议。

---

## 3. 最终目标形态

Q3 结束时，对话前台应收敛为以下结构：

```text
HomePage / 兼容路由
  -> FrontdeskShell
    -> FrontdeskChat
      -> mode = question | naming
        -> phase state machine
        -> clarify renderer
        -> payload builder
        -> submit handler
        -> success handler
        -> retry handler
```

其中：

1. `FrontdeskShell` 负责壳层、打开关闭、路由兼容、标题、布局。
2. `FrontdeskChat` 负责对话流和状态机。
3. `mode config` 负责差异化配置，不再把分支散在组件内部。

---

## 4. 范围

## 4.1 本期必做

1. 首页问事、取名统一接入同一前台壳层。
2. `/life/question`、`/life/naming` 仅作为兼容路由，内部复用同一前台组件。
3. 建立统一状态机，至少覆盖：
   - input
   - clarify
   - submitting
   - preview
   - deepening
   - followup
   - error_retry
4. 统一 payload builder 和 submit handler 接口。
5. 统一前台成功/失败后的结果承接逻辑。
6. 统一继续追问入口和历史恢复入口。

## 4.2 本期不做

1. 不重写成新的开放聊天产品。
2. 不引入另一套前台 UI 系统。
3. 不在本期统一命运K线到完全相同的对话壳，但要预留接入点。
4. 不在本期重写整个 `ResultPage`。

---

## 5. 工程原则

1. 复用现有组件，不另起一套 `QuestionFrontdeskV2`、`NamingFrontdeskV2`。
2. 差异化通过配置驱动，不通过复制组件。
3. 结果态与采集态分离，避免所有状态都压在结果页。
4. 错误恢复必须局部化，不允许整页刷新成为默认恢复策略。
5. 兼容路由保留，但不能再成为主流程实现分叉点。

---

## 6. 模块拆分

## 6.1 Shell 层

职责：

1. 决定以前台弹层还是页面模式渲染。
2. 挂载 mode。
3. 管理打开、关闭、返回、最外层 loading。
4. 保持首页入口与兼容路由共用同一实现。

建议文件边界：

1. `FrontdeskShell.tsx`
2. `FrontdeskEntryController.ts`

## 6.2 Chat 状态机层

职责：

1. 维护统一 `phase`。
2. 保存当前事项上下文。
3. 驱动补问、提交、成功、失败、追问。
4. 提供 mode 无关的统一事件。

建议统一事件：

1. `START_INPUT`
2. `SUBMIT_PRIMARY_INPUT`
3. `REQUEST_CLARIFY`
4. `SUBMIT_CLARIFY`
5. `SUBMIT_ANALYZE`
6. `ANALYZE_SUCCESS`
7. `ANALYZE_ERROR`
8. `START_DEEPEN`
9. `DEEPEN_ERROR`
10. `RETRY_LAST_ACTION`
11. `ENTER_FOLLOWUP`

## 6.3 Mode 配置层

职责：

1. 定义 greeting
2. 定义 quick intents
3. 定义 clarify strategy
4. 定义字段抽取器
5. 定义 payload builder
6. 定义 success mapping
7. 定义 retry copy

建议：

1. `question` 和 `naming` 都走同一个 config shape。
2. 不允许某一个 mode 走“例外式手写流程”。

## 6.4 Result 承接层

职责：

1. 前台如何跳结果页或内嵌展示 preview。
2. 深推如何进入已有结果链。
3. 继续追问如何回到对话链。

原则：

1. `recordId` 作为承接主键。
2. 不能只传临时 query 参数而没有后端真记录。

---

## 7. 战役拆解

## 战役 1：统一入口

交付：

1. 首页问事、取名点击逻辑统一。
2. 兼容路由复用相同壳层。
3. 删除旧主流程中的重复导航分叉。

验收：

1. 首页进入问事、取名不再跳两套不同前台。
2. 页面模式和弹层模式只在壳层差异，不在业务逻辑差异。

## 战役 2：统一状态机

交付：

1. `question`、`naming` 共用 phase 定义。
2. 前台显式区分采集、补问、提交、结果、追问、重试。
3. 深推失败可原地恢复。

验收：

1. 问事、取名不再靠 scattered state 维持流程。
2. 重试不会整页刷新。

## 战役 3：统一提交协议

交付：

1. mode 级 payload builder。
2. 统一 analyze 请求入口。
3. 统一 followup 请求承接。

验收：

1. 前台不再把 payload 拼接逻辑分散到多个页面和组件。
2. 任一 mode 都能追溯“从输入到后端记录”的链路。

## 战役 4：统一结果承接

交付：

1. preview 结果与 deepening 结果承接规则统一。
2. 继续追问入口统一。
3. 历史恢复能力统一。

验收：

1. 用户能从同一事项继续追问。
2. 历史打开后能回到正确事项上下文。

---

## 8. 里程碑

## M1：统一壳层完成

证据：

1. 首页和兼容路由共用同一前台实现。
2. 删除旧主流程双分叉。

## M2：统一状态机完成

证据：

1. 两个 mode 共用 phase 定义。
2. 深推失败局部重试可用。

## M3：统一提交协议完成

证据：

1. 问事、取名都可追溯到统一 analyze/followup 协议。
2. 结果承接不再依赖脆弱 query 组合。

---

## 9. 风险

1. `FrontdeskChat` 继续膨胀，最后成为新的巨型组件。
2. `ResultPage` 不减负，仍把所有状态收进去。
3. 旧路由兼容过程中残留第二套逻辑。
4. mode 配置不彻底，最后又回到“question 特判、naming 特判”。

应对：

1. 先抽壳层，再抽状态机，再抽 mode 配置。
2. 每完成一层就删旧分支，不保留长期双轨。

---

## 10. 验收清单

1. 首页问事与取名共用统一前台壳层。
2. `/life/question` 与 `/life/naming` 只保留兼容职责。
3. 问事与取名拥有同构 phase 状态机。
4. 深推失败支持局部重试。
5. 继续追问继承原 `recordId`。
6. 历史恢复能重新进入正确事项链路。
7. 不新增第三套前台组件体系。
