## 1. 目标

本作战图解决的是最核心的经营诉求：

`用户所有关键互动、命盘数据、结果与追问，都必须成为后台资产，而不是网页缓存。`

Q3 内需要完成 3 件事：

1. 三入口的数据口径统一。
2. 历史记录从“页面功能”升级成“用户资产入口”。
3. 管理员能按用户、事项、类型查看核心数据。

---

## 2. 当前事实

根据现有工程文档，当前已知事实如下：

1. Prisma 已有部分资产字段，如 `sourceEntry`、`namingType`、`namingPreferences`、`questionIntent`、`unlockStatus`、`shareGenerated`。
2. 这些字段此前并未在所有主链路中稳定写入。
3. 历史记录当前更像“咨询记录列表”，而不是以“人/事项”为核心的资产视图。
4. 结果页、追问链、分享链仍存在前端状态与后端真源混杂的风险。
5. 管理员后台查看能力不是系统级资产视图，只是局部字段可查。

结论：

1. 数据资产问题不是“没有表”。
2. 而是“写入不全、口径不一、展示不成体系、管理不成视图”。

---

## 3. 资产边界

Q3 要留住的不是所有前端细枝末节，而是以下 6 类核心资产：

1. 用户基础资料
2. 命盘与排盘快照
3. 首问/首需求
4. 补问信息与上下文
5. 初判/深推/追问结果
6. 历史行为与权益动作

其中最关键的是：

1. 同一事项必须能串起来。
2. 同一用户必须能回放自己的完整咨询脉络。
3. 管理员必须能看见真实用户路径，而不是只见最终结果。

---

## 4. Q3 目标结构

## 4.1 用户视角

用户应该得到：

1. 历史记录能回看自己问过什么。
2. 同一事项能继续追问，而不是重新开档。
3. 可以删除单条或批量记录。
4. 不会因为刷新或换设备就丢失重要结果。

## 4.2 管理员视角

管理员应该得到：

1. 能按用户查全部关键咨询资产。
2. 能按入口查：命运K线、问事、取名。
3. 能按事项查：这件事问了什么、追问了什么、最终输出了什么。
4. 能看付费、解锁、分享等关键转化动作。

## 4.3 工程视角

工程上必须满足：

1. 后端数据库是真源。
2. 前端缓存只做体验优化，不做真源。
3. `recordId` / `consultationId` 是串联主键。
4. 命盘、问题、结果、追问、权益口径可追踪。

---

## 5. 统一资产模型

Q3 不一定要大改表，但要统一成以下逻辑模型：

## 5.1 用户层

字段关注：

1. userId
2. email / login identity
3. isAdmin
4. creditBalance / membership

## 5.2 档案层

字段关注：

1. profileId
2. 姓名/称呼
3. 性别
4. 出生日期时间地点
5. 是否完整时辰

## 5.3 事项层

字段关注：

1. consultationId / recordId
2. sourceEntry = kline | question | naming
3. routeType / moduleType
4. questionIntent / namingType / klineType
5. status
6. createdAt / updatedAt

## 5.4 内容层

字段关注：

1. primaryInput
2. clarifyAnswers
3. algorithmSnapshot
4. previewResult
5. deepResult
6. followupThread

## 5.5 行为层

字段关注：

1. unlockStatus
2. shareGenerated
3. shareCount
4. payment or credit action refs
5. retryCount

原则：

1. 前台展示可以简化，但后端结构必须保证可追溯。
2. 算法快照与展示文案尽量分开存，避免以后无法复算或复盘。

---

## 6. 三大战役

## 战役 1：写入收口

目标：

让三入口所有关键动作都稳定入库。

范围：

1. analyze 创建记录
2. clarify 更新记录
3. deepening 更新记录
4. followup 追问链写入
5. share / unlock / retry 行为写入

验收：

1. 任一事项从进入到结束，都能看到完整链条。
2. 关键字段不再因为入口不同而缺失。

## 战役 2：历史收口

目标：

让历史记录从“功能列表”升级为“资产列表”。

范围：

1. 列表按人/事项/时间组织。
2. 支持单选、多选、全选、删除。
3. 列表卡片可显示人物核心信息、事项摘要、类型、时间。
4. 进入历史详情后能继续追问或查看完整结果。

验收：

1. 历史页不再只是“咨询记录”四个字导向。
2. 用户能从历史列表快速认出“这是谁、这是什么事”。

## 战役 3：后台视图收口

目标：

让管理员能把数据当资产运营，而不是当日志查看。

范围：

1. 用户维度视图
2. 事项维度视图
3. 入口维度视图
4. 行为转化维度视图

最小可用后台视图应回答：

1. 某个用户最近问了什么。
2. 这个用户有哪些命盘资料。
3. 这个事项经历了哪些追问与深推。
4. 哪个入口带来的转化更高。

验收：

1. 管理员无需读数据库原始表也能完成基本查看。
2. 能支撑客服、复盘、案例沉淀、内容运营的基础动作。

---

## 7. 推进顺序

## Phase 1：先保真写入

1. 梳理三入口关键写入点。
2. 确保 `recordId` 贯穿 analyze -> result -> followup。
3. 清理前端仅本地存在、后端无记录的流程。

## Phase 2：再改历史页

1. 先保证数据真有。
2. 再把列表组织方式从“系统视角”改成“用户视角”。

## Phase 3：再做管理员视图

1. 先把用户资产链路串完整。
2. 再做后台查询视图，不然只能看见一堆残缺字段。

---

## 8. 历史页目标形态

历史页卡片建议至少展示：

1. 人物名 / 匿名标签
2. 性别与出生信息摘要
3. 四柱或入口类型标识
4. 事项摘要
5. 最近更新时间
6. 状态标识：待验证 / 已深推 / 已分享 / 已完成

交互建议至少支持：

1. 单条删除
2. 多选删除
3. 全选删除
4. 打开详情
5. 从历史继续追问

原则：

1. 用户看到的是“我的人和事”。
2. 不是“系统生成过哪些条记录”。

---

## 9. 管理员视图目标形态

最小视图包含 4 个 tab：

1. 用户总览
2. 事项总览
3. 命盘与画像
4. 转化与行为

每个用户至少可看到：

1. 基础身份
2. 最近咨询
3. 命盘快照
4. 最近追问
5. 解锁记录
6. 分享记录

每个事项至少可看到：

1. 来源入口
2. 问题摘要
3. 初判摘要
4. 深推状态
5. followup 数量
6. 更新时间

---

## 10. 风险

1. 只改前台历史页，不补后端写入，最后仍是假资产。
2. 只堆字段，不做统一事项主键，最后查不出完整链。
3. 管理员视图直接查原始表，最终无法被业务使用。
4. 展示文案和算法快照混存，后续复盘困难。

应对：

1. 先补写入，再改展示。
2. 先串事项，再谈画像。
3. 先有最小后台视图，再考虑复杂 BI。

---

## 11. 验收清单

1. 三入口关键数据稳定写入后台。
2. `recordId` 贯穿主链路和追问链。
3. 历史页以人/事项为核心组织。
4. 历史页支持单删、多选、全选删除。
5. 用户可从历史继续追问或回看。
6. 管理员可按用户查看关键咨询资产。
7. 管理员可按事项查看完整链路。
8. 前端缓存不再承担数据真源职责。

---
