### 1.2 数据库约束

- **类型**：SQLite（文件型，非 MySQL/PostgreSQL）
- **驱动**：Prisma Client（异步，通过 `@prisma/client`）
- **连接模式**：Prisma 自动管理连接池，SQLite 默认单连接
- **表名约定**：PascalCase（如 `UserMemory`、`ConsultRecord`、`KlineBar`），与 `schema.prisma` 一致
- **迁移约束**：
  - SQLite 不支持 `DROP COLUMN`（需重建表）
  - 禁止 `db push` 覆盖生产结构
  - 迁移前必须 `cp dev.db dev.db.bak.<日期>.<批次>`
  - 生产迁移必须先在副本验证

### 1.3 后端模块边界

```text
apps/AWKN-LABlife/awkn-life-backend/
├── package.json                 # workspace 根（目标）
├── package-lock.json            # 唯一锁文件（目标）
├── ecosystem.config.js          # PM2 配置
├── scripts/bootstrap-production.js  # 生产启动器
└── apps/api-server/
    ├── package.json             # 业务依赖
    ├── prisma/schema.prisma     # 数据模型
    ├── src/                     # NestJS 业务代码
    └── scripts/                 # 构建/验证脚本
```

### 1.4 认证中间件约定

- **JWT**：`JwtAuthGuard` + `AdminGuard`（角色检查）
- **返回值类型**：`@UseGuards(JwtAuthGuard, AdminGuard)` 装饰器
- **Token 获取**：`Authorization: Bearer <token>` Header
- **错误码**：401（未认证）、403（无权限）

| 命令 | 用途 | 模式 | 当前状态 |
|------|------|------|---------|
| `npm run audit:changes` | 工作区变更分流 | 只读 | **损坏**（阶段 0 修复） |

| `npm run audit:backend` | 后端边界审计 | 只读 | 正常 |
| `npm run audit:workspace` | 工作区审计 | 只读 | 正常 |
| `npm run organize:workspace` | 工作区整理预演 | DRY-RUN | 正常 |

### 2.2 后端严格审计

```bash
powershell -NoProfile -ExecutionPolicy Bypass \
  -File scripts/maintenance/audit-backend-boundaries.ps1 -Strict
```

**检查项**：
- Schema 与代码引用一致性
- 锁文件唯一性
- 构建资产清单完整性
- 包管理器口径统一
- PM2 启动路径与依赖路径匹配

**退出码**：
- 0：通过
- 非 0：阻断（BLOCK + WARN）

### 2.3 单批次暂存命令（只打印，不修改）

```bash
powershell -NoProfile -ExecutionPolicy Bypass \
  -File scripts/maintenance/workspace-batch-map.ps1 \
  -Batch D1 -GitAddCommand
```

**约束**：命令仅打印 `git add` 命令，不直接修改暂存区；需人工确认后执行。

### 2.4 工具失效降级路径（P0-2 修复）

| 工具 | 失效场景 | 降级方案 |
|------|---------|---------|
| `audit:changes` | 空暂存区报错 | 阶段 0 修复 + Plan B 人工清单 |
| `audit:batches` | 空暂存区报错 | 阶段 0 修复 + Plan B 人工清单 |
| `audit:backend` | — | 正常运行，无需降级 |
| 发布闸门 | `audit:batches` 不可用 | 人工批次清单审核（项目负责人签字）+ `audit:backend` 双重确认 |

## 三、治理指标体系

### 3.1 红黄绿灯定义

| 指标 | 绿灯 | 黄灯 | 红灯 | 测量方式 |
|------|------|------|------|---------|
| 待人工归类 | 0 | 1—3 | >3 | `audit:batches` 输出 |
| 单活动批次变更 | ≤25 | 26—50 | >50 | `audit:batches -Strict` |
| 后端 BLOCK | 0 | 1 | ≥2 | `audit:backend` |
| 未核验删除项 | 0 | 1—5 | >5 | `audit:moves` + 人工 |
| 混合目标提交 | 0 | 1 | ≥2 | commit message 检查 |
| 根目录违规项 | 0 | 1—3 | >3 | `audit:workspace` |
| ACTIVE 文档缺少索引 | 0 | 1—2 | >2 | `docs/文档索引.md` 核对 |
| 发布缺少回滚记录 | 0 | 1 | ≥2 | Release Checklist 核对 |
| 知识版本缺少评估 | 0 | 1 | ≥2 | 资产台账核对 |
| **磁盘可用空间**（P1-7 修复） | >6G | 4—6G | <4G | `df -h` |

### 3.2 指标测量责任（P2-2 修复）

| 指标 | 测量人 | 测量频率 | 测量脚本 |
|------|--------|---------|---------|
| 待人工归类 | @程序员 | 每日开始 | `npm run audit:batches` |
| 后端 BLOCK | @程序员 | 每日开始 | `npm run audit:backend` |
| 根目录违规项 | @程序员 | 每周 | `npm run audit:workspace` |

### 3.3 红灯处理规则

红灯项出现后：
1. **暂停发布**（发布冻结）
2. **完成风险收口**（降为黄灯或绿灯）
3. **记录处理过程**（写入治理日志）
4. **恢复发布**（需质量审核人签字）

## 四、批次执行标准

### 4.1 批次开始前必填模板（P0-3 修复）

```text
批次编号：
业务目标：
用户结果：
文件范围：
禁止混入：
数据影响：
生产影响：
验证命令：
回滚方式：
回滚点 commit hash：____（必填，= 批次开始前的工作区 HEAD hash；未记录则禁止开始批次）
数据库快照路径：____（涉及 DB 变更时必填）
前端 dist.prev 路径：____（涉及前端构建时必填）
负责人：
审核人：____（P1-2 修复：审核人 ≠ 负责人）
```

### 4.2 批次结束时必产出

1. 文件清单
2. 代码或文档差异摘要
3. 测试与审计结果
4. 未完成项
5. 风险接受记录
6. 回滚命令
7. 下一批依赖

### 4.3 批次大小阈值（P1-3 修复）

- **默认阈值**：≤25 项（绿灯）
- **豁免条件**：功能无法拆分时允许 ≤40 项，但必须附"不可拆分证明"
- **硬上限**：>50 项（红灯）必须拆分

### 4.4 混合目标判定规则（P1-3 修复）

- **判定**：同一 commit message 出现 ≥2 个动词（如"完成+修复"、"重构+新增"）
- **豁免**：单一功能链涉及的配套测试/类型/i18n 不视为混合

## 五、Git 与提交治理

### 5.1 分支命名规则

| 类型 | 命名格式 | 示例 |
|------|---------|------|
| 产品功能 | `feat/<batch>-<topic>` | `feat/p2-frontdesk-naming` |
| 后端修复 | `fix/b0-<topic>` | `fix/b0-schema-restore` |
| 知识工程 | `knowledge/<batch>-<topic>` | `knowledge/k2-v3-switch` |
| 文档治理 | `docs/<batch>-<topic>` | `docs/g1-start-here` |
| 仓库治理 | `chore/governance-<topic>` | `chore/governance-audit-tools` |

### 5.2 提交信息格式

```text
feat(frontdesk): 完成取名候选状态闭环
fix(schema): 恢复记忆向量模型与访问时间字段
docs(archive): 归档已完成计划与过期 IDE 规格
chore(governance): 建立提交批次与后端审计闸门
knowledge(index): 修复空字节并重建知识索引
```

### 5.3 禁止操作

- `git reset --hard` 作用于整个工作区
- 无范围 `git checkout -- .`
- 未核验的批量删除
- 功能开发与目录迁移混合提交
- Schema 与锁文件进入普通功能提交
- 自动格式化覆盖全部仓库
- 直接提交数据库、日志、备份和构建包

### 5.4 批次级 Git Tag（P0-3 修复）

每个批次开始前：
```bash
git tag batch/<id>-start
```
每个批次结束后：
```bash
git tag batch/<id>-end
```

回滚时：
```bash
git reset --soft batch/<id>-start  # 保留工作区
# 或
git revert <commit-range>  # 创建回滚 commit
```

## 六、文档治理

### 6.1 文档状态

| 状态 | 使用规则 |
|------|---------|
| ACTIVE | 当前执行和决策依据 |
| PROPOSED | 待评审方案，禁止直接视为生产规则 |
| REFERENCE | 参考资料，不能覆盖当前基线 |
| DEPRECATED | 已停止使用，保留历史链接 |
| ARCHIVED | 历史过程，只用于追溯 |

### 6.2 文档层级

1. `START-HERE.md`：项目入口
2. `docs/文档索引.md`：全量导航与状态
3. 产品 PRD：用户目标与产品边界
4. 当前生产工程基线：运行事实
5. 模块文档：API、数据库、部署、测试
6. 质量报告：验收与取证
7. 历史归档：过程和旧方案

### 6.3 更新规则

- 代码实现完成后更新工程文档
- 生产部署完成后更新生产状态
- 方案讨论阶段使用 `PROPOSED`
- 旧文档迁移后更新索引和旧路径引用
- 同一主题保留一个 ACTIVE 主入口

### 6.4 文档循环依赖处理（P2-1 修复）

- **规则**：索引文件本身不进入索引
- **示例**：`docs/文档索引.md` 不在自身中列出
- **例外**：其他文档引用索引文件时，需标注"本索引"

## 七、知识资产治理

### 7.1 生产知识资产记录

每一份生产知识资产必须记录：
- 来源文件
- 原始版本
- 授权与使用范围
- 清洗脚本
- 切分方法
- 索引版本
- embedding 版本
- 评估报告
- 生产启用时间
- 回退版本

### 7.2 知识生产链

```text
原始资料
→ 清洗
→ 结构化
→ 切分
→ 索引
→ embedding
→ 离线评估
→ 生产切换
→ 运行监控
→ 版本回退
```

### 7.3 版本保留策略（P2-3 修复）

- **保留版本数**：最近 3 个生产版本
- **存储位置**：`knowledge/processed/archives/`
- **清理规则**：超过 3 个版本后，最旧版本移入 `_archive/`
- **回退要求**：必须保留可独立运行的完整版本（索引 + embedding + 评估报告）

### 7.4 生产索引更新约束

任何生产索引更新必须保留：
- 记录数
- 哈希
- 失败记录
- 评估结果
- 旧版本恢复路径

### 8.3 发布后验证

- 健康接口连续通过
- 核心问事、取名、K 线、用户资产入口可用
- 日志无新增高频异常
- 数据库迁移状态同步
- 前端错误采集正常
- 经营指标能够记录新版本数据

### 8.4 回滚触发条件（P1-6 修复：量化）

| 条件 | 阈值 | 回滚方式 |
|------|------|---------|
| 核心接口不可用 | 连续失败 ≥3 次（每次间隔 10s） | 自动 |
| Prisma 字段/表错误 | 持续出现 ≥30s | 自动 |
| 必需知识资产缺失 | 启动校验失败 | 自动 |
| 用户咨询记录无法落库 | 连续 ≥5 条失败 | 人工评估 |
| 新版本错误率 | >基线 ×1.5 | 人工评估 |
| 新版本错误率 | >基线 ×2 | 自动 |
| 数据迁移不可解释差异 | 任何 | 立即 |

### 8.5 灰度发布与全量发布（P1-5 修复）

| 类型 | 闸门要求 |
|------|---------|
| 灰度发布 | 可降级（audit:batches 不可用时人工审核） |
| 全量发布 | 必须全闸门通过 |

### 8.6 K2 切换降级路径（批判性审查 H2 补充）

- **触发**：v3 评估不达标或切换后错误率上升
- **降级**：编辑 `.env` 改回 `KNOWLEDGE_EMBED_VERSION=v2`
- **执行**：`pm2 reload knowledge-service --update-env`
- **验证**：健康接口返回 v2 版本标识

## 九、AI 协作治理

### 9.1 AI 读取顺序

1. `START-HERE.md`
2. `docs/00项目治理/项目治理计划-v1.0-20260712.md`（v1.1 发布后替换）

5. 当前模块 PRD

### 9.2 AI 修改前必须输出

- 当前批次
- 目标文件
- 计划修改范围
- 禁止触碰范围
- 验证方法

### 9.3 AI 修改后必须输出

- 实际修改文件
- 测试结果
- 剩余风险
- 文档同步情况
- 回滚方式

### 9.4 AI 准入机制（P1-4 修复，v1.2 实现）

**v1.1 过渡方案**（软约束 + 人工抽查）：
- AI 修改前必须写入 `.trae/batch-context.json`（含批次编号、目标文件、禁止范围）
- 审核人抽查该文件是否存在且字段完整

**v1.2 目标方案**（hook 拦截）：
- hook 检测 `.trae/batch-context.json` 存在且字段完整才允许 Edit/Write
- 高风险命令（reset、checkout、db push）强制 `requires_approval: true`

### 9.5 AI 禁止操作

- 全仓重置
- 全仓格式化
- 生产数据库迁移
- 高风险物理删除

### 9.6 Memory 优先级（P2-9 修复）

- **规则**：项目 Memory 优先于治理计划
- **顺序**：Memory → START-HERE → 治理计划 → 批次计划 → 文档索引 → PRD → 工程基线 → 源码
- **冲突处理**：Memory 与治理计划冲突时，以 Memory 为准，并升级治理计划版本

## 十、运行节奏

```bash
git status --short
npm run audit:batches
npm run audit:backend
df -h /  # P1-7 修复：检查磁盘
```

确认：

- 保存测试结果
- 更新批次状态

1. 当前活动批次数量

7. 产品闭环指标
8. 下周冻结范围

- 评审不通过 → 下一周冻结新需求

### 11.2 变更管理流程

1. **识别变更**：新增需求、入口变更、接口变更、数据格式变更、权限变更
2. **默认进入下个版本候选**：不直接塞回当前版本
3. **写入结果单**：未写入结果单的口头变更视为无效
4. **升版本**：变更累积到一定程度后升版本
5. **同步文档**：升版本后同步更新所有引用文档

## 十二、角色与责任

### 12.1 角色定义

| 角色 | 职责 | 互斥约束（P1-2 修复） |
|------|------|---------------------|
| 项目负责人（天火） | 最终决策、优先级、范围、风险接受 | — |
| 工程负责人（@程序员） | 代码契约、模块边界、测试、运行结果 | ≠ 质量审核人 |
| 质量审核人 | 验收、缺陷、生产证据、发布结论 | ≠ 工程负责人 |
| 知识负责人 | 知识资产来源、处理、索引、评估 | — |
| 部署负责人 | 部署、健康检查、回滚 | — |

### 12.2 角色互斥规则

- 质量审核人 ≠ 工程负责人（禁止自审）
- 若团队仅 1 人，引入外部审核人或 AI 审核代理
- 批次执行标准的"审核人"字段必须 ≠ "负责人"

### 12.3 宣告权分离（P0-4 修复）

- **执行权**：工程负责人执行
- **宣告权**：质量审核人宣告"闭环完成"
- **禁止**：执行者自我宣告闭环完成

## 十三、批判性审查机制

### 13.1 审查触发条件

- 治理计划升版本
- 工程交接包发布
- 工程文档发布
- 重大决策（ADR、PRD 冻结）

### 13.2 审查要求

- 假设前序有 ≥3 项隐藏缺陷
- 主动证伪，不依赖用户追问
- 出具审查单（编号、日期、结论、残余风险）

### 13.3 审查结论

- **放行**：无 P0，可进入下一步
- **有条件放行**：有 P0 但已识别修复路径，修复后放行
- **打回**：有 P0 且无明确修复路径，必须重做

每次高风险修改或复盘结束后，必须补一句：

> 下次遇到类似情况，先做哪 3 件事？
> 1. 查看当前状态（git status + 文档版本 + Memory 最新）
> 2. 备份当前版本（git commit + tag）
> 3. 读取完整文件并确认修改位置（行号级核对）
