## 二、三套体系的职责边界分析

```
用户提问
    │
    ├── RouterService (第一套)
    │   职责：快速确定需要收集什么信息（birthDate? askTime? gender?）
    │   输入：用户原始问题文本
    │   输出：requiredFields + clarifyingQuestion
    │   使用方：前端表单 → 决定展示哪些输入字段
    │
    ├── XuanxueOrchestrator (第二套)
    │   职责：拿到完整信息后，流水线式生成分析结果
    │   输入：question + birthInfo + askTime + calcResult
    │   输出：llmResult (JSON) → consultRecord
    │   使用方：前端轮询结果 → ResultPage 渲染
    │
    └── 张半山调度层 (第三套，待建)
        职责：LLM 级意图理解 + 反问 + 多 Agent 调度
        输入：用户问题（可能是多轮对话中的任意一轮）
        输出：调度决策（主调 + 佐调 Agent）
        使用方：替代/增强 Orchestrator 的 IntentRouter
```

## 三、核心矛盾

| 矛盾 | 描述 |
|------|------|
| **RouterService vs 张半山** | 两者都做"意图识别 → 决定 Agent"，但 RouterService 是关键词匹配、张半山是 LLM 语义理解。同一问题可能得出不同结果。 |
| **Orchestrator.IntentRouter vs 张半山** | Orchestrator 已有 IntentRouter 做 `ziping/liuren/mixed/clarify` 四分类，张半山引入了 8 种用户场景 × 多 Agent 组合，粒度完全不同。 |
| **Orchestrator 管道 vs 张半山调度** | Orchestrator 是 `IntentRouter → Evidence → Knowledge → Generate` 的线性管道，张半山需要「并行调用多 Agent → 聚合 → 仲裁」的扇形拓扑。 |

---

## 四、整合策略（推荐方案）

### 4.1 总原则：替代，不叠加

**张半山调度层替代 Orchestrator 的 IntentRouter，RouterService 保持不变。**

理由：
1. RouterService 职责明确（信息收集指引），且不依赖 LLM，适合保留
2. Orchestrator 的 IntentRouter 与张半山功能重叠最严重
3. 叠加三套 = 路由不一致风险 + 维护复杂度翻倍

### 4.2 三套体系的最终定位

```
用户提问
    │
    ├── [保留] RouterService
    │   职责不变：信息收集指引
    │   API: POST /consult/route (不变)
    │   何时用：前端加载时、用户首次输入问题后
    │
    ├── [改造] XuanxueOrchestrator
    │   移除：IntentRouter（由张半山替代）
    │   新增：张半山调度模块（替代 IntentRouter 的位置）
    │   保留：EvidenceBuilder → KnowledgeRetriever → GenerationComposer → QualityGate
    │   API: POST /consult/analyze (不变，但内部路由逻辑替换)
    │
    └── [新建] 张半山调度模块 (ZhangbanshanScheduler)
        职责：LLM 意图识别 + 反问 + 多 Agent 调度
        输入：question + userContext (session history)
        输出：SchedulingDecision { primaryAgent, secondaryAgent, needClarify, clarifyingQuestion }
        集成点：替代 Orchestrator.processJob() 中的 intentRouter.route() 调用
```

### 4.3 具体改动清单

| 文件 | 改动 | 工作量 |
|------|------|--------|
| `orchestrator/intent-router.service.ts` | **废弃**（保留文件但不再调用） | 0 |
| `orchestrator/orchestrator.service.ts` | `processJob()` 中将 `intentRouter.route()` 替换为 `zhangbanshanScheduler.schedule()` | 小 |
| **新建** `orchestrator/zhangbanshan-scheduler.service.ts` | 加载张半山-SKILL.md + 调度决策树 → LLM 调用 → 返回调度决策 | 中 |
| `router.service.ts` | **不改** | 0 |
| `consult.controller.ts` | **不改** API 签名 | 0 |

### 4.4 张半山调度模块的输入输出契约

```typescript
interface SchedulingInput {
  question: string;
  hasBirthInfo: boolean;
  hasAskTime: boolean;
  sessionHistory?: Array<{ role: string; content: string }>;  // Phase C+ 支持多轮
}

interface SchedulingDecision {
  primaryAgent: 'liuren' | 'qimen' | 'ziping' | 'ziwei' | 'liuyao' | 'quming';
  secondaryAgent?: 'liuren' | 'qimen' | 'ziping' | 'ziwei' | 'liuyao' | 'quming';
  needClarify: boolean;
  clarifyingQuestion?: string;
  scheduleReason: string;  // 调度理由，供前端展示
}
```

## 五、分阶段实施

| 阶段 | 内容 | 张半山替代 |
|------|------|-----------|
| **Phase B** (MVP) | 张半山调度模块实现单 Agent 调度 | 替代 IntentRouter，但只做 1→1 映射（等同当前功能） |
| **Phase C** | 双 Agent 并行（1 主 + 1 佐） | 张半山开始体现多 Agent 调度价值 |
| **Phase E** | 全系统并行 + 仲裁 | 完全替代 IntentRouter，8 场景 × N Agent 组合 |

---

## 六、不做什么

- 不删除 RouterService（职责不同，独立保留）
- 不改变现有 API 签名（`/consult/route` 和 `/consult/analyze` 对外不变）
- 不在 Phase B 就支持反问→重新调度的闭环（那是多轮对话能力，Task 5 独立处理）

---

## 七、风险与缓解

| 风险 | 缓解 |
|------|------|
| 张半山 LLM 调度不稳定（输出不是合法 routeType） | 输出解析层加 fallback：LLM 输出无效时降级到 IntentRouter |
| 张半山调度引入额外 1 次 LLM 调用（增加延迟 + 成本） | Phase B 评估：1 次调度 LLM + 1 次 Agent LLM = 2x 当前；可接受 |
| RouterService 和张半山对同一问题给出不同 Agent | 两者用途不同（信息收集 vs 实际调度），不一致是可预期的，不是 bug |
