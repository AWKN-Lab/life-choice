# 张半山优化 · 第一轮行动计划

> 日期：2026-05-29
> 状态：规划中
> 依据：脑暴圆桌会（战略架构师 × 体验设计师 × 技术架构师 × 商业模式分析师）
> 目标：让张半山从「包装层」升格为「调度协调层」，六个算法 Agent 形成合力

---

## A. 目标与边界

### 目标一句话

让张半山成为真正的调度者：收到用户问题后，决定调用哪几个 Agent，交叉比对后给出一个带代价说清的统一判断。

### 本轮做

- 张半山调度决策树（问题类型 → Agent 组合映射）
- 六 Agent 输出格式统一增加置信度字段
- 矛盾检测规则 + 张半山仲裁逻辑
- 重构输出格式：三段式（判断 / 代价 / 推理轨迹）
- 张半山 SKILL.md 整合四个角色文档为可填入系统的提示词模板

### 本轮不做

- LLM Gateway 工程层改造（留第二轮）
- 前端推理轨迹可视化交互
- 会员体系调整
- 六 Agent 算法本身的深度迭代（这是另一条线）

### 约束与假设

- 不改动 CalcEngine 数据结构（置信度字段在 Agent 层加，不动底层）
- 张半山调度决策树用「规则 + Few-shot」实现，不依赖复杂的规则引擎
- 六 Agent 现有 prompt 不改动，只改输出格式
- 前端推理轨迹先做「可展开」隐藏展示，暂不做独立交互组件

---

## B. 最小闭环（MVP-0）

用户问一个问题 → 张半山判断调用哪个 Agent → 单 Agent 输出 + 置信度 → 张半山翻译成代价描述 → 三段式输出展示。

MVP-0 不做多 Agent 交叉验证，只做两件事：
1. 置信度字段加进每个 Agent 的输出
2. 张半山在输出时必须说代价

验证方式：手动跑 3 个真实场景，看置信度有没有、代价有没有说清楚。

---

## C. 分步清单

### Step 1｜写张半山调度决策树

**动作**

- 梳理 7 种典型用户问题类型
- 定义每种类型对应调用哪几个 Agent（主 + 佐）
- 写出每种组合的调度逻辑（为什么这么选）

**产出**

`张半山-调度决策树.md`——7 种场景 × Agent 组合 × 调度理由

**验收标准**

任何一个人看完这份文档，能说清楚「用户问这个，张半山该调哪几个 Agent，为什么」

**验证方法**

找 5 个不同类型的问题，逐一检查调度决策树是否覆盖

**回滚方式**

删除文档，对现有流程无影响

---

### Step 2｜统一六 Agent 输出格式，增加置信度字段

**动作**

- 读取 6 个 Agent 的现有 prompt（`liuren-system-prompt.md` 等）
- 在输出格式说明里增加 `confidence` 字段（高/中/低）和 `uncertainty_factors` 字段
- 同步更新分析 prompt 模板

**产出**

6 个 prompt 文件的输出格式部分更新（加置信度字段说明）

**验收标准**

每个 Agent 的输出 JSON 里必须有 `confidence` 和 `uncertainty_factors` 两个字段

**验证方法**

用同一组输入数据跑 6 个 Agent，检查每个输出的 JSON 结构

**回滚方式**

用 git 恢复原始 prompt 文件

---

### Step 3｜写矛盾检测规则和张半山仲裁逻辑

**动作**

- 定义「一致」和「分歧」的判定标准
- 写出张半山在分歧时的仲裁流程（哪个 Agent 优先、仲裁理由必须包含什么）
- 把仲裁逻辑写入张半山 SKILL.md 的「决策规则」章节

**产出**

`张半山-矛盾检测与仲裁规则.md`

**验收标准**

分歧场景下，张半山的输出必须包含「我认为 X 比 Y 更可信，因为……」这句话

**验证方法**

构造一个六壬和奇门结论矛盾的场景，手动跑一遍

**回滚方式**

删除文档，对现有流程无影响

---

### Step 4｜写张半山 SKILL.md

**动作**

- 整合四个角色文档（世界观、角色档案、全流程对话设计、对话样例库）
- 填入系统提示词模板格式（角色定义 / 能力边界 / 输出规范 / 禁律 / 调度规则 / 样例）
- 加上 Step 1、Step 3 的调度决策树和仲裁规则

**产出**

`张半山-SKILL.md`——可直接填入系统的提示词模板

**验收标准**

- 字数在 3000-5000 字之间
- 包含所有角色文档的核心要素
- 有 5 个以上对话样例（含正确示范和错误示范对照）
- 有调度决策树摘要（可嵌入 prompt）

**验证方法**

让技术团队用这份 SKILL.md 跑一次真实对话场景，检查角色行为是否符合预期

**回滚方式**

保留原始四个文档，SKILL.md 单独管理

---

### Step 5｜重构输出格式：三段式

**动作**

- 定义三段式输出格式的模板（三段分别怎么写、长度限制、必须包含什么）
- 把模板写入 SKILL.md 的「输出规范」章节
- 更新 LLM Gateway 的输出校验规则（三段缺一不可）

**产出**

- 三段式输出模板（`张半山-输出格式规范.md`）
- Gateway 输出校验更新（可选）

**验收标准**

张半山的每次输出必须是以下三段：
1. 【我的判断】一句话核心结论（≤40字）
2. 【代价】这个选择意味着……（≤100字）
3. 【推理轨迹】可选展开，展示多系统校准过程

**验证方法**

用 5 个不同场景的实际对话，检查输出是否满足三段式规范

**回滚方式**

删除模板文档，Gateway 校验规则恢复默认

## D. 高风险清单

| 风险项 | 级别 | 说明 | Plan B |
|--------|------|------|--------|
| 六 Agent 输出格式改动影响现有流程 | 中 | 改了 prompt 可能导致现有接口不兼容 | 先在测试环境跑，验证通过再合入 |
| 置信度字段依赖算法层标注 | 中 | 如果算法本身没有置信度评估能力，字段为空 | 降级：让 LLM 在 Agent 层自评置信度，标注在输出里 |
| 三段式输出导致回答变长 | 低 | 用户可能觉得太长 | 第二段「代价」必读，第一段和第三段可精简 |

---

## E. 最终验收（DoD）

- 用户问一个决策问题，张半山给出三段式输出，判断 / 代价 / 轨迹三段齐全
- 每个 Agent 的输出 JSON 有置信度字段
- 分歧场景下，张半山能给出仲裁理由
- 张半山 SKILL.md 可直接填入系统跑通一个完整对话
- 手动跑 3 个真实场景，全部通过验收标准

### 卡点

1. **后端数据断桥**：`OPTIONAL_LLM_FIELDS` 白名单过滤导致 `zhangbanshan_output` 被静默丢弃。排查耗时约 30 分钟，根因是 `mergeOptionalFields()` 方法不在白名单的字段会被丢弃。修复：白名单末尾添加 `'zhangbanshan_output'`。
2. **前端 base path 硬编码**：多处 `/life/` 硬编码路径导致部署到其他子路径时资源 404。修复：统一改为 `import.meta.env.BASE_URL` 动态读取。

### 经验沉淀

- 规则 15：**API 白名单字段必须与后端新增字段同步**。后端新增返回字段时，必须检查 `mergeOptionalFields` / `OPTIONAL_LLM_FIELDS` 等白名单是否包含该字段，否则会被静默丢弃。
- 规则 16：**前端路径必须用构建工具变量而非硬编码**。`import.meta.env.BASE_URL` 代替 `/life/`，`vite build --base=` 控制部署路径。

### 下轮第一步

LLM Gateway 工程层改造——当前张半山调度依赖 orchestrator 内的硬编码逻辑，需要抽象为可配置的 Gateway 层，支持动态路由和模型切换。
