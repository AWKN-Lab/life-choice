## 一、核心矛盾

### 1.1 张半山需要多轮对话

张半山的人格设计中，「反问-观察-判断」是核心流程：

```
用户: 我该不该跳槽？
张半山: 「你是想动还是想等？」        ← 反问
用户: 想动，但怕跳完更差
张半山: 「那你最怕的是什么？」        ← 追问
用户: 怕新公司不稳定
张半山: [调度 六壬+奇门 → 输出判断]    ← 判断
```

这需要**3 轮对话**才能完成一次完整的调度→判断闭环。

### 1.2 当前系统是单次请求-响应

当前 `POST /consult/analyze` 是一次性请求：
1. 用户提交 question + birthInfo + askTime
2. Orchestrator 异步处理
3. 前端轮询 `/consult/result/:recordId` 获取结果
4. **一次请求 = 一次回答**，没有中间反问环节

## 二、分阶段策略

### 2.1 Phase B（MVP）：单轮对话，跳过反问

**策略**：张半山在 Phase B 不做反问，直接用用户的问题调度 Agent。

**理由**：
1. 反问需要 session 管理和 WebSocket/SSE，工程量远大于张半山调度核心
2. 反问的「想动还是想等」「最怕什么」本质是前端也可以在提交前做的信息收集
3. MVP 验证的是"LLM 调度是否比关键词匹配更准"，而非对话体验

**Phase B 对话流**：
```
用户: 我该不该跳槽？ + 出生信息
张半山: [调度 六壬] → [三段式输出]
        【我的判断】现在动比等更伤，等到秋天再看
        【代价】这意味着你放弃现在的窗口期...
        [展开推理轨迹 ▼]
```

**张半山在 Phase B 不产生反问**，调度决策树中的「张半山第一问」在 Phase B 中仅作为内部调度参考（帮助 LLM 更准确判断意图），不输出给用户。

## 三、多轮对话协议设计（Phase C+ 使用，Phase B 预留接口）

### 3.1 对话状态机

```
         ┌──────────────────────────────────┐
         │         DIALOG_STATES             │
         ├──────────────────────────────────┤
         │ IDLE          初始 / 对话结束      │
         │ SCHEDULING    张半山正在判断意图    │
         │ CLARIFYING    张半山反问，等待回复  │
         │ GENERATING    Agent 正在计算       │
         │ RESPONDING    张半山正在合成输出    │
         │ COMPLETED     输出已就绪           │
         └──────────────────────────────────┘
```

状态转换：
```
IDLE → SCHEDULING (用户提问)
SCHEDULING → CLARIFYING (张半山决定反问)
SCHEDULING → GENERATING (张半山直接调度 Agent)
CLARIFYING → SCHEDULING (用户回复后，重新调度)
GENERATING → RESPONDING (Agent 计算完成)
RESPONDING → COMPLETED (三段式输出就绪)
COMPLETED → IDLE (用户查看完毕 / 新问题)
```

### 3.2 API 协议（Phase C+ 实施）

#### 端点 1：启动对话

```
POST /consult/dialogue/start
Body: { question: string, birthInfo?: {...}, askTime?: string }
Response: {
  dialogueId: string,
  state: 'SCHEDULING' | 'CLARIFYING',
  clarifyingQuestion?: string,  // 如果 state=CLARIFYING
}
```

#### 端点 2：回复反问

```
POST /consult/dialogue/:dialogueId/reply
Body: { answer: string }
Response: {
  state: 'SCHEDULING' | 'CLARIFYING' | 'COMPLETED',
  clarifyingQuestion?: string,  // 如果继续反问
  result?: ZhangbanshanOutput,  // 如果 state=COMPLETED
}
```

#### 端点 3：获取结果（轮询 / SSE）

```
GET /consult/dialogue/:dialogueId/result
Response: {
  state: 'GENERATING' | 'COMPLETED',
  progress?: { primaryAgent: string, status: 'pending' | 'running' | 'done' },
  result?: ZhangbanshanOutput,
}
```

### 3.3 实时推送（SSE 方案，优于 WebSocket）

```
GET /consult/dialogue/:dialogueId/stream
→ SSE events:
  event: state_change
  data: {"state":"CLARIFYING","clarifyingQuestion":"你是想动还是想等？"}

  event: agent_progress
  data: {"agent":"liuren","status":"done"}

  event: result_ready
  data: {"result":{...}}
```

**选择 SSE 而非 WebSocket 的理由**：
1. 当前部署在 Nginx 反向代理后，SSE 配置比 WebSocket 简单
2. 前端只需接收推送，不需要双向通信
3. NestJS 原生支持 SSE（`@Sse()` 装饰器）

### 3.4 对话上下文存储

```
Prisma Schema 新增：

model ConsultDialogue {
  id           String   @id @default(cuid())
  recordId     String
  userId       String?
  sessionId    String?
  state        String   // IDLE | SCHEDULING | CLARIFYING | GENERATING | COMPLETED
  turns        Json     // [{role, content, timestamp}]
  finalResult  Json?    // ZhangbanshanOutput
  createdAt    DateTime @default(now())
  updatedAt    DateTime @updatedAt
}
```

### 4.2 前端改动

| 改动 | 说明 |
|------|------|

| 能力 | Phase B | Phase C+ |

| 张半山反问用户 | ❌ | ✅ |

| 实时推送调度进度 | ❌ | ✅ (SSE) |
| 对话历史持久化 | ❌ | ✅ (ConsultDialogue) |
| 用户中途取消/纠正 | ❌ | ✅ |

## 六、调度决策树「张半山第一问」在 Phase B 的使用方式

张半山调度决策树中每个场景都有「张半山第一问」：

| 场景 | 张半山第一问 | Phase B 用法 |
|------|-------------|-------------|
| 该不该动 | 「你是想动还是想等？」 | 内部参考：帮助 LLM 区分「主动想动」vs「被动想逃」 |
| 两个方向选哪个 | 「两个方向你最怕哪个结果？」 | 内部参考：帮助 LLM 理解用户真正的恐惧点 |
| 考研/创业 | 「你现在最担心的是什么？」 | 内部参考：区分「怕失败」vs「怕错过」 |

Phase B 中，这些反问**不输出给用户**，而是作为系统提示词的一部分注入给张半山 LLM：

```
【内部调度参考（不输出给用户）】
用户问的是跳槽，根据决策树，你需要追问「你是想动还是想等？」
但当前不支持反问——请在用户的问题中推断：
- 如果问题中含「受不了」「待不下去」→ 被动想逃 → 主调六壬
- 如果问题中含「更好的机会」「想试试」→ 主动想动 → 主调奇门
```

## 七、Phase C 前置条件

启动 Phase C（多轮反问）前需满足：
1. Phase B 验证通过（张半山调度准确率 > 关键词匹配）
2. 前端团队确认多轮对话 UI 排期
3. 运维确认 SSE 在 Nginx 反向代理下可用（`proxy_buffering off`）
4. 产品方确认反问轮次上限（建议 ≤ 2 轮）
