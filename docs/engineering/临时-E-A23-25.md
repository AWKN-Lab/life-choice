## E-A23：Git remote URL 协议统一（SSH优先，2026-07-03 新增）

> 来源：天火·人生决策宗师 Step 12+13 部署复盘

**核心断言**：git remote 的 fetch 和 push URL 必须统一协议和账号，禁止靠 GitHub 自动重定向作为长期方案。

### 触发条件

- `git remote -v` 显示 fetch 和 push 协议不一致（如 fetch=SSH, push=HTTPS+token）
- push URL 使用个人账号 token + 旧账号路径
- push 成功但靠 GitHub 重定向（出现 "repository moved" 提示）

### 规则

1. fetch 和 push 必须同为 SSH 协议或同为 HTTPS 协议（推荐 SSH）
2. SSH 优先于 HTTPS+token（不依赖 token 过期，认证更稳定）
3. 禁止靠 GitHub 自动重定向作为长期方案（重定向行为可能变化）

### 操作

```bash
# 检查当前配置
git remote -v

# 统一 push URL 为 SSH（使用 AWKN-Lab 组织 + 443 端口绕过防火墙）
git remote set-url --push origin ssh://git@ssh.github.com:443/AWKN-Lab/Mr.Mont.git

# 验证 SSH 认证
ssh -T git@ssh.github.com -p 443
# 预期输出：Hi AWKN-Lab! You've successfully authenticated, but GitHub does not provide shell access.
# 注意：exit code 1 是正常的（GitHub 不提供 shell access）
```

### 反例（2026-07-03 天火Life）

- fetch = `ssh://git@ssh.github.com:443/AWKN-Lab/Mr.Mont.git`（正确）
- push = `https://ghp_xxx@xiaxingxiaowei1983/Mr.Mont.git`（个人token+旧账号）
- push 成功靠 GitHub 重定向到 AWKN-Lab/Mr.Mont
- 风险：token 过期后 push 失败；重定向行为变化导致 push 失败

## E-A24：服务器备份策略调整（Git基线+dist.old，2026-07-03 新增）

> 来源：天火·人生决策宗师 Step 12+13 部署复盘（用户明确要求"不要在服务器上备份"）
> **本条替代 E-A10 的 cp -r 全量备份策略**

**核心断言**：回滚基线是 Git commit，不是服务器 cp -r 全量备份。服务器只保留 1 份 dist.old 做即时回滚。

### 新策略（替代 E-A10）

| 项 | 旧策略（E-A10） | 新策略（E-A24） |
|----|----------------|----------------|
| 回滚基线 | 服务器 cp -r + .bak-TS 累积 | **Git commit** |
| 服务器临时回滚 | dist.old + 多个 .bak-TS | **仅 dist.old**（下次部署覆盖） |
| 历史回滚 | 服务器保留多个 .bak-TS | **git reset → 重新部署** |
| 服务器空间 | 持续增长 | **稳定（仅 1 份 dist.old）** |

### 操作流程

**部署前**（Git 基线）：
```bash
git add -A && git commit -m "WIP 备份: $(date +%Y%m%d_%H%M%S)"
git push origin main
```

**服务器部署时**（仅保留 dist.old）：
```bash
ssh <host> "cd <parent-dir> && mv dist dist.old && mkdir dist"
rsync -avz --delete -e ssh <local-dist>/ <host>:<remote-dir>/dist/
chmod -R a+rX <remote-dir>/dist/
```

**即时回滚**（秒级）：
```bash
ssh <host> "cd <parent-dir> && rm -rf dist && mv dist.old dist && nginx -s reload"
```

**历史回滚**（分钟级）：
```bash
git reset --hard <commit-hash>
git push --force-with-lease origin main  # 需用户明确授权
# 重新构建 + 重新部署
```

### 禁止

- 在服务器累积 `.bak-TS` 历史备份（用户明确反对）
- 把服务器 cp -r 作为唯一回滚手段（Git 才是真相源）
- 不 commit 就直接部署（违反"先 Git 后服务器"原则）

## E-A25：Deploy Key vs Actions Secret 区分（2026-07-03 新增）

> 来源：天火·人生决策宗师 Step 12+13 部署复盘（用户询问 GitHub secret 配置）

**核心断言**：Deploy Key 和 Actions Secret 是两种不同的认证机制，概念不能混淆。

### 对比表

| 项 | Deploy Key | Actions Secret |
|----|-----------|----------------|
| 类型 | SSH 公钥 | 环境变量（加密） |
| 用途 | SSH push 认证 | GitHub Actions 自动化 |
| 标识 | SHA256 指纹 | 名称（如 `SSH_PRIVATE_KEY`） |
| 权限 | Read/write 或 Read-only | 由 workflow 决定 |
| 当前流程 | 足够（本地push+SSH手动部署） | 不需要 |

### 判断流程

```
当前部署方式是什么？
├── 本地 git push + SSH 手动部署 → Deploy Key 足够，不需要 Actions Secret
├── GitHub Actions 自动部署到服务器 → 需要 Actions Secret（SSH_PRIVATE_KEY, SERVER_HOST 等）
└── 混合模式 → Deploy Key + 按需 Actions Secret
```

### 反例（2026-07-03 天火Life）

- 用户看到 GitHub 仓库的 `mont`（SHA256指纹 + Read/write），误以为是 Actions Secret
- 实际是 Deploy Key（SSH公钥指纹），从未使用过
- 当前部署流程是"本地push + SSH手动部署"，不需要任何 Actions Secret
- 误设 Actions Secret 会增加维护成本（密钥轮换、权限管理）而无实际收益
