### 1.3 v1 报告的关键误解（2026-07-05 复核发现）

**误解**：v1 报告 §11.4 说"tide-inference.module.ts 当前仅注册 TideInferenceService"，暗示 TideJudgmentService 需要 DI 注册。

**真相**：
- `tide-judgment.service.ts` 第 49 行 `export class TideJudgmentService` 无 `@Injectable()` 装饰器
- 全部方法是 `static`（`static judgeTime` / `static judgePosition` / `static judgeMind` / `static judgePhase`）
- **静态类直接 `import { TideJudgmentService } from './tide-judgment.service'` 调用即可，无需 module 注册**

**影响**：P0-G3 接入路径简化 — 不需要改 `tide-inference.module.ts`，只需要在 `kline-tide.service.ts` 中 `import` 并调用静态方法。

## 二、核心矛盾分析

### 2.1 矛盾定义

```
产品目标：K线/潮汐接入问事，让用户看到"我现在好不好/为什么卡/什么时候能动"
当前现实：StateSnapshot 100% 是 seed/mock，LLM 推导入口从未触发
技术债务：tideInferenceService.inferAndPersist 写了但没被调用
```

### 2.2 三条可能的路径

| 路径 | 思路 | 优点 | 缺点 |
|---|---|---|---|
| **A. 先修 LLM 推导入口** | 让 `tideInferenceService.inferAndPersist` 真正被调用，生成真实 StateSnapshot，再接入 TideJudgmentService | 根本解决 mock 问题 | 改动大，需改 consult.service.ts 主链路 |
| **B. 先接 TideJudgmentService（基于现有 seed）** | 接入静态类，让 12 维有解释链，即使数据是 seed | 改动小，快速验证 UI 链路 | "在 mock 上叠规则解释"，违反 v1 报告约束 |
| **C. 拆分解释链与数据源** | TideJudgmentService 接入 + 显式标注 `dataSource: 'seed'/'llm'/'fallback'`，让前端可见数据来源 | 用户可见真相，不冒充 | 需要前端配合改 UI |

### 2.3 推荐路径：A + C 组合

**理由**：
1. v1 报告明确禁止"用模拟数据冒充真实能力" — 路径 B 单独使用违规
2. 路径 A 是根本解，但工作量大，不能快速见效
3. 路径 C 提供过渡方案 — 即使数据是 seed，用户也能看到"这是模拟数据"，不冒充
4. A + C 组合：先做 C（快速可见），再做 A（根本解），最后移除 C 的 seed 标注

## 三、三方案对比

### 方案 A：根本解（推荐 — 长期价值最高）

**路径**：修 LLM 推导入口 → 真实 StateSnapshot → 接入 TideJudgmentService → 接入问事

**步骤**：
1. 取证 `tideInferenceService.inferAndPersist` 未触发的根因（consult.service.ts:3244-3247）
2. 修复 LLM 推导入口，确保用户操作时真实生成 StateSnapshot
3. 接入 TideJudgmentService 静态方法到 kline-tide.service.ts
4. 清理 _seedStateSnapshots（v0.2 改为显式 mock 模式，仅管理员可触发）
5. 接入问事 prompt（任务 2 核心）
6. 接入 ResultPage 状态窗口

**工作量**：3-5 天
**风险**：改 consult.service.ts 主链路，可能影响现有问事功能
**回滚**：Git commit 分步提交，每步可独立回滚

### 方案 B：快速可见（短期收益快）

**路径**：接 TideJudgmentService 静态方法 + 数据源标注 → 灰度验证 UI → 再修 LLM 入口

**步骤**：
1. 在 kline-tide.service.ts 中 import TideJudgmentService，调用 buildTideJudgment
2. 在返回体中加 `dataSource` 字段（seed/llm/fallback）
3. 前端 /tide 页面显示"当前数据为模拟数据"提示（当 dataSource=seed 时）
4. 灰度验证 UI 链路完整
5. 然后做方案 A 的步骤 1-5

**工作量**：1-2 天（UI 验证）+ 3-5 天（根本解）
**风险**：UI 改动可能需要前端配合
**回滚**：纯添加，不删除现有逻辑，回滚安全

### 方案 C：最小治理（最保守）

**路径**：只做 P1 灰度前清理，不接问事，等扩容后再启动任务 2

**步骤**：
1. P1-G1 冻结 kline-decision.service.ts（加 @FROZEN 注释）
2. P1-G2 删除孤立 service 中未使用的 PrismaClient
3. P1-G3 清理 DTO 重复定义
4. P1-G4 清理 meta.note 内部阶段标记
5. P1-G5 补 tide-judgment.service.spec.ts 测试
6. 等服务器扩容后启动任务 2

**工作量**：0.5-1 天
**风险**：极低
**回滚**：每步独立 Git commit
