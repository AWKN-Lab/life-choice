## 〇、决策清单（来自与用户对齐）

| 决策点 | 选择 | 影响 |
|------|------|------|
| 范围 | 八字 + 六壬 | 不动奇门/周易/紫微/道德经 |

| 向量库 | **pgvector** | 与现有 Supabase/Postgres 栈一致 |
| 服务架构 | **升级现有 knowledge-service**（FastAPI，端口 8701） | 不重建、不换语言 |
| 硬编码知识 | ziping-agent 的调候/格局/十神表迁移为 JSON 读取 | 代码瘦身、知识可独立更新 |
| 典籍范围 | 八字全量（约 100+ 部）+ 六壬全量（约 50+ 部） | 一次性入库 |

## 二、目标与边界

### 2.1 本轮做（3-5）

1. **建立八字/六壬典籍向量库**（pgvector + BGE-Large-ZH）
2. **升级 knowledge-service** 为混合检索（向量+关键词）
3. **修复 bazi-knowledge-base 路径**：让八字结构化知识真正可检索
4. **ziping-agent 硬编码知识迁移为 JSON 读取**
5. **建立端到端验收**：八字/六壬咨询能命中典籍原文 + 结构化规则

### 2.2 本轮不做

- 奇门/周易/紫微/道德经/抱朴子/山医相灵宠典籍入库（下个迭代）
- 改造 RAG 生成层（generation-composer.service.ts）只接入检索结果
- 引入其他 embedding 模型（OpenAI/智谱）
- 替换为 TypeScript/Go 重建 knowledge-service
- 重新设计知识库 schema（沿用现有 Prisma + pgvector）
- 升级前端展示（仅后端能力升级）

### 2.3 约束

- 后端：NestJS + TypeScript + Prisma + Supabase
- Python 服务：FastAPI 8701（端口不冲突）
- 不引入新的外部 SaaS 依赖（BGE-Large-ZH 本地部署）
- 所有改动必须可回滚（Git commit 节点）
- 升级期间原关键词检索保持可用（兼容模式）

### 2.4 假设

- 假设 1：项目有 Supabase/Postgres 部署能力，pgvector 扩展可启用
- 假设 2：服务器有 CPU 资源运行 BGE-Large-ZH（≥8GB 内存可用）
- 假设 3：现有 passage 切分质量可用（preprocessed/ 21 部已切分）
- 假设 4：用户接受"向量库与原 JSON 共存"的过渡期

### 步骤 4｜pgvector 入库

**动作**：
- 在 Prisma schema 新增模型 `ClassicEmbedding`：
  ```prisma
  model ClassicEmbedding {
    id          BigInt   @id @default(autoincrement())
    passageId   String   @unique
    book        String
    chapter     String?
    systemType  String   // "bazi" | "liuren"
    text        String   @db.Text
    embedding   Unsupported("vector(1024)")
    source      String
    createdAt   DateTime @default(now())
    @@index([systemType])
    @@index([book])
  }
  ```
