```markdown
### 阶段 7.5｜项目质量评分卡（v2.8.8 新增，源自 E86/E87）

Verification 阶段不仅验证代码正确性，还必须对项目整体质量做量化评估。

**触发条件**：用户说"评估项目"/"项目现状"/"上线前检查"/"部署就绪"/"质量评估"

**评分流程（5 步强制）**：

1. **先读文件再打分**（E87 铁律）：每个维度打分前，必须先 Read 关键文件确认事实，禁止基于假设打分
2. **5 维评分卡**：

| 维度 | 权重 | 检查项 | 评分依据 |
|------|------|--------|----------|
| 算法/核心逻辑 | 30% | 核心算法准确率、对标竞品、边界case覆盖 | 对标测试+真机验证 |
| 后端集成 | 25% | API 完整度、数据流通、降级策略、错误处理 | 端到端调用+日志验证 |
| 前端完整度 | 20% | 页面路由、UI 逻辑、交互闭环、样式一致性 | 源码行数+浏览器验证 |
| 测试覆盖 | 15% | 单元/集成/E2E 测试、覆盖率、skipped 测试 | 测试运行结果 |
| 部署就绪 | 10% | Docker/CI-CD/HTTPS/数据库/安全/环境变量 | 文件存在性+内容验证 |

3. **三层验证**（E86 铁律）：
   - L1 代码存在：文件存在、函数定义完整
   - L2 功能生效：端到端调用验证功能真正可用
   - L3 部署可用：Docker 构建通过、环境变量齐全、健康检查通过

4. **评分标注规则**：
   - 已验证维度：标注 ✅ + 证据（文件路径/测试结果）
   - 待确认维度：标注 ⚠️ + 需补充的信息
   - 假设维度：标注 ❌ + 假设内容（必须先验证再打分）

5. **输出格式**：

| 维度 | 权重 | 得分 | 加权分 | 依据 | 验证层级 |
|------|------|------|--------|------|----------|
| 算法/核心逻辑 | 30% | X | X×0.3 | 证据 | L1/L2/L3 |
| 后端集成 | 25% | X | X×0.25 | 证据 | L1/L2/L3 |
| 前端完整度 | 20% | X | X×0.2 | 证据 | L1/L2/L3 |
| 测试覆盖 | 15% | X | X×0.15 | 证据 | L1/L2/L3 |
| 部署就绪 | 10% | X | X×0.1 | 证据 | L1/L2/L3 |
| **总分** | **100%** | — | **XX** | — | — |

**防偏差规则**：
- 任何维度不得在未读文件的情况下打分（E87）
- L1 通过 ≠ L2 通过 ≠ L3 通过（E86）
- 评分偏差 >15 分时，必须重新验证所有维度
```

## 更新2：新增 E86 经验

**位置**：E66 之后、十六、版本历史 之前

```markdown
## E86｜端到端验证门禁：改了代码≠功能通了（v2.8.8 新增，2026-06-16）

### E86.1 触发条件
- 修复 bug 后 / 改了代码后 / 编译通过后
- 功能不生效 / 降级 / fallback 触发

### E86.2 核心规则
修复 bug 后必须执行三层验证，不能只验证编译通过：
1. **编译验证**：tsc --noEmit 通过
2. **功能验证**：端到端调用验证功能生效（不只是编译通过）
3. **回归验证**：确认修复没有引入新问题

### E86.3 反例
`spawn()` → `spawnSync()` 后只跑 tsc --noEmit，没有实际调用 Python CLI 验证数据返回。结果：代码编译通过但 Python 引擎永远降级到 iztro，bug 存在数月未被发现。

### E86.4 防复发
- 修复 bug 后，必须构造最小端到端验证用例
- 验证用例必须覆盖"输入→处理→输出"完整链路
- 触发词：修复 bug / 改了代码 / 编译通过 / 功能不生效 / 降级 / fallback

### 教训来源
2026-06-16 人生决策宗师项目全流程深度复盘：spawn bug 存在数月因只验证编译
```

## 更新3：新增 E88 经验

**位置**：E86 之后

```markdown
## E88｜Prisma schema 变更后必须重新 generate（v2.8.8 新增，2026-06-16）

### E88.1 触发条件
- 修改 schema.prisma 后
- TypeScript 报 PrismaService / 字段类型不存在错误

### E88.2 核心规则
Prisma schema 变更后的标准流程（不可跳过）：
1. 修改 schema.prisma
2. `npx prisma migrate dev`（开发）或 `npx prisma migrate deploy`（生产）
3. **`npx prisma generate`**（重新生成 Client 类型 — 关键步骤）
4. `tsc --noEmit`（验证类型正确）

### E88.3 反例
修改 schema 后直接 tsc --noEmit，14 个类型错误。运行 `npx prisma generate` 后类型错误消失。

### E88.4 防复发
- schema 变更后，步骤 2-3 不可跳过
- 触发词：Prisma / schema 变更 / 类型不存在 / PrismaService / generate

### 教训来源
2026-06-16 人生决策宗师项目全流程深度复盘：schema 变更后 14 个类型错误
```
