## E86｜端到端验证门禁：改了代码≠功能通了（v2.8.8 新增，2026-06-16）

### E86.1 触发条件
- 修复 bug 后 / 改了代码后 / 编译通过后
- 功能不生效 / 降级 / fallback 触发

### E86.2 核心规则
修复 bug 后必须执行三层验证，不能只验证编译通过：
1. **编译验证**：tsc --noEmit 通过
2. **功能验证**：端到端调用验证功能生效（不只是编译通过）
3. **回归验证**：确认修复没有引入新问题

### E86.3 反例
`spawn()` → `spawnSync()` 后只跑 tsc --noEmit，没有实际调用 Python CLI 验证数据返回。结果：代码编译通过但 Python 引擎永远降级到 iztro，bug 存在数月未被发现。

### E86.4 防复发
- 修复 bug 后，必须构造最小端到端验证用例
- 验证用例必须覆盖"输入→处理→输出"完整链路
- 触发词：修复 bug / 改了代码 / 编译通过 / 功能不生效 / 降级 / fallback

### 教训来源

## E88｜Prisma schema 变更后必须重新 generate（v2.8.8 新增，2026-06-16）

### E88.1 触发条件
- 修改 schema.prisma 后
- TypeScript 报 PrismaService / 字段类型不存在错误

### E88.2 核心规则
Prisma schema 变更后的标准流程（不可跳过）：
1. 修改 schema.prisma
2. `npx prisma migrate dev`（开发）或 `npx prisma migrate deploy`（生产）
3. **`npx prisma generate`**（重新生成 Client 类型 — 关键步骤）
4. `tsc --noEmit`（验证类型正确）

### E88.3 反例
修改 schema 后直接 tsc --noEmit，14 个类型错误。运行 `npx prisma generate` 后类型错误消失。

### E88.4 防复发
- schema 变更后，步骤 2-3 不可跳过
- 触发词：Prisma / schema 变更 / 类型不存在 / PrismaService / generate

### 教训来源
2026-06-16 人生决策宗师项目全流程深度复盘：schema 变更后 14 个类型错误
