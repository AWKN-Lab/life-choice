## 三、批判性分析：5个被忽视的严重问题

### 问题1：知识库 bazi 路径断裂 — "八字咨询无典籍支撑"（P0 未修复）

**现象**：
- `loader.py` L29 加载 `knowledge-base/bazi/` 目录
- 实际 `knowledge-base/` 下只有 `liuren/`，没有 `bazi/`
- 结果：所有八字咨询的【参考知识】段为空

**批判性追问**：
- 为什么7份计划文档中只有"八字六壬典籍计划"提到这个问题，其他文档都忽略了？
- 答案：知识库是"看不见的后端能力"，前端验证无法发现，只有读代码才能确认
- 这正是 E86 铁律的典型案例：代码存在 ≠ 功能生效

**影响**：
- 张半山八字咨询时无法引用《滴天髓》《穷通宝鉴》
- 用户感知不到（LLM 仍会回复），但回复质量显著下降
- 与竞品（天辅智能）的"Curated Knowledge Base"差距拉大

**修复方案**：
1. 创建符号链接：`knowledge-base/bazi/` → `knowledge/eastern-metaphysics/八字命理/bazi-knowledge-base/`
2. 或修改 `loader.py` L29 指向正确路径
3. 验证：`curl /health` 返回 `baziItems > 30`

### 问题2：前端零测试 — "71个测试"已成历史（P1 严重退化）

**现象**：
- 多份计划文档引用"vitest 71/71 通过"作为验证基准
- 实际调研：`app/src/` 下 **0个** .test.ts/.test.tsx 文件
- vitest 基础设施已就绪（config + setup.ts），但无测试用例

**批判性追问**：
- 71个测试去哪了？是被删除了，还是从未存在过，还是文档虚假？
- 答案：可能是从其他项目（如 awkn-agent）复制了测试基准描述，但人生决策宗师项目本身从未有前端测试
- 这是 E87 铁律的典型案例：评分基于验证，不能基于假设

**影响**：
- 每次修改前端代码无回归保护
- "tsc通过=没问题"的假象持续误导决策
- 上线后前端 bug 只能靠用户发现

**修复方案**：
1. 为核心页面写最小测试套件（HomePage/ResultPage/ConsultPage 各3-5个用例）
2. 为核心工具函数写测试（intentRouter/consultDataMigration/localEngine）
3. 目标：20个测试用例，覆盖核心路径

### 问题3：ZIWEI_CLI_PATH 未文档化 — "Docker部署会静默降级"（P1 隐患）

**现象**：
- `ziwei-agent.service.ts` L275 读取 `process.env.ZIWEI_CLI_PATH`
- `.env.example` 中**没有**这个变量
- Dockerfile 中设置了 `ENV ZIWEI_CLI_PATH=/app/python-engine/paipan_cli.py`
- 但裸机部署（PM2）时如果 .env 中没有这个变量，代码会降级到硬编码路径

**批判性追问**：
- 之前会话中声称"已文档化"，为什么实际没有？
- 答案：可能写入了 `.env.prod.example`（后端目录），但未写入根 `.env.example`
- 两个 .env.example 文件（根目录 vs api-server 目录）造成混乱

**影响**：
- 裸机部署时 Python 引擎可能找不到 CLI
- 静默降级到 iztro，用户无感知但排盘准确率下降

**修复方案**：
1. 在 `awkn-life-backend/.env.example` 添加 `ZIWEI_CLI_PATH=`
2. 在 `awkn-life-backend/apps/api-server/.env.example` 添加 `ZIWEI_CLI_PATH=`
3. 文档说明：本地开发留空（用硬编码路径），生产环境必须设置

### 问题4：CI 部署路径前后端不一致 — "deploy job 可能失败"（P0 阻断）

**现象**：
- ci.yml deploy job：
  - 后端：`cd awkn-life-backend/apps/api-server`（从 `/opt/awkn-life` 起）
  - 前端：`cd /opt/awkn-life/apps/AWKN-LABlife/app`
- 后端路径缺少 `apps/AWKN-LABlife/` 前缀

**批判性追问**：
- 这个路径是正确的吗？也许生产服务器有符号链接？
- 答案：无法确认，但如果不一致，deploy job 会在 `cd awkn-life-backend` 时失败
- 这正是 E64 铁律的典型案例：tsc通过 ≠ 运行时正确

**影响**：
- push 到 main 分支后 deploy job 可能失败
- 后端不会更新，前端会更新，导致版本不一致

**修复方案**：
1. 确认生产服务器实际目录结构
2. 统一前后端路径前缀
3. 在 deploy job 中添加 `pwd && ls` 验证步骤

### 问题5：4个后端测试 skipped — "测试覆盖率虚高"（P2 质量隐患）

**现象**：
- 后端55个 .spec.ts 文件，但4个 `it.skip`
- skipped 的测试：合同咨询回访、创业现金流记忆、财运追问、大词追问
- 这些都是核心业务场景

**批判性追问**：
- 为什么 skip？是因为测试写错了，还是功能没实现？
- 答案：无法确认，但 skip 的测试等于没有测试
- 如果这些功能确实有问题，应该修复而不是 skip

**影响**：
- 测试通过率虚高（55个文件全绿，但4个核心场景未验证）
- 可能在生产环境中暴露这些场景的 bug

**修复方案**：
1. 逐个检查4个 skipped 测试的 skip 原因
2. 能修复的修复，不能修复的标注 TODO + issue
3. 目标：0个 skipped 测试

## 六、根因分析：为什么这些问题持续存在？

### 6.1 三层断裂带

```
第一层断裂：代码存在 ≠ 功能生效
  - spawnSync 已改但未端到端验证
  - /hybrid_search 已实现但 bazi 路径断裂
  - HTTPS 配置已写但未实际验证

第二层断裂：计划文档 ≠ 执行完成
  - 7份计划文档覆盖全面，但执行率约60%
  - 部分完成的项目被标记为"已完成"
  - 未完成的计划没有追踪到关闭

第三层断裂：测试通过 ≠ 质量达标
  - tsc 0 errors 但前端0个测试
  - 后端55个spec但4个skip
  - 无E2E测试
```

### 6.2 根因

**根因1：验证深度不足**
- 每次修改后只跑 tsc + build，不跑端到端验证
- 知识库路径断裂问题只有读代码才能发现，但没有人读

**根因2：计划文档碎片化**
- 7份计划文档有大量重叠（3份"上线前计划"）
- 没有统一的进度追踪，已完成/未完成状态混乱
- 部分计划写了但从未执行

**根因3：测试债务累积**
- 前端从始至终0个测试
- 后端4个skip测试无人处理
- "71/71通过"的基准可能是从其他项目复制的错误信息
