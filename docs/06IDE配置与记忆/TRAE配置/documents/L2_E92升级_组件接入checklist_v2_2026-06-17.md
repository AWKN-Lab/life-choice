## 教训

组件开发完成 ≠ 组件被使用。**规则写入 ≠ 规则执行**。E92 v1 刚写入就被违反——上次会话声称"8 个孤儿全部接入"，实际还有 7 个未扫描到，根因是扫描范围不完整。

## v1 规则（保留）
1. Grep 验证引用：`grep -r "import.*ComponentName" src/`
2. 路由/页面接线：确认组件在 JSX 中被渲染
3. 构建验证：`npm run build` 确认无 import 错误

## v2 新增规则（4 条）

### 规则 4：扫描必须全量覆盖
- 孤儿扫描必须用 `Glob **/*.tsx` 列全量清单，不能只扫部分子目录
- 不能依赖 search agent 的"局部扫描"——agent 可能只扫了 3 个子目录就报告"全部接入"
- 验证方法：Glob 全量清单 vs 已接入清单，差集 = 遗漏

### 规则 5：区分预装库和项目组件
- shadcn/ui 等预装组件库未使用是正常的，不算孤儿
- 只对"项目特定组件"（components 根级、业务子目录）做孤儿判定
- search agent 输出必须过滤预装库后再报告

### 规则 6：禁止 as any 绕过 props 类型
- 接入组件时必须读取组件实际 props 类型定义
- 禁止用 `as any` 绕过类型不匹配
- 如果 props 类型不匹配，要么修改调用方数据，要么修改组件 props 定义
- `as any` 是技术债，tsc 通过 ≠ 运行时安全

### 规则 7：重复文件必须先清理再接入
- 如果存在同名组件（如根级 KLineShareCard 和 kline/KLineShareCard），必须先确认哪个是正式版本
- 删除非正式版本，只接入正式版本
- 不能两个都接入，会导致维护混乱

### 反例 2：as any 绕过
```typescript
// 错误：用 as any 绕过类型
<BaZiDetail analysis={calcResult as any} gender={...} birthYear={...} />
// tsc 通过，但运行时如果 calcResult 结构不匹配 BaZiDetail 期望的 props，会崩溃
```

KLineShareCard 根级和 kline/ 各一个，两个都接入 → 改一个忘改另一个 → 维护混乱
