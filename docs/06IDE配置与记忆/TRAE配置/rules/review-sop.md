# 审核 SOP（Review Standard Operating Procedure）

> 适用范围：本仓库所有 Pull Request、合并请求、上线前质量门禁。
> 优先级：SYSTEM RULES ＞ SAFETY GATE ＞ 本规则。
> 来源：由 `_tmp_review_skill.md`（AWKN 审核 v4.0.0）正式化而来，作为 Trae IDE 规则常驻生效。

---

## 一、审核结论三选一（硬规则）

任何审核动作完成后，**必须且只能**给出以下三种结论之一。无结论不得流转。

| 结论 | 含义 | 触发条件 | 后续动作 |
| --- | --- | --- | --- |
| **放行（Approve）** | 所有必填检查项通过 | 必填项全部 PASS，无 P0/P1 阻断 | 进入合并 / CI/CD |
| **打回（Request Changes）** | 有必填项未通过 | 任一必填项 FAIL，或存在 P0/P1 问题 | 退回作者修复后重新提交 |
| **升级（Escalate）** | 超出当前审核人权限 | 涉及核心模块 / 安全 / 支付 / 隐私 / 数据库结构变更 | 转交 CTO 或对应 Owner 复审 |

> 禁止使用「感觉没问题」「应该可以」「看起来 OK」等模糊措辞作为结论。
> 禁止「无结论放行」——未给出明确三结论之一的，视为未完成审核。

## 二、审核优先级分级

| 优先级 | 含义 | 响应时效 | 完成时效 | 升级条件 |
| --- | --- | --- | --- | --- |
| **P0 阻断** | 不修不能合并，影响上线/安全/数据 | 30 分钟 | 2 小时 | 超时 → 拉架构师 |
| **P1 重要** | 不修留隐患，本次必须处理 | 2 小时 | 8 小时 | 超时 → 升级 P0 |
| **P2 改进** | 可在后续迭代处理 | 4 小时 | 24 小时 | 超时 → 升级 P1 |

**默认时效**：24 小时内首次响应，48 小时内完成审核。
**P0 阻断项**必须修复后才能放行；P1 重要项原则上本次修复，确需延后必须写入结果单并升版本；P2 改进项可记入 backlog。

## 三、审核维度（5 维度）

| 维度 | 关键检查点 |
| --- | --- |
| **功能** | 是否实现需求；核心闭环是否跑通；边界/异常/失败兜底是否覆盖 |
| **安全** | 无密钥泄露；无 SQL 注入；无 XSS；权限校验；AI prompt 注入防护；供应链安全 |
| **性能** | 无 N+1 查询；无内存泄漏；无阻塞主线程；关键链路有基准对比 |
| **可维护性** | 命名清晰；单一职责；无重复代码；关键逻辑有注释；不引入不必要的抽象 |
| **测试覆盖** | 新增/修改代码有测试；核心 service 至少 1 条测试；零测试 = 未交付（E28） |

## 四、PR 审核清单（必填检查项）

> 所有必填项必须 PASS 才能放行。任一 FAIL 即打回。

### 4.1 代码风格
- [ ] `npm run lint`（eslint）通过，无 error
- [ ] `npm run format`（prettier）通过，无格式差异
- [ ] 命名符合项目规范（驼峰/连字符按既有约定）

### 4.2 类型检查
- [ ] `npm run typecheck` 通过，无 TS error
- [ ] 新增类型定义完整，无 `any` 滥用（确需使用需注释说明）

### 4.3 单元测试
- [ ] 新增/修改代码有对应测试（E28 零测试门禁）
- [ ] `npm run test` 通过，无失败用例
- [ ] 核心 service 至少 1 条核心逻辑测试
- [ ] Zod/Yup/Joi schema 覆盖率 ≥ 90%（E24）

### 4.4 安全检查
- [ ] 无密钥/凭证硬编码（API Key、Token、密码、连接串）
- [ ] 无 SQL 注入风险（参数化查询 / ORM）
- [ ] 无 XSS 风险（`v-html`/`dangerouslySetInnerHTML` 必须经 DOMPurify 消毒）
- [ ] 权限校验完整（鉴权中间件 / 角色检查）
- [ ] AI 相关代码：prompt 注入防护 / 输出 JSON schema 验证 / 工具调用参数消毒
- [ ] 依赖无已知高危漏洞（npm audit / SBOM）

### 4.5 性能检查
- [ ] 无 N+1 查询（循环内禁止发 SQL/请求）
- [ ] 无内存泄漏（事件监听/定时器/订阅需清理）
- [ ] 无阻塞主线程的同步大计算
- [ ] 关键链路有基准对比，性能回归 ≤ 5%

### 4.6 文档更新
- [ ] API 变更同步更新接口文档
- [ ] 数据库 schema 变更同步更新数据库文档
- [ ] 新增模块同步更新 REPO-MAP.md / 工程交接文档
- [ ] 行为变更同步更新用户文档（如有）

### 4.7 可维护性
- [ ] 无空 try-catch（至少 `logger.error`）
- [ ] 无硬编码数字（超时/延迟/阈值提取为命名常量）
- [ ] 无重复代码（≥3 处相同逻辑需提取）
- [ ] 函数单一职责，单文件 < 2000 行（E26）

### 4.8 端到端接线（如涉及入口/路由）
- [ ] service 函数 ↔ API 路由 ↔ AI tool 三方对齐（E27）
- [ ] 入口文件修改有集成测试（E26）
- [ ] 模块独立 PASS + 入口调用链 PASS（E25）

## 五、审核豁免规则

| 豁免类型 | 豁免范围 | 必须条件 |
| --- | --- | --- |
| **docs-only** | 仅文档变更（*.md） | PR 标题标注 `[docs-only]`，可豁免 lint/typecheck/test/性能 |
| **配置变更** | 仅配置文件（.json/.yml/.env.example） | 仍需安全检查（密钥泄露）+ 文档同步 |
| **紧急修复** | 线上 P0 故障修复 | 需 CTO 口头放行，事后 24 小时内补审核 + 复盘 |

> 任何豁免必须在 PR 描述中明确标注，否则按全量检查执行。

## 六、审核流程

```
PR 创建 ──> 自动检查 (CI/lint/typecheck/test) ──> CODEOWNERS 自动分配 ──> 人工审核 ──> 三结论之一 ──> 合并/打回/升级
                                                          │
                                                          ├── 放行 (Approve)
                                                          ├── 打回 (Request Changes)
                                                          └── 升级 (Escalate to CTO/Owner)
```

### 6.1 审核人职责
1. 24 小时内首次响应
2. 按第四章节清单逐项检查
3. 给出明确三结论之一
4. 打回时必须列出具体修复项 + 优先级
5. 升级时必须说明升级原因 + 转交对象

### 6.2 作者职责
1. PR 描述填写完整（变更说明/类型/测试结果/风险/验收清单）
2. 自检通过后再提交审核（避免表演式审核）
3. 打回后按优先级修复，不绕过 P0
4. 升级后配合 CTO/Owner 复审
