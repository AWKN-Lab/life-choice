## 二、新建 meihua-agent 工作量评估

### 2.1 参考模板：六爻 Agent（最接近的 Agent）

以 [liuyao-agent.service.ts](file:///C:/Users/10919/Desktop/AWKN-Lab/人生决策宗师/AWKN-LABlife/awkn-life-backend/apps/api-server/src/liuyao-agent/liuyao-agent.service.ts) (645 行) 为模板：

| 模块 | 内容 | 估时 |
|------|------|------|
| **CalcEngine（排盘）** | 梅花易数起卦算法（年月日时 / 数字 / 文字起卦）、体用生克、互卦变卦 | 3-5 天 |
| **System Prompt** | `meihua-system-prompt.md`（300+ 行，含卦象解读、体用生克规则） | 2-3 天 |

| **Prompt 回归测试** | 与现有 Agent 交叉验证，确保不退化 | 1-2 天 |
| **总计** | | **10-15 天** |

### 2.2 梅花易数的技术特殊性

梅花易数与其他 Agent 的关键区别：

| 维度 | 六爻（已有） | 梅花（待建） |
|------|------------|-------------|
| 起卦方式 | 大衍筮法 / 手动摇卦 | 年月日时数 / 物数 / 字数 |
| 核心逻辑 | 纳甲 + 六亲 + 世应 | 体用生克 + 八卦类象 |
| 动爻规则 | 老阴老阳为动 | 动爻 = 总数÷6 余数 |
| 输出重点 | 用神旺衰 + 忌神原神 | 体卦用卦生克 + 互卦变卦 |
| CalcEngine 依赖 | `iching-shifa` npm 包 | **需从零实现或找第三方库** |

CalcEngine 是最大工作量——梅花易数目前没有现成的 npm 包（`iching-shifa` 只支持六爻），需要从零编写或找 Python 梅花易数库通过 pythonBridge 桥接。

## 三、替代方案评估

### 方案 A：用六爻替代梅花（推荐）

| 维度 | 评估 |
|------|------|
| **可行性** | 高。六爻和梅花都是卦象体系，在"感情要不要继续"场景中六爻的妻财/官鬼用神判断与梅花的体用生克可以达到相似的决策效果 |
| **改动量** | 仅修改调度决策树：感情场景 主调 六爻 + 佐调 紫微 |
| **用户体验** | 用户感知不到"梅花"和"六爻"的差异，张半山调度理由写「用六爻起卦帮你看看这段关系的走向」即可 |
| **风险** | 低。无需新增代码 |
| **代价** | 损失了梅花易数特有的"体用生克"分析维度（但对于 MVP 可接受） |

### 方案 B：用奇门替代梅花

| 维度 | 评估 |
|------|------|
| **可行性** | 中。奇门是时空盘，与感情分析的关联不如六爻直接 |
| **改动量** | 同上，修改调度决策树 |
| **推荐度** | 低于方案 A |

### 方案 C：新建 meihua-agent

| 维度 | 评估 |
|------|------|
| **可行性** | 可行但工作量大 |
| **时机** | Phase D，在 MVP 验证后再决定是否投入 |
| **前置条件** | 找到成熟的梅花易数计算库（npm 或 Python） |

## 四、推荐决策

**Phase B（MVP）：用六爻替代梅花。**

理由：
1. MVP 的目标是验证张半山调度层，不是补齐所有 Agent
2. 感情场景用六爻（妻财/官鬼用神）可以得出有效判断
3. 节省 10-15 天工期，优先验证核心假设
4. 如果用户反馈感情场景需要更深度的分析，Phase D 再新建梅花

### 4.1 调度决策树调整

```diff
| 感情要不要继续 | 分手/离婚/感情/ta爱不爱/第三者 |
-| **梅花** | **紫微** |
+| **六爻** | **紫微** |
| 「你是累了还是寒了？」 |
```

### 4.2 张半山调度理由文案（Phase B）

```
感情场景 → 调度理由：
「感情这件事，我用六爻起了一卦，看看你们之间的用神位在哪——是妻财得力还是官鬼当令。再让紫微看看你的夫妻宫和福德宫。」
```

### 4.3 Phase D 预留

如果以下条件满足，Phase D 新建 meihua-agent：
1. 用户反馈感情场景需要更细分（体用生克 vs 六亲用神）
2. 找到成熟的梅花易数计算库
3. MVP 验证通过，有资源投入新 Agent
