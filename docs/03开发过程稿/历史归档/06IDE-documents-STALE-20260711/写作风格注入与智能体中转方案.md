# 写作风格注入 + 智能体中转方案

## 目标一句话
将三套成熟写作方法论（吴梦知体、卡兹克公众号、AWKN爆款引擎）系统性地注入到现有 LLM 链路中，通过一个"写作智能体"作为后台与 LLM 之间的中转层，让所有断事输出具备一致的高质量自然语言风格。

## 本轮范围

### 本轮做
1. **写作风格能力盘点**：提炼三套方法论中可复用的核心原则，形成统一的能力矩阵
2. **智能体架构设计**：设计一个"写作中转智能体"的架构方案（不开发，先冻结方案）
3. **落地方案**：明确这个智能体如何插入现有链路、改哪些文件、改多少量
4. **MVP 切口**：确定最小的第一步（一个模块验证可行性）

### 本轮不做
- 不开发智能体代码（仅冻结架构方案）
- 不修改现有 Agent 的算法逻辑
- 不重构 LlmProvidersService 或 LlmGatewayService
- 不涉及前端改动

## 约束与假设
- 现有架构：LlmProvidersService（多Provider） → Agent（算法+LLM+兜底） → LlmGatewayService（路由+质量）
- 6 个 Agent：Ziping、Liuren、Quming、Qimen、Liuyao、Ziwei
- 3 个付费模块：morning（醒神早贴）、breakthrough（深入推演）、kline（人生K线）
- 目标：不改算法，只优化"从结构化数据到自然语言"这一段

## A. 三套写作方法论核心能力盘点

### 1. 吴梦知体 → 适用于"金句、标题、定性判断"

| 可复用原则 | 说明 | 适用场景 |
|-----------|------|---------|
| **意象转译法** | 抽象→具象：把"吉"翻译为"灯塔亮了"，"凶"翻译为"乌云压顶" | 醒神早贴 overview、深入推演定性句 |
| **矛盾统一法** | 制造语言张力："压力大到想掀桌，但也逼出你最硬的一面" | 醒神早贴 warnings、K线图注解 |
| **四字对仗法** | 凝练韵律："披荆为冠，斩棘为袍" | 深入推演金句、K线图标签 |
| **三段式黄金结构** | 引入→展开→升华 | 深入推演正文结构 |
| **痛点共情法** | 先承认痛苦，再给希望 | 醒神早贴 overview、深入推演开头 |
| **设问留白法** | 用问题代替答案，引导思考 | 深入推演结尾 |

### 2. 卡兹克公众号 → 适用于"长文、分析、对话感"

| 可复用原则 | 说明 | 适用场景 |
|-----------|------|---------|
| **活人感** | "有见识的普通人在认真聊一件打动他的事" | 所有模块的 LLM System Prompt |
| **节奏感** | 句子时长时短，一句一段制造重点 | 深入推演正文 |
| **知识输出方式** | "聊着聊着顺手掏出来"，不是"下面我来科普" | 术语解释 |
| **私人视角** | 用"我觉得""我自己也经历过"连接个人 | 醒神早贴 daily_tips |
| **判断力** | 敢下判断，不模棱两可 | 深入推演结论 |
| **对立面理解** | 先站读者角度承认处境合理，再给不同视角 | 醒神早贴 stop_doing |
| **L1-L4 四层自检** | 硬性规则→风格一致性→内容质量→活人感 | 所有输出质检 |
| **绝对禁区** | 禁用"首先其次""综上所述""说白了""意味着" | 所有 LLM Prompt 注入 |

### 3. AWKN 爆款引擎 → 适用于"结构化输出、去 AI 味"

| 可复用原则 | 说明 | 适用场景 |
|-----------|------|---------|
| **认知工程学** | 不教"做什么"，重构读者"是谁" | 深入推演核心论点 |
| **6 模块结构** | 钩子→痛点→承诺→核心→金句→赋权 | 深入推演结构模板 |
| **7 轮编辑法** | 清晰度→语气→So What→证据→具体性→情感→零风险 | 输出后处理管道 |
| **去 AI 味词表** | 禁用"赋能、抓手、闭环、综上所述" | 所有 LLM 输出清洗 |
| **语气控制** | "朋友式的叛逆者"：像朋友聊天，不像老师讲课 | System Prompt 注入 |
| **金句提炼** | 每段 1 句可摘录金句，斜体标记 | 深入推演 + 醒神早贴 |

### 三套方法论的交叉互补

```
吴梦知体 ──→ 负责"一句话能记住"（金句、意象、对仗）
卡兹克体 ──→ 负责"读完像跟人聊天"（活人感、节奏、判断力）
爆款引擎 ──→ 负责"结构能传播"（钩子、去AI味、质量检查）
```

## B. 智能体架构设计

### B.1 为什么需要一个"写作智能体"

**现状问题：**

```
当前每个 Agent 各自写自己的 System Prompt，导致：
  ├── 醒神早贴 → 算法兜底（我们刚优化过）
  ├── 深入推演 → 独立的 System Prompt（在 generateFastModuleJson 中硬编码）
  ├── K线图    → 纯算法模板 + LLM 注解
  ├── 六壬断事 → liuren-system-prompt.md
  ├── 六爻断事 → liuyao-system-prompt.md
  └── 八字分析 → ziping-agent 内部 prompt

问题：
  1. 风格不统一：同一个用户的六壬结果和八字结果读起来像两个人写的
  2. 维护成本高：改一个写作原则要改 5+ 个文件
  3. 质量参差：有的 Agent prompt 写得好，有的写得很模板化
  4. 没有统一的"去 AI 味"后处理
```

**有了写作智能体后：**

```
所有 Agent 的输出 → 写作智能体（统一风格注入 + 后处理） → 最终输出

好处：
  1. 风格统一：所有断事结果读起来像同一个人写的
  2. 维护成本低：改写作原则只改一处
  3. 质量可控：统一质检管道
  4. 可实验：A/B 测试不同风格版本
```

### B.2 智能体定位：不替代 Agent，包装 Agent

**写作智能体不是另一个 Agent Service。** 它是一个**后处理管道**，插入在"LLM 输出"和"前端渲染"之间。

```
当前链路：
  排盘数据 → Agent.analyzeWithLLM() → LLM 返回 JSON → 前端渲染

新链路：
  排盘数据 → Agent.analyzeWithLLM() → LLM 返回 JSON 
    → WritingPipeline.process()  ← 新增
      ├── Pre: 风格 System Prompt 注入（改写 Agent 的 System Prompt）
      ├── Mid: 实时风格参数注入（temperature、maxTokens 调整）
      └── Post: 输出后处理（去AI味 + 金句提炼 + 活人感检查）
    → 前端渲染
```

### B.3 模块边界

```
WritingPipeline（新增模块 src/writing-pipeline/）
├── writing-pipeline.service.ts   — 核心：后处理管道
├── style-profiles/               — 风格配置
│   ├── wumengzhi.profile.ts      — 吴梦知体：意象库、对仗模板、金句规则
│   ├── khazix.profile.ts         — 卡兹克体：口语词组、禁用词表、节奏规则
│   └── awkn-viral.profile.ts     — 爆款体：结构模板、7轮编辑、去AI味词表
├── processors/
│   ├── pre-processor.ts          — 前置：System Prompt 风格增强
│   ├── post-processor.ts         — 后置：去AI味 + 风格润色
│   └── quality-checker.ts        — 质检：L1-L4 四层自检
└── writing-pipeline.module.ts    — NestJS 模块
```

### B.4 关键设计决策

**决策 1：前置注入 vs 后置改写**

| 方案 | 优点 | 缺点 |
|------|------|------|
| **前置注入**（修改 System Prompt） | LLM 原生生成，风格自然融入 | 增加 token 消耗，可能影响 JSON 格式 |
| **后置改写**（LLM 输出后再调一次 LLM） | 不干扰原有逻辑 | 增加一次 LLM 调用，延迟翻倍，成本翻倍 |
| **混合方案（推荐）** | 前置注入风格约束 + 后置做轻量去 AI 味清洗 | 复杂度可控 |

**推荐混合方案：**
- **前置**：在 Agent 的 System Prompt 中注入精简版风格约束（~200 tokens），不破坏原有 JSON Schema
- **后置**：对 LLM 输出的文本字段做规则化清洗（去禁用词、去套话、加口语化），**不再调 LLM**

**决策 2：独立模块 vs 嵌入现有 Agent**

| 方案 | 优点 | 缺点 |
|------|------|------|
| 独立 WritingPipeline | 统一维护，风格一致 | 需要修改所有 Agent 的调用链 |
| 嵌入每个 Agent | 改动小 | 维护成本高，风格不统一 |

**推荐独立模块**：`@Global()` 模块，所有 Agent 通过依赖注入获取 `WritingPipelineService`。

**决策 3：全量覆盖 vs 渐进式**

| 方案 | 优点 | 缺点 |
|------|------|------|
| 全量覆盖所有 6 个 Agent | 一步到位 | 风险大，验证困难 |
| 渐进式（先 1 个 Agent + 1 个付费模块） | 风险可控，可验证 | 周期长 |

**推荐渐进式**：先改造 `liuren-agent` + `morning`（醒神早贴），验证效果后再推广。

## C. MVP 切口：最小可验证的第一步

### MVP 目标
验证"写作智能体"能否显著提升醒神早贴的自然语言质量。

### MVP 范围
- **新建** `src/writing-pipeline/` 模块（4 个文件）
- **修改** `consult.service.ts` 的 `generateMorningContent()` 调用 WritingPipeline
- **不改** Agent 内部逻辑、不改前端

### MVP 验收标准
1. 醒神早贴的 LLM 输出经过 WritingPipeline 后处理
2. 后处理后的文本不含禁用词（"首先""其次""综上所述""说白了"等）
3. overview 字段包含至少 1 个具象意象（来自吴梦知体意象库）
4. daily_tips 字段使用口语化表达（"你""我觉得"等）
5. 后处理不改变 JSON Schema 结构
6. 后处理延迟 < 50ms（纯规则，不调 LLM）

### MVP 三步走

```
Step 1: 创建 WritingPipeline 模块骨架
  └── writing-pipeline.module.ts + service.ts + 3 个 profile 文件

Step 2: 实现后处理器（post-processor.ts）
  └── 去 AI 味 + 禁用词替换 + 口语化词组注入

Step 3: 接入醒神早贴验证
  └── consult.service.ts → generateMorningContent() → pipeline.process()
```

## H. 总结：这个智能体解决什么问题

| 问题 | 当前状态 | 智能体解决后 |
|------|---------|-------------|
| 风格不统一 | 六壬结果和八字结果像两个人写的 | 统一风格 profile，所有输出读起来像同一个人 |
| 维护成本高 | 改一个写作原则要改 5+ 个文件 | 只改 WritingPipeline 一处 |
| AI 味重 | 频繁出现"综上所述""首先其次" | 后置清洗自动去 AI 味 |
| 金句缺失 | 输出只有信息，没有记忆点 | 吴梦知体意象转译自动生成金句 |
| 质量不可控 | 每个 Agent 各自质检 | 统一 L1-L4 四层自检管道 |
| 无法实验 | 改 prompt 要改代码部署 | 风格 profile 可配置，支持 A/B 测试 |
