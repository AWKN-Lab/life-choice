# 三法融合与知识库数据化计划

> 版本：v1 | 日期：2026-05-14 | 状态：计划阶段

---

## A. 目标与边界

### 目标一句话
将大六壬、六爻、小六壬三种断事能力融合为统一入口，将断事规则、神煞对照、格局判定写成可计算的规则引擎，LLM只负责自然语言包装。

### 核心架构原则
**规则引擎做计算，LLM做包装。**
- 确定性推理（神煞触发、格局判定、吉凶判断、交叉验证）→ 规则引擎 if-then 计算
- 不确定性表达（白话翻译、场景化建议、自然叙述、语气温度）→ LLM 包装
- LLM不再被要求"记住"断事规则，只被要求"翻译"规则引擎的结构化输出

### 本轮做（5项）
1. 统一断事入口：用户一个自然语言问题 → 系统自动选择1-3种方法并行断事 → 交叉验证输出综合结论
2. 新建小六壬Agent：补齐三种断事能力的最后一块拼图
3. 规则引擎数据化：将神煞对照、格局判定、分类占断逻辑写成 if-then 可计算规则
4. LLM自然语言包装管线：规则引擎输出结构化JSON → LLM翻译为自然叙述
5. 多方法交叉验证逻辑：规则引擎判定"一致/互补/冲突"，LLM包装输出

### 本轮不做（5项）
1. 不修改八字/紫微/奇门/取名等已有Agent
2. 不修改前端UI（融合逻辑在服务端完成）
3. 不做向量检索/语义搜索（规则引擎的确定性计算替代模糊匹配）
4. 不让LLM"记住"或"推理"断事规则（LLM只管语言表达）
5. 不删除现有独立Agent入口（保留向后兼容）

### 约束与假设
- 小六壬从零新建，参考六爻Agent的架构模式
- 规则引擎以 TypeScript 实现，不依赖 Python 引擎
- 规则格式：JSON定义条件+结论，引擎解释执行
- 交叉验证为规则引擎的确定性判断（非LLM判断）
- LLM输入永远是结构化的规则引擎输出，LLM输出永远是自然语言
- 所有变更保持向后兼容，现有API不受影响

## B. 当前状态分析

### B.1 三种断事能力对比

| 维度 | 大六壬 | 六爻 | 小六壬 |
|------|--------|------|--------|
| Agent服务 | `liuren-agent` ✅ | `liuyao-agent` ✅ | ❌ 不存在 |
| 算法引擎(TS) | `liuren-engine.ts` (400行) | `iching-shifa` 库 | ❌ 无 |
| 算法引擎(Python) | `knowledge-base/tools/da_liu_ren/` (11个模块) | `knowledge-base/tools/liu_yao/` (6个模块) | ❌ 无 |
| Prompt文件 | 5个（系统+分析+神煞+分类+节气） | 1个（系统） | ❌ 无 |
| 案例库 | `东方术数/六壬/案例库/案例.txt` | 经典卦例库（Python） | ❌ 无 |
| 分析深度 | 极深（八门断事+毕法赋+分类占断） | 中等（用神/原神/忌神/仇神） | ❌ 无 |
| 适用场景 | 复杂多变量决策、长期趋势 | 具体yes/no问题、短期判断 | 快速日常决策 |

### B.2 当前架构问题

```
用户提问 → router.service.ts → 选一个Agent → 单方法输出
                                    ↓
                          一次只能用一个方法
                          没有交叉验证
                          没有知识库检索
```

**具体问题**：
1. **孤岛架构**：三个Agent独立运行，router.service.ts 通过关键词匹配选一个，无法并行
2. **知识库断层**：Python引擎（`knowledge-base/tools/`）有完整算法但NestJS后端不调用，Prompt里写死知识而非动态检索
3. **案例浪费**：案例.txt 和经典卦例库只是文件，LLM看不到也搜不到
4. **无交叉验证**：用户对同一问题用不同方法得到矛盾结论时，系统无法给出"综合判断"

### B.3 知识库资产盘点

| 资产类型 | 位置 | 格式 | 规模 | 可数据化程度 |
|---------|------|------|------|------------|
| 六壬案例 | `东方术数/六壬/案例库/案例.txt` | 自然语言 | ~3个完整案例 | 中（需人工结构化） |
| 六壬神煞 | `prompts/六壬神煞总览.md` | Markdown表格 | ~100条 | 高（已是结构化表格） |
| 六壬分类占断 | `prompts/分类占断纲要.md` | Markdown | ~50条规则 | 高 |
| 六壬节气月将 | `prompts/节气月将对照表.md` | Markdown表格 | 24条 | 高 |
| 六爻经典卦例 | `knowledge-base/tools/liu_yao/` | Python数据结构 | 不确定 | 高 |
| 六爻断卦规则 | `ly_duangua.py` | Python代码 | ~120行逻辑 | 高 |
| 毕法赋 | `knowledge-base/tools/da_liu_ren/dlr_bifa.py` | Python | 100条赋文 | 高 |
| 命理法则 | `knowledge-base/命理法则索引.md` | Markdown | ~200条 | 高 |
| 经典原文 | `knowledge-base/preprocessed/` + `sources/` | Markdown | 45篇 | 中（需分段索引） |

## C. 目标架构

```
用户自然语言提问
        ↓
┌───────────────────────────────────────┐
│      统一断事入口 (DivinationHub)       │
│  意图识别 → 方法选择 → 并行调度         │
│  【LLM负责：理解用户意图，选择方法】      │
└───────────────────────────────────────┘
        ↓           ↓           ↓
   ┌────────┐ ┌────────┐ ┌──────────┐
   │ 大六壬  │ │  六爻   │ │  小六壬   │
   │ Agent  │ │ Agent  │ │  Agent   │
   └────────┘ └────────┘ └──────────┘
        ↓           ↓           ↓
┌─────────────────────────────────────────────┐
│              规则引擎 (RuleEngine)            │
│  输入：排盘数据（干支/神煞/卦象/课体）         │
│  处理：if-then 规则链求值                     │
│  输出：结构化断事JSON（吉凶/风险/时间窗/宜忌）  │
│                                             │
│  ┌────────────┐ ┌────────────┐ ┌─────────┐  │
│  │ 神煞触发器  │ │ 格局判定器  │ │ 分类占断  │  │
│  │(条件→神煞) │ │(月令透干→格)│ │(问题→规则)│  │
│  └────────────┘ └────────────┘ └─────────┘  │
│                                             │
│  规则格式示例：                               │
│  {                                          │
│    "id": "shensha-001",                     │
│    "condition": {                           │
│      "dayGanZhi": "丙午",                    │
│      "monthJian": "辰"                       │
│    },                                       │
│    "then": {                                │
│      "shensha": "月厌",                      │
│      "level": "凶",                          │
│      "judgment": "谋事多阻，不宜嫁娶出行"      │
│    }                                        │
│  }                                          │
└─────────────────────────────────────────────┘
        ↓
┌─────────────────────────────────────────────┐
│       交叉验证引擎 (CrossValidator)           │
│  【规则引擎判定：一致/互补/冲突】              │
│  输入：各方法的结构化结论                      │
│  规则：≥2方法结论方向相同→一致                 │
│        结论方向不同但无矛盾→互补               │
│        结论方向相反→冲突                      │
│  输出：交叉验证结果JSON                       │
└─────────────────────────────────────────────┘
        ↓
┌─────────────────────────────────────────────┐
│         LLM 自然语言包装层 (NLPacker)         │
│  输入：规则引擎JSON + 交叉验证JSON            │
│  LLM任务：                                   │
│  1. 将结构化结论翻译为自然叙述                │
│  2. 术语紧跟白话翻译                          │
│  3. 生成"落一句实在话"                       │
│  4. 生成场景化行动建议                        │
│  5. 禁止巴纳姆效应                           │
│  输出：用户可读的自然语言                      │
└─────────────────────────────────────────────┘
        ↓
    综合输出（自然语言 + 结构化证据）
```

**关键数据流**：
```
排盘数据 → 规则引擎(if-then) → 结构化结论 → LLM(翻译包装) → 自然语言
                                                      ↑
                                         案例库(作为LLM的参考素材)
```

## D. 分步清单

### Step 1｜规则引擎核心：RuleEngine 服务

**动作**：新建通用规则引擎服务，支持加载 JSON 规则文件并执行 if-then 求值

**产出**：
- 新增 `src/shared/rule-engine/rule-engine.service.ts`
- 规则加载器：从 JSON 文件加载规则集
- 规则求值器：遍历规则链，匹配 condition → 收集 then
- 规则DSL定义文件：`src/shared/rule-engine/rule-types.ts`

**规则 DSL 规范**：

```typescript
// 条件运算符
type ConditionOp = 'eq' | 'neq' | 'in' | 'notIn' | 'contains' | 'gte' | 'lte' | 'between';

// 单条规则
interface Rule {
  id: string;           // 唯一标识，如 "shensha-yueyan"
  category: string;     // 分类：shensha | pattern | zhanduan | jixiong
  priority: number;     // 优先级（冲突时高优先覆盖）
  source: string;       // 来源，如 "毕法赋第3条"
  condition: Record<string, ConditionClause>;  // 条件组（AND逻辑）
  then: Record<string, unknown>;               // 结论
}

// 条件子句
interface ConditionClause {
  op: ConditionOp;
  value: unknown;
}

// 规则集
interface RuleSet {
  name: string;         // 如 "liuren-shensha"
  version: string;
  rules: Rule[];
}
```

**验收标准**：
- 支持加载 JSON 规则文件并执行求值
- 输入排盘数据 → 遍历所有规则 → 返回匹配的结论数组
- 规则冲突时按 priority 取高优先
- 单次求值 < 10ms（100条规则以内）
- 支持热加载（修改规则文件无需重启）

**验证方法**：
1. 加载神煞规则集，输入 `{dayGanZhi: '丙午', monthJian: '辰'}` → 返回匹配神煞列表
2. 输入不匹配任何规则的数据 → 返回空数组
3. 修改规则JSON文件 → 调用 reload() → 新规则生效

### Step 6｜交叉验证引擎（CrossValidator）

**动作**：新建交叉验证服务，对多方法结果进行对比分析

**产出**：
- 新增 `src/divination-hub/cross-validator.service.ts`
- 交叉验证规则定义文件

**验收标准**：
- 三种交叉验证结论：
  1. **一致**：≥2个方法结论方向相同 → 加强结论置信度，输出"三法合参，结论一致"
  2. **互补**：方法从不同角度给出不矛盾的结论 → 综合视角，输出"六壬看趋势，六爻看节点"
  3. **冲突**：结论方向相反 → 标注分歧，给出各方法置信度，让用户自行判断
- 交叉验证结论包含：各方法摘要、一致性判断、综合建议、注意事项
- 单方法时不触发交叉验证，正常输出

**验证方法**：
1. 用案例.txt中"合作赚钱"问题 → 六壬+六爻都偏正面 → 输出"一致"
2. 构造一个"吉凶参半"的问题 → 输出"互补"
3. 单方法调用 → 不触发交叉验证

### Step 7｜LLM自然语言包装管线（NLPacker）

**动作**：新建 LLM 包装服务，接收规则引擎的结构化输出，转换为自然语言

**产出**：
- 新增 `src/divination-hub/nl-packer.service.ts`
- LLM 包装 Prompt 模板：`src/divination-hub/prompts/nl-packer-prompt.md`
- 修改三个 Agent 的 LLM 调用：不再让 LLM 推理规则，只让它翻译

**包装 Prompt 核心要求**：
```
你是一个命理断事翻译器。你的输入是规则引擎的结构化结论，你的任务是将它翻译为自然、有温度的中文叙述。

【禁止做的事】
- 不要添加规则引擎输出中没有的断语
- 不要编造经典引用
- 不要使用巴纳姆效应语句
- 不要说你"分析"或"推算"了什么（那是规则引擎做的）

【必须做的事】
1. 将结构化结论翻译为自然叙述，结论先行
2. 每个术语紧跟白话翻译，一段不超过3个术语
3. 基于规则引擎的"applicable"字段生成场景化行动建议
4. 生成"落一句最实在的话"（30字以内）
5. 标注规则来源（如"（据毕法赋）"）

【输入格式】
你收到的输入是以下JSON：
{
  "structuredConclusion": { ... },  // 规则引擎输出
  "crossValidation": { ... },       // 交叉验证结果（多方法时）
  "caseReferences": [ ... ]         // 参考案例（如有）
}

【输出格式】
纯自然语言，不要JSON，不要Markdown格式。
```

**验收标准**：
- LLM Prompt 中不包含任何断事规则（神煞/格局/用神等）
- LLM 输入为结构化 JSON，LLM 输出为自然语言
- 包装后的输出与参考案例（案例.txt）风格一致：结论先行、术语翻译、行动建议、结尾金句
- 规则引擎输出为空时 → LLM 输出兜底语句（"当前数据不足以做出判断"）
- 禁止巴纳姆效应检测仍然生效

**验证方法**：
1. 用规则引擎输出测试 → LLM 翻译结果自然通顺
2. 对比改造前后输出 → 规则引擎模式下的"准确度"不下降（人工review）
3. 检查 LLM Prompt → 无神煞规则、无格局判定逻辑、无用神规则
4. 检查 LLM 输出 → 无编造的经典引用

## H. 关键设计决策

### 为什么规则引擎而不是向量检索？
- **确定性**：神煞触发、格局判定、吉凶判断是确定性推理，不需要模糊匹配
- **可解释性**：每条结论都能追溯到具体规则（`source` 字段），用户可以追问"为什么"
- **可维护性**：修改规则只需编辑 JSON 文件，不需要重新训练或重建索引
- **性能**：100条规则求值 < 10ms，向量检索 + LLM 至少 500ms
- **LLM的角色清晰**：规则引擎管"对错"，LLM管"好听"

### 为什么保留 LLM 包装层？
- 规则引擎输出是 JSON，用户需要自然语言
- 场景化建议需要 LLM 的常识推理（"事业可冲"→"怎么做"）
- 语气温度、口语化表达是 LLM 的强项
- 案例参考需要 LLM 做上下文融合

### LLM 包装层的输入输出契约
```
输入（规则引擎）→ 输出（LLM）
"贵人相助"       → "现在正好有人愿意帮你，抓住这个机会"
"谋事多阻"       → "这段时间做事容易卡壳，别硬推，等时机"
"财爻旺相"       → "钱能进来，但要算清楚分账，别光看热闹"
```

### 为什么保留独立Agent入口？
- 有些场景只需要快速六爻断事，不需要六壬的深度分析
- 向后兼容：现有调用方不受影响
- 渐进式迁移：DivinationHub先作为可选增强，稳定后切换默认

### 小六壬 vs 大六壬的定位差异？
- 小六壬：快速日常决策（"今天宜不宜出门"），3秒出结果
- 大六壬：复杂多变量决策（"这个合作能不能做"），深度推演
- 六爻：具体yes/no判断（"这次面试能不能过"），精准打击
