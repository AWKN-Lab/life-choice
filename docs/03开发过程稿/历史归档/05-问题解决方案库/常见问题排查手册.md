## 1. LLM 相关问题

### 1.1 LLM 调用超时（180s timeout）

| 项目 | 内容 |
|------|------|
| **症状** | 请求 LLM 接口后长时间无响应，最终抛出 180s 超时错误 |
| **影响范围** | 所有依赖 LLM 的功能（咨询、解读、Agent 推理） |
| **常见原因** | Provider 服务端故障；网络波动；请求 payload 过大导致推理时间过长 |

**排查步骤：**

1. 检查当前 Provider 状态（访问 Provider 状态页或 API health endpoint）
2. 确认网络连通性（`curl` 或 `ping` 测试）
3. 检查请求 payload 大小，是否超出模型 context window
4. 查看 PM2 日志中是否有超时记录：`pm2 logs --lines 100`

**解决方案：**

- 切换备用 Provider（MiniMax ↔ OpenAI ↔ Moonshot）
- 减小单次请求 token 数，拆分为多轮对话
- 调整 timeout 配置（仅在确认网络稳定时）

### 1.2 LLM 返回 JSON 格式错误

| 项目 | 内容 |
|------|------|
| **症状** | LLM 返回内容无法被 `JSON.parse()` 解析，或字段缺失/类型错误 |
| **影响范围** | 结构化输出场景（八字解读、六壬分析、决策建议） |
| **常见原因** | Prompt 约束不够严格；模型幻觉导致格式偏移；未做 schema 验证 |

**排查步骤：**

1. 打印 LLM 原始返回内容，确认格式偏移位置
2. 检查 prompt 中 JSON 格式约束是否明确（示例、字段列表、类型声明）
3. 确认是否因 context 过长导致模型截断输出

**解决方案：**

- 在 prompt 中增加 JSON schema 约束与示例
- 添加 `zod` / `ajv` 等 schema 验证层，解析失败时重试
- 使用 `response_format: { type: "json_object" }`（OpenAI 兼容接口）

### 1.3 LLM 杜撰经典引用

| 项目 | 内容 |
|------|------|
| **症状** | LLM 输出中引用了不存在的经典文献、伪造的原文或错误的出处 |
| **影响范围** | 命理解读、经典引用、学术性内容 |
| **常见原因** | sourceId 覆盖率不足；未启用强制检索模式；模型幻觉 |

**排查步骤：**

1. 检查知识库 sourceId 覆盖率，确认引用来源是否在库中
2. 确认是否启用了 RAG 强制检索模式
3. 对比 LLM 输出与知识库原文，定位杜撰内容

**解决方案：**

- 启用强制检索（Force Retrieval），禁止模型自由生成引用
- 扩充知识库 sourceId 覆盖范围
- 在 prompt 中明确约束："仅引用知识库中存在的原文，不得编造"

### 1.4 Barnum 语句检测

| 项目 | 内容 |
|------|------|
| **症状** | LLM 输出包含巴纳姆效应语句（"你有时候很外向，有时候又很内向"等模糊泛化描述） |
| **影响范围** | 命理解读、性格分析、决策建议 |
| **常见原因** | 模型倾向生成安全但无信息量的语句；prompt 未约束具体性 |

**排查步骤：**

1. 检查 `barnum-phrases.ts` 过滤词库是否加载
2. 确认输出是否经过 Barnum 过滤管道
3. 统计 Barnum 语句命中率

**解决方案：**

- 确保 `barnum-phrases.ts` 过滤管道在 LLM 输出链路中生效
- 扩充 Barnum 短语词库
- 在 prompt 中增加约束："禁止使用模糊泛化描述，必须给出具体可验证的判断"

### 1.5 Moonshot 账户被封

| 项目 | 内容 |
|------|------|
| **症状** | Moonshot API 返回 401/403 错误，所有请求被拒绝 |
| **影响范围** | 以 Moonshot 为默认 Provider 的功能 |
| **常见原因** | 账户欠费、违规使用、API Key 过期 |

**排查步骤：**

1. 确认 Moonshot 账户状态（登录控制台检查）
2. 检查 API Key 是否有效
3. 查看 PM2 日志中的错误码

**解决方案：**

- 系统应自动降级到备用 Provider（MiniMax / OpenAI）
- 检查 Provider 路由配置中的 fallback 链路
- 联系 Moonshot 客服恢复账户

## 2. 命理计算问题

### 2.1 真太阳时校准偏差

| 项目 | 内容 |
|------|------|
| **症状** | 出生时间校准后与预期真太阳时存在数分钟到数十分钟偏差 |
| **影响范围** | 八字排盘、所有依赖出生时间的命理计算 |
| **常见原因** | 经度数据不准确；时区处理错误；solarTime.ts 算法偏差 |

**排查步骤：**

1. 检查输入的出生地经度数据是否准确（精确到小数点后2位）
2. 验证 `solarTime.ts` 中的真太阳时计算公式
3. 与权威天文历表对比校准结果

**解决方案：**

- 更新经度数据库，确保城市/区县级别精度
- 验证 `solarTime.ts` 中的均时差（Equation of Time）计算
- 增加与天文历表的自动化对比测试

### 2.2 八字排盘精度问题

| 项目 | 内容 |
|------|------|
| **症状** | 四柱八字与手动排盘结果不一致，尤其是月柱和时柱 |
| **影响范围** | 八字解读、命理分析 |
| **常见原因** | 节气计算精度不足；bazi-data.service.ts 数据源错误；闰月处理不当 |

**排查步骤：**

1. 使用已知八字案例（如名人八字）进行对比验证
2. 检查 `bazi-data.service.ts` 中的节气交接时间数据
3. 确认闰月场景的处理逻辑

**解决方案：**

- 更新节气交接时间数据源（使用天文精确计算而非查表法）
- 增加边界测试用例（节气交接时刻出生、闰月出生）
- 与多个权威排盘工具交叉验证

### 2.3 六壬起课规则不完整

| 项目 | 内容 |
|------|------|
| **症状** | 六壬排盘结果缺少四课/三传，或九宗门取法错误 |
| **影响范围** | 大六壬起课与解读 |
| **常见原因** | liuren-calculator.ts 中九宗门规则未全覆盖；四课/三传推导逻辑有缺陷 |

**排查步骤：**

1. 用经典六壬案例（如《大六壬指南》中的课例）进行验证
2. 逐一检查九宗门（贼克、比用、涉害、遥克、昴星、别责、八专、伏吟、返吟）的取法
3. 确认四课的天地盘关系计算是否正确

**解决方案：**

- 补全 `liuren-calculator.ts` 中缺失的九宗门规则
- 增加经典课例的回归测试
- 建立六壬排盘与人工排盘的对比验证机制

### 2.4 神煞计算错误

| 项目 | 内容 |
|------|------|
| **症状** | 神煞列表与手动查表结果不一致，部分神煞缺失或多余 |
| **影响范围** | 八字解读中的神煞分析 |
| **常见原因** | shensha.json 五层体系数据不完整；神煞查法规则实现有误 |

**排查步骤：**

1. 检查 `shensha.json` 五层体系（年干、年支、日干、日支、月支）的完整性
2. 用已知八字案例验证各神煞的计算结果
3. 确认神煞查法是否遵循传统规则（如天乙贵人的查法分歧）

**解决方案：**

- 补全 `shensha.json` 中缺失的神煞定义
- 对有争议的神煞查法，标注流派来源
- 增加神煞计算的单元测试覆盖

## 3. 前端问题

### 3.1 首页弹窗事故（git restore 导致代码丢失）

| 项目 | 内容 |
|------|------|
| **症状** | 执行 `git restore` 后，用户当天 17:30 之后的所有未提交代码修改被丢弃 |
| **影响范围** | HomePage.tsx、InfoPage.tsx 等核心页面 |
| **常见原因** | 未备份即执行不可逆 git 操作；AI Agent 未检查 git status |

**排查步骤：**

1. 检查 `git reflog` 是否有可恢复的提交
2. 检查编辑器本地历史（VS Code Local History）
3. 确认丢失文件列表和影响范围

**解决方案：**

- **必须先备份再操作**：执行任何不可逆 git 命令前，先 `git stash` 或创建备份分支
- AI Agent 执行 git 操作前必须先检查 `git status`
- 详见 [首页弹窗修改事故复盘](./首页弹窗修改事故复盘.md)

### 3.2 动画性能问题（Three.js 粒子系统）

| 项目 | 内容 |
|------|------|
| **症状** | 首页星空/粒子动画卡顿，帧率低于 30fps |
| **影响范围** | 首页视觉体验、低端设备兼容性 |
| **常见原因** | 粒子数量过多；GPU 渲染瓶颈；未使用 InstancedMesh |

**排查步骤：**

1. 打开 Chrome DevTools → Performance 面板，录制动画帧率
2. 检查 GPU 使用率（`about:gpu` 或系统监视器）
3. 确认粒子数量和渲染方式

**解决方案：**

- 降低粒子数量（移动端 ≤ 500，桌面端 ≤ 2000）
- 使用 `InstancedMesh` 替代独立 Mesh
- 启用 `requestAnimationFrame` 节流
- 移动端降级为 CSS 动画

### 3.3 国际化翻译缺失

| 项目 | 内容 |
|------|------|
| **症状** | 页面显示翻译 key 而非实际文本（如 `home.title` 而非"首页"） |
| **影响范围** | 多语言页面 |
| **常见原因** | locales 目录中缺少对应语言的翻译文件；新增文案未同步到所有语言 |

**排查步骤：**

1. 检查 `locales/` 目录下各语言 JSON 文件的完整性
2. 对比中文（基准语言）与其他语言的 key 集合
3. 搜索代码中硬编码的文案

**解决方案：**

- 补全缺失的翻译 key
- 建立 i18n key 同步检查脚本（CI 集成）
- 禁止代码中硬编码文案，统一走 i18n

## 4. 部署问题

### 4.1 PM2 进程崩溃

| 项目 | 内容 |
|------|------|
| **症状** | PM2 管理的 Node.js 进程状态变为 `errored` 或 `stopped` |
| **影响范围** | 后端 API 服务不可用 |
| **常见原因** | 内存溢出（OOM）；未捕获的异常；依赖缺失 |

**排查步骤：**

1. 查看进程状态：`pm2 list`
2. 查看错误日志：`pm2 logs --err --lines 200`
3. 检查内存使用：`pm2 monit`
4. 检查系统内存：`free -h`

**解决方案：**

- OOM：增加 `--max-memory-restart` 参数，或优化内存使用
- 未捕获异常：添加 `process.on('uncaughtException')` 全局兜底
- 依赖缺失：确认 `node_modules` 完整性，重新 `npm ci`

### 4.2 Nginx 配置错误

| 项目 | 内容 |
|------|------|
| **症状** | 页面 502 Bad Gateway 或 404；API 请求无法到达后端 |
| **影响范围** | 所有通过 Nginx 代理的请求 |
| **常见原因** | 反向代理规则配置错误；upstream 地址不匹配；SSL 证书问题 |

**排查步骤：**

1. 检查 Nginx 配置语法：`nginx -t`
2. 查看 Nginx 错误日志：`tail -f /var/log/nginx/error.log`
3. 确认 upstream 地址与后端服务端口一致
4. 检查 SSL 证书是否过期

**解决方案：**

- 修正 `proxy_pass` 地址指向正确的后端端口
- 确保 `location` 规则优先级正确（API 路由优先于静态资源）
- 更新 SSL 证书（使用 certbot 自动续期）

### 4.3 数据库连接失败

| 项目 | 内容 |
|------|------|
| **症状** | API 返回 500 错误，日志显示数据库连接超时或拒绝 |
| **影响范围** | 所有需要数据库读写的功能 |
| **常见原因** | Prisma 配置错误；SQLite/PG 切换不当；连接池耗尽 |

**排查步骤：**

1. 检查 `.env` 中 `DATABASE_URL` 配置是否正确
2. 确认 Prisma schema 中的 provider 与实际数据库一致
3. 测试数据库连接：`npx prisma db push --preview-feature` 或直接连接测试
4. 检查连接池状态（PostgreSQL：`pg_stat_activity`）

**解决方案：**

- 修正 `DATABASE_URL` 格式（SQLite vs PostgreSQL 语法不同）
- 确认 Prisma schema 的 `provider` 与 `DATABASE_URL` 匹配
- 调整连接池大小（`connection_limit` 参数）
- SQLite 场景：确认文件路径和读写权限
