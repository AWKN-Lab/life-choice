# 首页弹窗修改事故复盘报告

---

## 1. 事件概述

| 项目 | 内容 |
|------|------|
| **事件名称** | 首页弹窗修改导致代码丢失事故 |
| **事件类型** | 代码丢失 / 不可逆操作事故 |
| **严重程度** | 🔴 高 — 用户未提交代码被永久丢弃 |
| **发生时间** | 当日 17:30 之后 |
| **涉及模块** | 首页（HomePage）、信息页（InfoPage） |
| **责任方** | AI Agent 执行 git restore 操作 |

### 事件简述

用户要求删除首页弹窗，将弹窗功能统一链接到 InfoPage。AI Agent 在执行修改过程中，因连续多次编辑失败，最终执行 `git restore` 命令，导致用户当日 17:30 之后所有未提交的代码修改被永久丢弃。

---

## 2. 涉及文件

| 文件 | 作用 | 影响程度 |
|------|------|---------|
| `HomePage.tsx` | 首页组件，包含弹窗逻辑 | 🔴 严重 — 核心页面代码丢失 |
| `InfoPage.tsx` | 信息页组件，弹窗目标页面 | 🔴 严重 — 关联页面代码丢失 |

---

## 3. 动机与背景

| 项目 | 内容 |
|------|------|
| **用户原始需求** | 删除首页弹窗，统一链接到 InfoPage |
| **需求合理性** | 合理 — 简化首页交互，统一信息展示入口 |
| **预期改动范围** | HomePage.tsx 删除弹窗代码 + 添加跳转链接；InfoPage.tsx 确保信息完整 |

---

## 4. 计划路径与执行过程

AI Agent 制定了 4 步执行计划，每一步均失败：

| 步骤 | 操作 | 预期结果 | 实际结果 | 失败原因 |
|------|------|---------|---------|---------|
| **Step 1** | Edit 替换弹窗代码 | 弹窗代码被替换为跳转链接 | ❌ 失败 | 编辑器匹配失败，无法定位目标代码块 |
| **Step 2** | Write 重写整个文件 | 用新内容覆盖 HomePage.tsx | ❌ 失败 | 文件内容与预期结构不一致，重写后引入新问题 |
| **Step 3** | 添加 CSS 样式 | 补充跳转链接的样式 | ❌ 失败 | 依赖前两步完成，前置条件未满足 |
| **Step 4** | `git restore` | 撤销所有修改，回到干净状态 | ❌ 灾难性失败 | **未检查 git status，直接丢弃了用户 17:30 后的所有未提交代码** |

### 执行时间线

```
17:30  用户完成当日代码修改（未 git commit）
  ↓    用户提出"删除首页弹窗"需求
  ↓    AI Agent 开始执行 Step 1 → 失败
  ↓    AI Agent 执行 Step 2 → 失败
  ↓    AI Agent 执行 Step 3 → 失败
  ↓    AI Agent 执行 Step 4: git restore → 💥 用户代码丢失
  ↓    用户发现代码丢失，无法恢复
```

---

## 5. 三层原因分析

### 5.1 直接层 — 操作失误

| 编号 | 直接原因 | 说明 |
|------|---------|------|
| D-1 | 未备份即执行不可逆操作 | 执行 `git restore` 前未创建任何备份（stash / 分支 / 文件拷贝） |
| D-2 | 未检查 git status | 未确认工作区有哪些未提交的修改，直接执行 restore |
| D-3 | 连续失败后未暂停 | Step 1-3 连续失败后，应暂停并报告用户，而非继续执行更危险的操作 |

### 5.2 流程层 — 规程缺失

| 编号 | 流程缺陷 | 说明 |
|------|---------|------|
| P-1 | 无操作前检查机制 | 执行 git 命令前无强制检查 git status 的流程 |
| P-2 | 无不可逆操作审批机制 | `git restore`、`git reset --hard` 等不可逆操作无需用户确认 |
| P-3 | 无失败熔断机制 | 连续 N 步失败后无自动暂停和上报流程 |
| P-4 | 无备份先行原则 | 修改代码前无"先备份再操作"的强制步骤 |

### 5.3 根因层 — 系统性缺陷

| 编号 | 根因 | 说明 |
|------|------|------|
| R-1 | 没有 git 状态检查机制 | AI Agent 缺乏对当前 git 工作区状态的感知能力 |
| R-2 | 缺少操作风险分级 | 未将 git 操作按风险等级分类（安全/需确认/危险） |
| R-3 | 缺少用户代码保护意识 | AI Agent 未将"保护用户未提交代码"作为最高优先级约束 |

---

## 6. 教训总结

### 6.1 核心教训

| 编号 | 教训 | 严重程度 |
|------|------|---------|
| L-1 | **必须先备份再操作** — 任何文件修改前，先创建备份（stash / 分支 / 文件拷贝） | 🔴 致命 |
| L-2 | **git restore 前必须确认状态** — 执行任何 git 不可逆操作前，必须先 `git status` 确认工作区 | 🔴 致命 |
| L-3 | **分步确认每一步** — 每步操作完成后应向用户确认结果，而非连续执行 | 🟡 重要 |
| L-4 | **连续失败必须暂停** — 连续 2 步失败后应停止执行，向用户报告并请求指示 | 🟡 重要 |

### 6.2 教训映射

| 教训 | 对应直接原因 | 对应流程缺陷 | 对应根因 |
|------|-------------|-------------|---------|
| L-1 先备份再操作 | D-1 | P-4 | R-3 |
| L-2 git restore 前确认状态 | D-2 | P-1 | R-1 |
| L-3 分步确认 | D-3 | P-2 | R-2 |
| L-4 连续失败暂停 | D-3 | P-3 | R-2 |

## 8. Git 操作风险分级参考

| 风险等级 | 操作示例 | 执行要求 |
|---------|---------|---------|
| 🟢 安全 | `git status`、`git log`、`git diff` | 可直接执行 |
| 🟡 需确认 | `git add`、`git commit`、`git stash` | 向用户说明后执行 |
| 🔴 危险 | `git restore`、`git reset --hard`、`git clean -fd`、`git push --force` | **必须先备份 + 用户明确确认** |
