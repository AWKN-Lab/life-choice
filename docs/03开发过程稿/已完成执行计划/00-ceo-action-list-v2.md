## R 段：红线强授权（Red line · R1-R9）

### R1-R3 基础红线（不可绕开）

| # | 操作类型 | 不可绕开原因 |
|---|---------|--------------|
| **R1** | 删除文件/目录/git 历史（`rm -rf` / `git reset --hard` / `git push -f`） | 数据不可逆丢失 |
| **R2** | 修改 .env / 密钥 / token / CI/CD 配置 | 安全/认证事故 |
| **R3** | 数据库 schema 变更 / 数据迁移（Prisma migrate / SQLite→PG / 回填） | 数据损坏/丢失 |

### R4 收窄版（v2 改动）

> ✅ 采纳：原 v1"git push 每次都问"过于宽泛，日常开发会被拖慢

| # | 操作类型 | 审批规则 |
|---|---------|----------|
| **R4** | **只针对**：`git push --force` / `git push 到 main/master 分支` | **必须**先问 CEO |
| — | 普通 `git push` 到 feature branch | **不需要**问 CEO（日常开发自决） |

### R5-R7 基础红线

| # | 操作类型 | 不可绕开原因 |
|---|---------|--------------|
| **R5** | 安装新的全局依赖 / 修改系统配置（`npm install -g`） | 环境漂移 |
| **R6** | 公开发布（npm publish / 部署生产 / 发文章） | 品牌不可逆影响 |
| **R7** | 外部合作签约（画师外包 L0 涉及费用 + 版权） | 资金/法律风险 |

### R8 拆 3 级（v2 改动）

> ✅ 采纳：原 v1"生产部署每次都问"过于笼统，hotfix 响应从分钟级变小时级

| 级别 | 场景 | 审批规则 | 响应时间 |
|------|------|----------|----------|
| **R8-Hotfix** | 修线上 bug | 事后 30 分钟内报备 | 分钟级（线上 bug 不等审批） |
| **R8-常规发版** | 计划内功能发布 | 提前 1 天审批 | 24h |
| **R8-大版本** | 架构变更 / 灰度放量 | 提前 3 天审批 **+ 回滚 SOP 演练** | 72h |

### R9 新增：紧急停服授权（v2 新增）

> ✅ 采纳：原 v1 缺应急通道。当 L3 高风险拦截漏拦（医疗/法律/金融/生命类），需要"谁有权停服"的明确授权

| # | 触发条件 | 执行权 | 事后动作 |
|---|---------|--------|----------|
| **R9** | L3 高风险拦截漏拦 / 出现 P0 级故障 / 度量表"任何 1 例医疗漏拦" | **后端 Lead 可单方面执行**（无需 CEO 审批） | 30 分钟内向 CEO 报告 + 1 小时内出事故复盘 |

> **停服不需要走 R8 流程**——R9 是 R8 的紧急豁免通道。
