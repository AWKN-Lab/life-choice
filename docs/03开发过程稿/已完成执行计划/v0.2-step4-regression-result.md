## D. 关键发现

### 1. 红线硬约束是 v0.2 最大成功
v2.4 时 11 条 case 中仅 gc-001 命中 1 条 expectedRedLine（"不共同贷款"），其他 10 条红线命中 0/2 ~ 0/3。
v0.2 后 6 次输出全部红线以"不"开头，且 gc-001 deepseek 命中 1/3 expectedRedLine（"不共同贷款"）。

**含义**：prompt 硬约束对 LLM 红线表达方式有强约束力，【硬约束】标记是有效的 prompt 工程手段。

### 2. 风险等级判定增强对 deepseek 有效，对 minimax 弱
- deepseek-direct：2/3 匹配预期（gc-001/005 输出 high）
- minimax：0/3 匹配（gc-001/005 仍 medium，gc-011 过度到 high）

**根因假设**：
- deepseek-v4-flash 对【强制规则】标记敏感，遵循度高
- minimax MiniMax-M2.7 对【强制规则】标记不敏感，仍倾向保守
- minimax gc-011 输出 high 是过度反应（看到"不得保守降级"后反向过度）

**v0.3+ 改进方向**：接入 `enforceRiskLevel` 到主链，用规则强制覆盖 LLM 输出（规则 > LLM 自评）

### 3. 反集中约束产生反作用
【反集中约束】"禁止集中在 55/65/70"导致 LLM 集体趋同到 58/68：
- minimax：58/58/68
- deepseek：58/58/68

**根因**：LLM 看到"禁止 55/65/70"后，选择最接近的"具体到个位数"分值（58/68），形成新的集中。

**v0.3+ 改进方向**：去掉【反集中约束】，改为"必须说明分值与基准 61 的差异原因（如'比基准低 3 分，因为 XXX 信号比案例更严重'）"，让 LLM 基于命理信号给分而非基于"避开特定数字"。

### 4. score-engine enforceRiskLevel 函数已就绪但未接入主链
函数已实现并编译通过，但主链（orchestrator/generation-composer）未调用。

**v0.3+ 改进方向**：在 generation-composer 输出后，调用 `enforceRiskLevel(jiShenSignals)` 覆盖 LLM 输出的 riskLevel。
