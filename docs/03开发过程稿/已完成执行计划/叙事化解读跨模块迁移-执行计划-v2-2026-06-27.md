## v1 批判性分析摘要

v1 计划被判定为"不可开工"。12 个问题中，3 个致命：

| # | 严重度 | 问题 | 根因 |
|---|--------|------|------|
| 1 | 致命 | 解决的不是根本问题 | 对标分析发现最大差距是输入层（缺双方八字），但 v1 只修 prompt 层 |
| 2 | 致命 | 方法论来自单样本过拟合 | 6 条规则从 1 个案例.docx 抽象，未经验证假设适用于所有模块 |
| 3 | 致命 | 测试数据创建在 prompt 升级之后 | 自我实现预言：知道 prompt 约束再写 case，无法证明 prompt 升级有效 |

4 个严重问题：无 A/B 对照组 / token 预算未评估 / 核心指标无法自动化 / 缺少中间检查点。

**用户关键洞察**：案例.docx 是多轮交互产物（用户补充信息 → AI 修正），不是单次 prompt 输出。当前 golden case 全部是单轮。**v2 必须把"单轮 vs 多轮"作为第一变量。**

## A. 目标与边界

- **目标一句话**：验证"单轮 LLM 能否达到案例.docx 多轮交互的叙事水准"，找到最小可行架构，并迁移到全部模块。
- **本轮做（5 项）**：
  1. 创建"多轮交互"标杆 case（gc-012 合婚场景，模拟案例.docx 的用户→AI→用户补充→AI 修正流程）
  2. 跑基线对比：单轮 old prompt vs 多轮 old prompt vs 案例.docx（回答"单轮本身差多少"）
  3. 补齐 4 个模块的单轮标杆 case（财运/健康/子女/合作，先建 case 再改 prompt，盲测）
  4. 升级 prompt-layers（基于基线对比的差距，只加"有证据支持"的约束，不加"假设有效"的约束）
  5. 跨模块回归验证 + A/B 对比（旧 prompt vs 新 prompt，同 case 跑两遍）
- **本轮不做（7 项）**：
  1. 不改造为多轮交互架构（先验证单轮能否达到，再决定要不要改架构）
  2. 不接入 fine-tune 或 RLHF（先验证 prompt 工程能做到什么程度）
  3. 不改 score-engine 打分规则
  4. 不改 calc-engine 排盘逻辑
  5. 不接入新 LLM provider（用现有 minimax + deepseek-direct）
  6. 不在 prompt 中加入 few-shot example（先验证硬约束有效，再考虑 few-shot）
  7. 不把"叙事化解读"作为可自动化指标（本轮用人工验收）
- **约束与假设（10 项）**：
  1. 不破坏现有主链（generation-composer + orchestrator）
  2. 每步必须可独立 git commit + 回滚
  3. **先建 case，再改 prompt**（盲测顺序，防止自我实现预言）
  4. 跨模块 case 必须有真实命理信号（不能编造八字）
  5. 弱 LLM 环境：minimax + deepseek-direct
  6. 每模块至少 2 条 case（覆盖正反两面）
  7. 验收用"案例水准语义判定"（v2.1 标准），**人工阅读验收**（本轮不自动化）
  8. LLM 调用成本控制 ≤40 次（含 A/B 对比 + 多轮实验）
  9. token 预算：升级后 prompt ≤3500 字符，max_tokens 保持 2000（若不够，升到 3000 作为 Plan B）
  10. **停机条件**：prompt 升级 2 轮后若 gc-001 叙事化仍无改善，停止 prompt 方向，承认"单轮弱 LLM 叙事化需要架构级改造（多轮/微调/更强 LLM）"

---

## B. 选定拆解视角

- **刀法选择**：按数据流（输入 → 处理 → 输出 → 对比）
- **为什么选它**：
  1. 核心问题是"输入信息量（单命 vs 双命）→ 处理方式（单轮 vs 多轮）→ 输出质量（叙事化程度）"的因果链
  2. 按数据流视角能清晰回答：是输入不够？还是处理不够？还是两者都不够？
  3. v1 的"模块边界"视角忽略了"输入→输出"的因果验证，导致 prompt 和 case 的顺序颠倒

---

## C. 最小闭环（MVP-0）

- **MVP-0 定义**：创建 1 条多轮合婚 case（gc-012）+ 用现有 prompt 跑单轮版 + 手动跑多轮版（分两轮调用），对比三个版本：单轮 LLM / 多轮 LLM / 案例.docx
- **MVP-0 的"临时项"清单**：
  - 临时：只验证 1 条 case（gc-012 合婚，对标案例.docx 婚嫁场景）
  - 临时：多轮版手动分两轮调用（不做自动化编排）
  - 临时：只用 minimax 一个 provider
  - 临时：不升级 prompt（用现有 prompt，先测基线）
  - 移除条件：MVP-0 跑通后，明确"单轮差距"和"多轮差距"的量化数据，再决定升级方向

### L.2 停机判定

> **判定：转向（Pivot）**

**触发条件**：Step 9 A/B 对比 <6/8 条改善（实际 5/8）

**证据**：
1. E1：5/8 条有改善 < 6/8 阈值（gc-015/016/018/019/020 改善，gc-013/014 退化，gc-017 持平）
2. E2：分值改善不显著（3 条改善，3 条退化，1 条持平），平均分值变化：-1.5
3. E3：叙事化翻译质量（三层翻译+具体年份+可执行动作）在旧 prompt 已达 100%，新 prompt 无增量

**不触发完全停止的原因**：
- 结构完整性从 75% 提升到 100%（P0 约束生效）
- gc-018 截断问题已修复（max_tokens 3000）
- 叙事化翻译质量在旧 prompt 下已稳定，说明 prompt 工程方向正确但已触达天花板

### L.3 核心发现

1. **叙事化翻译能力不依赖 prompt 升级**：旧 prompt 下 8/8 条已有三层翻译+具体年份+可执行动作。这说明 deepseek-v4-flash 已经具备叙事化翻译能力，不需要额外 prompt 约束。

2. **结构完整性是最大的可改善点**：max_tokens 2000→3000 解决了 gc-018 的截断问题，强制完整性约束让 gc-015 从 11 段→14 段。这两个 P0 改动是有效的。

3. **分值稳定性是当前瓶颈**：同一 case 两次跑分差可达 18 分（gc-015: 55→37），说明 LLM 打分高度不稳定。这不是 prompt 能解决的，需要 score-engine 或人工校准。

4. **双命输入是叙事化质量的关键变量**：Step 2 发现双命输入后单轮 LLM 已接近案例.docx 水准。单命输入下 LLM 无法做合婚/互冲分析，内容深度自然受限。

### L.4 转向建议

基于本轮证据，建议方向：

1. **架构改造（推荐）**：改为多轮交互（模拟案例.docx 的 用户→AI→用户补充→AI 修正 流程），让每轮 LLM 输出更聚焦、更深入
2. **score-engine 接管打分**：LLM 自评分高度不稳定，建议用 score-engine 替代 LLM 自评分，LLM 只负责叙事化解读
3. **扩展双命输入场景**：合婚/合作等模块天然需要双方八字，扩展 partnerBirthInfo 到更多模块
4. **不强求 prompt 工程**：旧 prompt 的叙事化翻译已达标，不需要进一步升级 prompt
