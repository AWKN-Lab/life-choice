# 后端包管理与 Schema 风险清单

> 日期：2026-07-11
> 范围：`apps/AWKN-LABlife/awkn-life-backend/`
> 目的：将安装、构建、资产复制、数据库结构变化从目录治理批次中隔离。

## 一、结论

当前后端存在四组高风险变化。自动审计命令：

```bash
npm run audit:backend
```

最近结果：`BLOCK=5 WARN=3 INFO=1 PASS=3`。

风险分组：

1. 三份锁文件并存并同时发生大规模变化。
2. 根构建命令取消资产复制和构建验证。
3. 资产清单删除一个必需文件声明。
4. Prisma Schema 删除模型、字段和索引。

这些变化需要独立评审和独立提交。目录治理批次禁止包含上述文件。

## 二、包管理器现状

### 文件分布

```text
apps/AWKN-LABlife/awkn-life-backend/package-lock.json
apps/AWKN-LABlife/awkn-life-backend/yarn.lock
apps/AWKN-LABlife/awkn-life-backend/apps/api-server/package-lock.json
```

### 文档口径

| 来源 | 当前口径 |
|---|---|
| `apps/AWKN-LABlife/DEPLOY.md` | 多处使用 `npm ci`、`npm install` |
| 根 `package.json` | npm scripts；未声明 `packageManager` |
| API Server `package.json` | npm scripts；未声明 `packageManager` |
| 后端 README | 出现 `pnpm install` |
| `yarn.lock` | 文件仍存在 |

### 当前风险

- 开发机可能使用 npm、pnpm、yarn 中任一种方式安装。
- 三套解析结果可能产生不同依赖树。
- 根包与 API Server 的依赖版本不完全一致。
- Prisma、BullMQ、Sentry、Winston 等版本存在差异。
- 生产部署使用 `npm ci` 时只信任对应目录的 `package-lock.json`。

### 本轮锁文件变化

| 文件 | 增加 | 删除 |
|---|---:|---:|
| API Server `package-lock.json` | 约 1212 行 | 约 13 行 |
| 后端根 `package-lock.json` | 约 1208 行 | 约 8 行 |
| 后端根 `yarn.lock` | 约 857 行 | 约 7 行 |

### 闸门

1. 确认唯一生产包管理器。
2. 确认安装目录：后端根或 `apps/api-server`。
3. 在干净工作区重新生成唯一锁文件。
4. 使用全新 `node_modules` 执行 `npm ci` 或对应命令。
5. 构建、测试、Prisma generate 全部通过。
6. 其余锁文件删除或明确标为历史文件。

当前证据支持 npm：CI、生产和 Staging 均使用 `npm ci`。推荐架构与迁移步骤见 `ADR-后端依赖安装与构建边界-20260711.md`。ADR 当前状态为 `PROPOSED`。

## 三、构建命令变化

### 原命令

```json
"build": "cd apps/api-server && npx nest build && node scripts/copy-assets.js && node scripts/verify-build.js"
```

### 当前工作区命令

```json
"build": "cd apps/api-server && npx nest build"
```

### 风险

- YAML、JSON、Prompt 和规则资产可能未复制到 `dist/`。
- 构建完成后缺少 `verify-build.js` 验证。
- 本地 TypeScript 构建可能成功，生产运行仍会缺文件。
- 当前 `DEPLOY.md` 和生产基线依赖完整构建产物。

### 闸门

1. 查明构建命令修改来源。
2. 核对 API Server 自身 `build` 命令是否已经完整执行资产复制与验证。
3. 使用空 `dist/` 目录执行生产构建。
4. 运行 `scripts/verify-build.js`。
5. 对关键 YAML、JSON 和 Prompt 做存在性检查。

## 四、资产清单变化

2. 检查文件当前真实位置。
3. 验证编译后路径。
4. 删除清单项需要对应代码删除或路径迁移证据。

## 五、Prisma Schema 变化

当前工作区删除或调整：

- `UserMemory.lastAccessedAt`
- `UserMemory.expiresAt` 索引
- `UserMemory.lastAccessedAt` 索引
- `ConsultDialogue.dialogueTurns` 关系
- `ConsultDialogueTurn` 模型
- `MemoryEmbedding` 模型

### 风险

- 已部署数据库与本地 Schema 继续分叉。
- 迁移文件可能仍引用已删除模型。
- 对话轮次独立存储和记忆向量能力失去 Schema 支撑。
- Prisma Client 重新生成后，相关服务可能编译失败。
- 生产数据表若已存在，后续迁移策略会更复杂。

### 闸门

1. 核对当前生产数据库真实表结构。
2. 搜索代码对上述字段和模型的引用。
3. 检查迁移目录和 `_ground-truth.md`。
4. 运行 `prisma validate`、`prisma generate`、后端 typecheck。
5. 形成保留、回滚、迁移三选一决策。
6. Schema 变化单独提交并附数据库回滚方案。
