# 项目治理计划 v1.0 批判性分析

> 状态：ACTIVE
> 分析日期：2026-07-12
> 分析对象：`项目治理计划-v1.0-20260712.md`
> 分析方法：批判性思维 20 维度证伪审查
> 结论：**打回（Request Changes）**——存在 4 项 P0 缺陷、7 项 P1 缺陷，需修正后方可作为生产执行依据

---

## 一、分析目的与方法

本分析不替代审核 SOP 的三结论判定，而是对治理计划本身进行"假设前序有 3 项隐藏缺陷"的主动证伪。审查范围覆盖：目标可证伪性、时间排期现实性、责任权力对等性、工具失效降级、度量可操作性、回滚物理可行性、与上游规则衔接、自我批判盲点等 20 个维度。

---

## 二、总体评价

### 2.1 优点（先肯定）

1. **治理意识成熟**：识别了"提交边界与生产边界需要集中收口"的核心问题，方向正确。
2. **证据驱动**：2.2 节实时现场表用具体数字而非主观判断，符合"证据进入结论"原则。
3. **分阶段切割**：阶段 0-4 有明确时间窗口和出口条件，符合"一批一目标"。
4. **审计工具化**：建立 `audit:*` 命令族，把人工判断交给脚本，符合"自动审计先行"。
5. **高风险独立处理**：Schema、锁文件、依赖单独成批，符合 SAFETY GATE 精神。

### 2.2 核心风险（先亮底牌）

| 风险等级 | 数量 | 一句话概括 |
|---|---:|---|
| P0 阻断 | 4 | 数据自相矛盾、工具失效无 Plan B、回滚物理不可行、批判环节缺失 |
| P1 重要 | 7 | 时间排期无 Buffer、责任自审、度量激励错位、AI 约束软执行等 |
| P2 改进 | 9 | 文档循环依赖、指标测量人未指定、知识资产保留策略缺失等 |

**判定**：当前 v1.0 不能作为生产执行依据，必须升 v1.1 并修正 P0 后方可放行。

## 三、P0 阻断缺陷（必须修复）

### P0-1｜数据自相矛盾：后端 BLOCK 数量不一致

**证据**：
- 第 21 行："当前后端存在 **5 个**硬阻断项，在清零前禁止生产发布。"
- 第 42 行（2.2 实时现场表）："后端 BLOCK | **3** | 较前一日减少 2 项"

**批判**：
- 5 与 3 之间差 2，恰好等于"较前一日减少 2 项"。这意味着第 21 行的"5"是旧基线，第 42 行的"3"是新基线。但文档同日发布（2026-07-12），不允许两个基线并存。
- 如果 3 是最新，第 21 行的"5"必须更新；如果 5 是最新，第 42 行的"3"必须更正。
- **影响**：发布冻结判据不明确。到底是 BLOCK=0 解冻，还是 BLOCK=5→0 解冻？审核人无法判定。

**修复建议**：
- 统一为最新值 3，并在第 21 行追加"（较 2026-07-11 减少 2 项）"。
- 列出 3 个 BLOCK 的具体名称（如 `B0-1 Schema 不一致`、`B0-2 构建资产清单缺失`、`B0-3 包管理边界未固化`），否则"清零"无法验收。

---

### P0-2｜工具失效无 Plan B，阶段 0 验收依赖坏工具

**证据**：
- 第 45 行："`audit:changes` 与 `audit:batches` 在空暂存区场景出现空对象错误。"
- 阶段 0 验收（第 178-186 行）："`audit:changes` 正常运行"、"`audit:batches -Strict` 返回 0"。
- 第 59 行："工具恢复前，禁止依据旧批次数字直接执行批量暂存。"

**批判**：
- 阶段 0 既要修复工具，又依赖工具验收。如果修复失败，阶段 0 无法 PASS，后续阶段 1-4 全部阻塞。
- 文档没有给出"修复失败怎么办"的降级路径：是延期？是用人工审计替代？是用其他脚本兜底？
- 更严重：第 59 行禁止"依据旧批次数字直接执行批量暂存"，但工具坏了就意味着**没有任何可信的批次视图**。此时第 21 行"治理期间允许继续开发"就变成了"在没有批次视图的情况下允许开发"——直接违反"一批一目标"原则。

**修复建议**：
- 在阶段 0 增加 Plan B："若 2026-07-12 18:00 前工具未修复，启用人工批次清单（Git status + 文件分类表），由项目负责人签字确认每批次边界，工具修复后回填审计。"
- 增加 Plan C："若 2026-07-13 仍无法修复，暂停所有开发提交，仅允许阶段 0 工具修复本身推进。"

---

### P0-3｜回滚物理不可行：未强制批次开始前创建回滚点

**证据**：
- 第 96 行（原则 5）："全程可回滚：涉及删除、移动、数据库和部署的动作必须先写恢复路径。"
- 第 425-430 行（批次执行标准）：要求填写"回滚方式"，但**不要求填写"回滚点 commit hash"**。
- 项目 Memory（2026-07-09）："前端无回滚备份副本"、"后端有 2 个回滚备份而非 1 个"——历史已发生过回滚点缺失。

**批判**：
- "回滚方式"是描述性字段（如"git revert + 数据库 restore"），但不强制要求"批次开始前必须 git commit/tag 作为基线"。如果批次进行中产生多次提交，回滚到哪个点？
- 第 469-477 行禁止 `git reset --hard` 作用于整个工作区，但没有提供替代的"批次级回滚标准动作"。
- 数据库回滚要求"记录回滚 SQL"（第 315 行），但没要求"迁移前必须创建数据库快照"。SQL 回滚在 Schema 变更（如 DROP COLUMN）时不可靠。

**修复建议**：
- 批次执行标准增加强制字段："批次开始前回滚点 commit hash：____（必填，未提交则禁止开始批次）"。
- 数据库批次增加强制动作："迁移前必须 `pg_dump` 或等效快照，快照路径记录在批次单。"
- 引入"批次级 git tag"：每个批次开始前 `git tag batch/<id>-start`，结束时 `git tag batch/<id>-end`。

---

### P0-4｜批判性审查环节缺失，违反 RULE CRITIQUE-BEFORE-COMPLETE

**证据**：
- 用户规则 RULE CRITIQUE-BEFORE-COMPLETE："闭环交付前必须经过批判性审查环节（假设前序有 3 项隐藏缺陷主动证伪），不依赖用户主动追问；执行者不自我宣告闭环完成，闭环宣告权与执行权分离。"
- 本治理计划 v1.0 是闭环交付物（第 704-717 行"治理完成标准"是验收点），但：
  - 文档中没有"批判性审查"章节。
  - 没有"假设前序有 3 项隐藏缺陷"的证伪记录。
  - "治理完成标准"由治理计划自身定义、自身验收——执行权与宣告权未分离。

**批判**：
- 这份治理计划本身违反了它要求项目遵守的规则。
- 如果治理计划自身未经批判性审查就发布为 ACTIVE，那么它治理项目的资格存疑。
- 本分析即是对该缺陷的事后补救，但应在 v1.1 中将"批判性审查"作为治理计划发布的强制前置环节。

**修复建议**：
- v1.1 发布前必须由"非治理计划作者"执行批判性审查并出具审查单。
- 治理计划新增第十八章"批判性审查记录"，每次升版本必须附带审查单编号。
- "治理完成标准"第 717 行"项目进入常态运行"的宣告权，必须由独立审核人行使，不得由项目负责人自宣。

## 四、P1 重要缺陷（原则性修复）

### P1-1｜时间排期过于乐观，无 Buffer

**证据**：
| 阶段 | 时间窗口 | 工作量 | 风险 |
|---|---|---|---|
| 阶段 0 | 7-12（1 天） | 修复工具+回归+新基线+核对 49 项+记录 HEAD | 1 天完成 9 动作+9 验收，几乎不可能 |
| 阶段 2 | 7-15—7-19（5 天） | 向量检索 v3+经营看板+前端错误采集+统一前台联动+文档 | 4 大功能+文档，5 天 |
| 阶段 3 | 7-18—7-23（6 天） | Schema+构建资产+包管理，含生产副本验证 | 6 天含生产迁移演练 |

**批判**：
- 阶段 0 的 1 天工作量被严重低估。修复空暂存区 bug + 回归测试 + 生成新基线 + 核对 49 个删除状态，即使顺利也需要 2-3 天。
- 阶段 2 和阶段 3 时间重叠（7-18、7-19），但阶段 3 要求"生产发布继续冻结"，阶段 2 的 P1/P2 完成后如何发布？如果阶段 2 代码不能发布，就只是"代码完成"而非"功能交付"。
- 没有任何 Buffer。软件开发中 30% Buffer 是常识，这份计划 0 Buffer。

**修复建议**：
- 阶段 0 延长至 7-12—7-14（3 天），与阶段 1 并行。
- 阶段 2 延长至 7-15—7-21（7 天），阶段 3 调整为 7-20—7-26。
- 集中治理周期从 7-26 延至 7-31。
- 或：明确"代码完成 ≠ 功能交付"，阶段 2 只交付代码，发布等阶段 3 解冻后统一进行。

---

### P1-2｜责任与权力未对等，自审风险

**证据**：
- 第 118 行："同一人可以承担多个角色。角色责任仍需分别执行，避免开发结果直接替代质量结论。"
- 责任表：项目负责人=最终决策；工程负责人=工程实现+后端边界+工程事实；质量审核人=质量取证。

**批判**：
- "同一人多角色"在小团队是现实，但"角色责任仍需分别执行"是软约束。如果一个人同时是工程负责人和质量审核人，他审自己的代码，违反"执行权与宣告权分离"。
- 没有机制保障"分别执行"：没有要求"质量审核人必须非工程负责人"。
- 项目 Memory 显示用户"可委托决策权"，但委托后由谁行使宣告权未定义。

**修复建议**：
- 增加"角色互斥规则"：质量审核人与工程负责人不得为同一人；若团队仅 1 人，则引入外部审核人或 AI 审核代理。
- 批次执行标准的"审核人"字段增加约束："审核人 ≠ 负责人"。

---

### P1-3｜度量激励错位

**证据**：
- 第 668 行："单活动批次变更 ≤25"（绿灯）、"26-50"（黄灯）、">50"（红灯）。
- 第 667 行："待人工归类 = 0"（绿灯）。

**批判**：
- "≤25"阈值无依据。如果一个功能天然涉及 30 个文件（如统一前台联动涉及前端+后端+类型+测试+i18n），会被强制拆成两个批次，但拆分本身可能破坏功能完整性。
- "待人工归类=0"激励"把所有变更都归到某个批次"以达标，而不是真正核验。归到批次 ≠ 已核验。
- "混合目标提交=0"同理：判定"混合"的标准未定义，执行者可以宣称"我的提交都是单一目标"以达标。

**修复建议**：
- 阈值改为"功能完整性优先，批次大小次之"：若功能无法拆分，允许 ≤40，但必须附"不可拆分证明"。
- "待人工归类"改为"待核验变更"，增加"已归入批次但未核验"的中间态。
- "混合目标提交"定义判定规则：同一 commit message 出现 ≥2 个动词（如"完成+修复"）即判定为混合。

---

### P1-4｜AI 协作治理为软约束

**证据**：
- 第 604-611 行：AI 开始修改前必须输出 5 项。
- 第 613-618 行：AI 完成修改后必须输出 5 项。
- 第 620 行："禁止 AI 自行执行全仓重置、全仓格式化、生产数据库迁移和高风险物理删除。"

**批判**：
- "必须输出"但没有"不输出就禁止继续"的机制。AI 可以跳过输出直接修改。
- "禁止 AI 自行执行"是声明性约束，但 AI 执行 git 命令的权限边界未定义。谁能物理阻止 AI 执行 `git reset --hard`？
- 项目 Memory 显示用户偏好"24 小时连续执行、10 分钟自验证、无需逐步 boss 审批"，这与"AI 输出 5 项才能开始"存在张力——如果 AI 不输出，是否有 hook 拦截？

**修复建议**：
- 增加"AI 准入 hook"：AI 修改文件前必须先写入 `.trae/batch-context.json`（含批次编号、目标文件、禁止范围），hook 检测该文件存在且字段完整才允许 Edit/Write。
- 高风险命令（reset、checkout、db push）必须人工授权，工具层面强制 `requires_approval: true`。
- AI 完成修改后未输出 5 项结论，禁止进入下一批次（由审核人判定）。

### P1-5｜发布闸门依赖坏工具

**证据**：
- 第 550-557 行（发布前闸门）：
  ```bash
  npm run audit:batches
  npm run audit:backend
  ```
- 第 45 行：`audit:batches` 当前损坏。

**批判**：
- 发布闸门包含 `audit:batches`，但该工具在阶段 0 才修复。如果阶段 0 未完成，发布闸门无法运行。
- 阶段 3 要求"生产发布继续冻结"，但如果阶段 2 的 P1/P2 代码完成后需要灰度发布怎么办？
- 没有定义"工具损坏时的发布闸门降级方案"。

**修复建议**：
- 发布闸门增加降级路径："若 `audit:batches` 不可用，启用人工批次清单审核（项目负责人签字）+ `audit:backend` 双重确认。"
- 定义"灰度发布"与"全量发布"的闸门差异：灰度可降级，全量必须全闸门通过。

### P1-6｜回滚触发条件不可量化

**证据**：
- 第 581-588 行（回滚触发）："新版本错误率超过发布前基线"。

**批判**：
- "超过"是 0.1% 还是 1%？没有阈值。
- "核心接口不可用"——不可用持续多久？1 秒还是 1 分钟？
- "用户咨询记录无法落库"——是偶发还是持续？
- 这些模糊表述会导致回滚决策滞后。

**修复建议**：
- 错误率阈值：>发布前基线 ×1.5（如基线 2%，新版本 >3% 即触发）。
- 不可用持续时间：核心接口连续失败 ≥3 次（每次间隔 10s）即触发。
- 落库失败：连续 ≥5 条咨询记录落库失败即触发。
- 增加"自动回滚"与"人工回滚"分级：错误率 ×2 自动回滚，×1.5 人工评估。

---

### P1-7｜与项目 Memory 脱节

**证据**：
- 项目 Memory（2026-07-09）："disk space at 90% (3.9G remaining), needing to be freed to over 6G before official release."
- 项目 Memory："前端无回滚备份副本"、"后端有 2 个回滚备份而非 1 个"。
- 本治理计划：未提及磁盘空间作为治理指标，未显式要求"前端回滚备份"。

**批判**：
- 治理计划应该是项目现状的反映，但它忽略了 Memory 中已记录的硬约束。
- 磁盘 90% 是发布阻断项，但治理指标（第十五章）没有"磁盘可用空间"。
- 前端回滚备份缺失是历史教训，但批次执行标准没有"前端构建产物必须保留 prev 版本"。

**修复建议**：
- 治理指标增加"磁盘可用空间 ≥6G"（红灯：<4G；黄灯：4-6G；绿灯：>6G）。
- 批次执行标准增加"前端批次必须保留 dist.prev/ 用于回滚"。
- 治理计划发布前必须对照项目 Memory 最新版核验，作为阶段 0 的强制动作。

## 五、P2 改进缺陷（建议修复）

### P2-1｜文档循环依赖

第十章要求"同一主题保留一个 ACTIVE 主入口"，但本文档自身是 ACTIVE，且引用了 `项目治理计划-v1.0-20260712.md`（自身）。文档索引如何索引自身？需明确"索引文件本身不进入索引"。

### P2-2｜指标测量人未指定

第十五章红黄绿灯定义了阈值，但没说"谁每天测量"。如果是 AI，需要定义测量脚本；如果是人，需要指定角色。

### P2-3｜知识资产保留策略缺失

第十一章要求"旧版本恢复路径"，但没说保留多久。embedding 重新计算耗时，旧版本应该保留 N 个版本？存储成本谁承担？

### P2-4｜8 项未核验删除处理路径模糊

阶段 0 第 170 行："剩余 8 项逐一说明目的。"如果发现其中某些是真删除（非迁移），如何处理？是恢复还是接受删除？没有判定规则。

### P2-5｜批次大小阈值无依据

"≤25"这个数字从何而来？建议引用行业基准或历史数据（如"过去 30 天平均批次 18 项，P95 为 32 项，故阈值定为 25"）。

### P2-6｜每周治理评审无失败处理

第十四章每周评审 8 项，但"评审不通过怎么办"未定义。应增加"评审不通过则下一周冻结新需求"。

### P2-7｜版本冻结点未定义

SR5 要求"冻结版本禁止口头插入变更"，但本治理计划 v1.0 没有明确"冻结点"。什么时候 v1.0 冻结？什么时候升 v1.1？治理期间产生的变更是 v1.0 修订还是 v1.1 候选？

### P2-8｜audit:moves 判定逻辑未公开

文档依赖 `audit:moves` 判定"41 项纯移动"，但脚本的判定逻辑（是按内容哈希？按路径相似度？按 git log？）未公开。如果脚本误判，"纯移动"结论不可信。

### P2-9｜AI 读取顺序与 Memory 读取顺序冲突
