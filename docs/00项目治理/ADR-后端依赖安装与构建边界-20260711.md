# ADR｜后端依赖安装与构建边界

> 编号：ADR-BACKEND-001
> 日期：2026-07-11
> 状态：**PROPOSED**
> 决策范围：npm、workspace、锁文件、CI、构建、PM2 启动

## 一、决策摘要

推荐后端采用以下结构：

1. 唯一包管理器：npm。
2. 后端根目录成为 npm workspace 根。
3. `apps/api-server` 作为唯一应用 workspace。
4. 后端根目录保留 PM2 启动器、部署脚本和 workspace 调度命令。
5. API Server 保留业务依赖、Prisma、测试和完整构建脚本。
6. 全后端只保留一份根 `package-lock.json`。
7. 删除 API Server 独立 `package-lock.json` 和根 `yarn.lock`。
8. CI、生产部署、本地开发统一从后端根目录执行 `npm ci`。
9. 根 build 通过 workspace 调用 API Server 完整 build。

目标结构：

```text
awkn-life-backend/
├── package.json                 # workspace 根、PM2 启动依赖、统一脚本
├── package-lock.json            # 唯一后端锁文件
├── ecosystem.config.js
├── scripts/
│   └── bootstrap-production.js
└── apps/
    └── api-server/
        ├── package.json         # API 业务依赖与业务脚本
        ├── prisma/
        ├── src/
        └── scripts/
```

## 二、当前问题

### 1. 安装边界分裂

当前存在三份锁文件：

```text
awkn-life-backend/package-lock.json
awkn-life-backend/apps/api-server/package-lock.json
awkn-life-backend/yarn.lock
```

### 2. 依赖版本分叉

根 package 与 API package 对同一依赖声明不同版本：

| 依赖 | 后端根 | API Server |
|---|---|---|
| `@prisma/client` | `^5.22.0` | `^5.10.0` |
| `prisma` | `^5.22.0` | `^5.10.0` |
| `@sentry/node` | `^8.0.0` | `^8.55.2` |
| `bullmq` | `^5.76.8` | `^5.78.0` |
| `winston` | `^3.11.0` | `^3.19.0` |
| `winston-daily-rotate-file` | `^4.7.1` | `^5.0.0` |

### 3. 工具口径分裂

| 场景 | 当前方式 |
|---|---|
| CI 后端测试 | API Server 目录执行 `npm ci` |
| 生产 CI 部署 | API Server 目录执行 `npm ci --production` |
| Staging 部署 | API Server 目录执行 `npm ci --production` |
| 旧部署脚本 | 后端根目录执行 `npm ci` |
| 后端 README | 使用 `pnpm install` |
| 仓库文件 | 保留 `yarn.lock` |

### 4. 启动边界分裂

PM2 从后端根目录启动：

```text
scripts/bootstrap-production.js
```

启动器依赖根目录 `dotenv`，随后运行：

```text
apps/api-server/dist/main.js
```

API Server 的业务依赖由另一份 package 声明管理。Node 模块解析可能受服务器遗留 `node_modules` 影响。

---

## 三、选择 npm workspaces 的原因

### 1. 兼容当前生产流程

现有 CI 和部署体系已经以 npm 为主，迁移成本较低。

### 2. 保留根启动器

根目录可继续承载：

- `bootstrap-production.js`
- `ecosystem.config.js`
- 部署、回滚和巡检脚本
- 根级统一命令

### 3. 保留 API Server 模块边界

API Server 继续独立维护：

- NestJS 业务依赖
- Prisma 依赖
- 单元测试
- 类型检查
- 资产复制
- 构建校验

### 4. 单一锁文件

npm workspace 生成一份根锁文件，依赖解析结果可在本地、CI 和生产复现。

### 5. 根脚本统一调度

示例：

```json
{
  "workspaces": ["apps/api-server"],
  "scripts": {
    "build": "npm run build --workspace=api-server",
    "test": "npm run test --workspace=api-server",
    "typecheck": "npm run typecheck --workspace=api-server",
    "db:generate": "npm run db:generate --workspace=api-server",
    "start:prod": "node scripts/bootstrap-production.js"
  }
}
```

## 四、依赖归属规则

### 后端根 package

只保留：

- `dotenv`
- 根启动器直接依赖的包
- workspace 调度脚本
- 根级开发工具

### API Server package

保留：

- NestJS
- Prisma
- BullMQ / Redis
- LLM SDK
- 术数算法依赖
- 日志、支付、鉴权
- 测试与 TypeScript 工具

### 重复依赖处理

同一运行时依赖只在 API Server 声明。根启动器确实直接 `require()` 的包保留在根 package。

## 五、构建边界

### API Server 完整构建

权威命令：

```bash
nest build && node scripts/copy-assets.js && node scripts/verify-build.js
```

### 后端根构建

权威命令：

```bash
npm run build --workspace=api-server
```

根目录不复制 API 构建逻辑，减少命令漂移。

### 生产产物闸门

构建完成后必须包含：

```text
dist/main.js
dist/assets-manifest.json
dist/consult/safety/scenario-rules.yaml
dist/consult/orchestrator/rules/scenario-rules.yaml
dist/consult/orchestrator/evidence-composer/knowledge-retriever/rule-knowledge-bindings.json
```

## 六、CI 与部署目标命令

### CI

工作目录改为后端根：

```bash
npm ci
npm run typecheck
npm test
npm run build
```

### 生产部署

```bash
cd /opt/awkn-life/apps/AWKN-LABlife/awkn-life-backend
npm ci --omit=dev
npm run db:generate
npm run build
pm2 reload awkn-life-backend
```

构建阶段需要 TypeScript、Nest CLI、Prisma CLI 等开发依赖。若生产服务器现场构建，则安装命令应保留 devDependencies；完成构建后再执行依赖裁剪，或改用 CI 构建产物部署。

建议中期升级为：

```text
CI 构建制品 → 校验 → 上传 → 服务器解包 → npm ci --omit=dev → PM2 reload
```

## 七、迁移步骤

### Phase 0｜冻结

1. 冻结当前三份锁文件变化。
2. 保存当前 HEAD 和依赖文件哈希。
3. 记录生产 Node/npm 版本。
4. 在独立干净分支执行迁移。

### Phase 1｜建立 workspace

1. 根 `package.json` 增加 `workspaces`。
2. 增加 `packageManager` 字段。
3. 根脚本改为 workspace 调度。
4. 根 package 仅保留启动器直接依赖。
5. API package 收口业务依赖版本。

### Phase 2｜重建锁文件

1. 删除根 `node_modules`。
2. 删除 API Server `node_modules`。
3. 删除三份旧锁文件的工作副本。
4. 在后端根执行 `npm install --package-lock-only`。
5. 执行 `npm ci` 验证全新安装。

### Phase 3｜验证

```bash
npm run typecheck
npm test
npm run build
npm run db:generate
node apps/api-server/scripts/verify-build.js
```

### Phase 4｜CI 与部署切换

1. CI 工作目录切换到后端根。
2. cache dependency path 指向根 `package-lock.json`。
3. 生产与 Staging 部署切换到后端根。
4. 后端 README 统一为 npm。
5. 删除 `yarn.lock` 和 API Server 独立 `package-lock.json`。

## 八、验收标准

- 后端仅保留一份 `package-lock.json`。
- 仓库中没有后端 `yarn.lock`、`pnpm-lock.yaml`。
- 根和 API package 均声明清晰职责。
- Prisma 与 `@prisma/client` 使用同一版本。
- 全新克隆后，根目录一次 `npm ci` 完成安装。
- 根 `npm run typecheck` 通过。
- 根 `npm test` 通过。
- 根 `npm run build` 包含资产复制和验证。
- PM2 启动器可以解析 `dotenv`。
- API Server 运行时可以解析全部业务依赖。
- CI、生产、Staging、本地文档使用同一命令口径。

---

## 九、回滚方案

迁移失败时：

1. 回到迁移前 Git commit。
2. 恢复原三份锁文件。
3. 删除重建的 `node_modules`。
4. 按原 CI 工作目录重新执行 `npm ci`。
5. 恢复原 PM2 与部署脚本。
6. 运行当前生产烟测。
