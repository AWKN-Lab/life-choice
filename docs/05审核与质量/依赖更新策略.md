# 依赖更新策略

> 适用范围：人生决策宗师仓库所有第三方依赖（npm / GitHub Actions）的自动更新与审核。
> 配置文件：`.github/dependabot.yml`
> 关联文档：`审核SOP.md`、`PR审核流程.md`、`分支保护规则.md`、`密钥管理SOP.md`。

---

## 一、目标

在「依赖不更新 = 安全债」与「盲目升级 = 引入故障」之间建立可验收的平衡：

- 定期、自动、低噪声地发现依赖新版本与安全漏洞
- 每次升级都有 CI 兜底 + 人工把关
- major 版本与安全漏洞有差异化处理节奏
- 所有动作可追溯、可回滚

---

## 二、Dependabot 运行机制

### 2.1 检查频率

- **每周一 09:00（北京时间，Asia/Shanghai）** 自动检查依赖更新。
- 4 个更新源同时触发：
  | # | 生态系统 | 目录 | commit 前缀 | 标签 | 默认审核人（占位符） |
  |---|----------|------|------------|------|---------------------|
  | 1 | npm | `/apps/AWKN-LABlife/app` | `deps(frontend)` | dependencies, frontend | frontend-lead |
  | 2 | npm | `/apps/AWKN-LABlife/awkn-life-backend` | `deps(backend)` | dependencies, backend | backend-lead |
  | 3 | npm | `/apps/AWKN-LABlife/awkn-life-backend/apps/api-server` | `deps(api-server)` | dependencies, backend | backend-lead |
  | 4 | github-actions | `/` | `deps(ci)` | dependencies, ci | — |

- 每个源 `open-pull-requests-limit: 5`，避免一次性刷屏。

### 2.2 自动创建 PR

- 发现新版本后，Dependabot **自动创建 Pull Request**。
- 所有 PR 自动打上 `dependencies` 标签（外加 frontend/backend/ci 子标签）。
- commit message 带统一前缀，便于在 git log 中检索与回滚定位。

### 2.3 占位符替换（上线前必做）

> ⚠️ 当前 `reviewers` 字段为占位符（`frontend-lead` / `backend-lead`），**需替换为仓库中真实存在的 GitHub 用户名或团队 slug**。

替换步骤：
1. 编辑 `.github/dependabot.yml`，将 `frontend-lead` / `backend-lead` 改为真实账号。
2. 同步更新本文件「2.1 检查频率」表格中的「默认审核人」列。
3. 确认 `.github/CODEOWNERS` 中对应路径的 owner 与 reviewers 一致。
4. 替换前若账号不存在，Dependabot 会忽略 reviewers 并在日志告警（PR 仍会创建）。

## 三、PR 合并门槛

依赖 PR 与普通 PR 走同一套审核流程（见 `审核SOP.md`），并额外满足：

### 3.1 必须通过

- ✅ **CI 检查全部通过**（lint / typecheck / test / build）。
- ✅ **人工审核通过**（CODEOWNERS 自动分配审核人，三结论之一：放行 / 打回 / 升级）。
- ✅ 不引入新的安全告警（ Dependabot security alert / npm audit）。

### 3.2 合并策略

- 默认使用 **Squash merge**，保持 main 历史整洁。
- 一次只合并一个依赖 PR，避免冲突叠加；冲突由 Dependabot 自动 rebase（`@dependabot rebase`）。

## 四、分级处理规则

### 4.1 Patch / Minor 版本（如 1.2.3 → 1.2.4 / 1.3.0）

- 走标准流程：CI 通过 + 1 名审核人放行即可合并。
- 建议在每周一集中批量审核，避免日常被打断。

### 4.2 Major 版本（如 1.x → 2.0.0）

- 🔴 **需额外审核**：除默认审核人外，需至少 1 名升级（Escalate）复审人确认。
- PR 标题/描述中应标注 `major`，便于筛选。
- 合并前必须：
  - 阅读 release notes / migration guide，确认 breaking change 影响。
  - 在 PR 描述中写明「已评估 breaking change，影响范围：___」。
  - 必要时先在独立分支跑全量回归测试。
- 不确定时优先「打回」或「升级」，不强行合并。

### 4.3 安全漏洞修复（Dependabot security update）

- 🔴 **优先处理，24 小时内响应**：
  - 收到 security alert 后 24 小时内必须有人认领（评论认领 + 评估）。
  - 若漏洞影响线上服务，48 小时内合并修复 PR 并发布。
  - 若为 dev 依赖或无线上影响，可在下一个工作日内合并，但需在 PR 中说明影响评估。
- 安全更新 PR 不受每周一固定时间限制，Dependabot 会在发现漏洞时立即创建。
- 严重漏洞（CVSS ≥ 9.0）触发「升级」结论，通知仓库 Owner 决策。

## 五、回滚策略

依赖 PR 合并后若引发故障：

1. **首选**：在 GitHub 上对该 PR 执行 `Revert`，生成回滚 PR。
2. 回滚 PR 走标准审核流程（紧急情况下可走 hotfix 流程，见 `审核SOP.md`）。
3. 回滚后在该依赖的下一个 Dependabot PR 中备注「上次升级回滚原因：___」，避免重复踩坑。
4. 重大回滚需在 `docs/04复盘总结/` 下补一份复盘记录。

## 六、不做清单

- ❌ 不在 dependabot.yml 中开启 `allow` 白名单过滤（保持全量发现，由审核环节把关）。
- ❌ 不开启自动合并（auto-merge），所有依赖 PR 必须人工确认。
- ❌ 不在 dependabot.yml 中硬编码密钥或 token。
- ❌ 不修改既有依赖版本（Dependabot 只负责「发现 + 提议」，不负责「决定」）。
- ❌ 不允许跳过 CI 直接合并依赖 PR。

## 七、验收清单（配置生效后）

- [ ] `.github/dependabot.yml` 已提交至默认分支。
- [ ] GitHub 仓库 Settings → Code security and analysis → Dependabot 已启用。
- [ ] `reviewers` 占位符已替换为真实账号。
- [ ] 仓库存在 `dependencies` / `frontend` / `backend` / `ci` 标签。
- [ ] 下一个周一 09:00 后，Insights → Dependency graph → Dependabot 可看到检查记录。
- [ ] 安全告警通知邮箱/渠道已配置（Settings → Code security → Alert notifications）。
