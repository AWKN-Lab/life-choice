# 审核 SOP（审核标准作业流程）

> 适用范围：人生决策宗师仓库所有 Pull Request、合并请求、上线前质量门禁。
> 来源：由 `_tmp_review_skill.md`（AWKN 审核 v4.0.0）正式化而来。
> 配套规则：`.trae/rules/review-sop.md`（Trae IDE 常驻规则）。
> 关联文档：`PR审核流程.md`、`分支保护规则.md`、`密钥管理SOP.md`。

---

## 一、目的

把审核动作变成可验收、可追溯、可回滚的标准流程，防止：

- 越权合并
- 跳过审核
- 误判完成
- 未冻结先开发
- 高风险操作导致事故

所有审核动作必须服从：**SYSTEM RULES ＞ SAFETY GATE ＞ 本 SOP**。

---

## 二、审核流程（端到端）

```
PR 创建 ──> 自动检查 (CI/lint/typecheck/test) ──> CODEOWNERS 自动分配审核人 ──> 人工审核 ──> 三结论之一 ──> 合并/打回/升级
                                                          │
                                                          ├── 放行 (Approve) ──> 合并 ──> 结果单写回
                                                          ├── 打回 (Request Changes) ──> 作者修复 ──> 重新审核
                                                          └── 升级 (Escalate) ──> CTO/Owner 复审 ──> 三结论之一
```

### 2.1 PR 创建（作者职责）

1. 在功能分支上完成开发并推送。
2. 向 `main`（或目标分支）发起 Pull Request。
3. PR 模板（`.github/pull_request_template.md`）自动填充，按模板填写：
   - 变更说明
   - 变更类型（feature/fix/refactor/docs/test/chore）
   - 测试结果（lint / typecheck / test / 手动验证）
   - 风险
   - 验收清单
4. **自检通过后再提交审核**（避免表演式审核）。
5. 如仅文档变更，PR 标题标注 `[docs-only]` 申请豁免。

### 2.2 自动检查（CI 职责）

CI 自动运行以下检查，任一失败即阻断人工审核：

- `lint`（eslint）
- `typecheck`（tsc --noEmit）
- `test`（vitest / jest）
- `build`（构建通过）
- `audit`（npm audit，无高危漏洞）

### 2.3 CODEOWNERS 自动分配

GitHub 根据 `.github/CODEOWNERS` 自动把对应模块 owner 加为审核人。详见 `PR审核流程.md`。

### 2.4 人工审核（审核人职责）

1. **24 小时内首次响应**。
2. 按本文件第三章《PR 审核清单》逐项检查。
3. 按第四章《三结论规则》给出明确结论。
4. 产出《审核结果单》（第六章）。
5. 打回时必须列出具体修复项 + 优先级。
6. 升级时必须说明升级原因 + 转交对象。

### 2.5 合并

- 仅当结论为「放行」且所有 CI 检查通过时方可合并。
- 合并方式默认 `Squash and merge`，保留清晰 commit message。
- 合并后作者删除功能分支。

## 三、PR 审核清单（必填检查项）

> 所有必填项必须 PASS 才能放行。任一 FAIL 即打回。

### 3.1 代码风格
- [ ] `npm run lint`（eslint）通过，无 error
- [ ] `npm run format`（prettier）通过，无格式差异
- [ ] 命名符合项目规范（驼峰/连字符按既有约定）

### 3.2 类型检查
- [ ] `npm run typecheck` 通过，无 TS error
- [ ] 新增类型定义完整，无 `any` 滥用（确需使用需注释说明）

### 3.3 单元测试
- [ ] 新增/修改代码有对应测试（E28 零测试门禁：零测试 = 未交付）
- [ ] `npm run test` 通过，无失败用例
- [ ] 核心 service 至少 1 条核心逻辑测试
- [ ] Zod/Yup/Joi schema 覆盖率 ≥ 90%（E24）

### 3.4 安全检查
- [ ] 无密钥/凭证硬编码（API Key、Token、密码、连接串）
- [ ] 无 SQL 注入风险（参数化查询 / ORM）
- [ ] 无 XSS 风险（`v-html`/`dangerouslySetInnerHTML` 必须经 DOMPurify 消毒）
- [ ] 权限校验完整（鉴权中间件 / 角色检查）
- [ ] AI 相关代码：prompt 注入防护 / 输出 JSON schema 验证 / 工具调用参数消毒
- [ ] 依赖无已知高危漏洞（npm audit / SBOM）

### 3.5 性能检查
- [ ] 无 N+1 查询（循环内禁止发 SQL/请求）
- [ ] 无内存泄漏（事件监听/定时器/订阅需清理）
- [ ] 无阻塞主线程的同步大计算
- [ ] 关键链路有基准对比，性能回归 ≤ 5%

### 3.6 文档更新
- [ ] API 变更同步更新接口文档
- [ ] 数据库 schema 变更同步更新数据库文档
- [ ] 新增模块同步更新 REPO-MAP.md / 工程交接文档
- [ ] 行为变更同步更新用户文档（如有）

### 3.7 可维护性
- [ ] 无空 try-catch（至少 `logger.error`）
- [ ] 无硬编码数字（超时/延迟/阈值提取为命名常量）
- [ ] 无重复代码（≥3 处相同逻辑需提取）
- [ ] 函数单一职责，单文件 < 2000 行（E26）

### 3.8 端到端接线（如涉及入口/路由）
- [ ] service 函数 ↔ API 路由 ↔ AI tool 三方对齐（E27）
- [ ] 入口文件修改有集成测试（E26）
- [ ] 模块独立 PASS + 入口调用链 PASS（E25）

## 四、三结论规则（硬规则）

任何审核动作完成后，**必须且只能**给出以下三种结论之一。无结论不得流转。

### 4.1 放行（Approve）

**触发条件**：所有必填检查项 PASS，无 P0/P1 阻断项。
**后续动作**：进入合并流程。
**残余风险**：如有 P2 改进项，记录后放行，记入 backlog。

### 4.2 打回（Request Changes）

**触发条件**：任一必填项 FAIL，或存在 P0/P1 问题。
**后续动作**：退回作者，按优先级修复后重新提交。
**要求**：打回时必须列出：
- 具体问题（文件 + 行号 + 描述）
- 优先级（P0/P1/P2）
- 修复建议

### 4.3 升级（Escalate）

**触发条件**：涉及以下任一情况，超出当前审核人权限：
- 核心模块变更（auth/payment/consult/数据库 schema）
- 安全相关变更（密钥/权限/鉴权/AI prompt）
- 支付链路变更
- 隐私合规变更
- 数据库结构变更

**后续动作**：转交 CTO 或对应 Owner 复审，复审后仍需给出三结论之一。

> 禁止使用「感觉没问题」「应该可以」「看起来 OK」等模糊措辞作为结论。
> 禁止「无结论放行」——未给出明确三结论之一的，视为未完成审核。

## 五、审核优先级与时效

### 5.1 优先级分级

| 优先级 | 含义 | 处理原则 |
| --- | --- | --- |
| **P0 阻断** | 不修不能合并，影响上线/安全/数据 | 必须修复后才能放行 |
| **P1 重要** | 不修留隐患，本次必须处理 | 原则上本次修复，确需延后必须写入结果单并升版本 |
| **P2 改进** | 可在后续迭代处理 | 记入 backlog，可放行 |

### 5.2 审核时效

| 优先级 | 响应时间 | 完成时间 | 升级条件 |
| --- | --- | --- | --- |
| P0 阻断 | 30 分钟 | 2 小时 | 超时 → 拉架构师 |
| P1 严重 | 2 小时 | 8 小时 | 超时 → 升级 P0 |
| P2 一般 | 4 小时 | 24 小时 | 超时 → 升级 P1 |

**默认时效**：
- **24 小时内首次响应**
- **48 小时内完成审核**

超时未响应的 PR，作者可 @审核人提醒；超时 24 小时仍未响应，自动升级到对应 Owner。

## 六、审核豁免规则

| 豁免类型 | 豁免范围 | 必须条件 |
| --- | --- | --- |
| **docs-only** | 仅文档变更（*.md） | PR 标题标注 `[docs-only]`，可豁免 lint/typecheck/test/性能 |
| **配置变更** | 仅配置文件（.json/.yml/.env.example） | 仍需安全检查（密钥泄露）+ 文档同步 |
| **紧急修复** | 线上 P0 故障修复 | 需 CTO 口头放行，事后 24 小时内补审核 + 复盘 |

> 任何豁免必须在 PR 描述中明确标注，否则按全量检查执行。
> 豁免不等于免审——仍需审核人确认豁免适用并给出三结论之一。

## 七、审核维度（5 维度）

| 维度 | 关键检查点 |
| --- | --- |
| **功能** | 是否实现需求；核心闭环是否跑通；边界/异常/失败兜底是否覆盖 |
| **安全** | 无密钥泄露；无 SQL 注入；无 XSS；权限校验；AI prompt 注入防护；供应链安全 |
| **性能** | 无 N+1 查询；无内存泄漏；无阻塞主线程；关键链路有基准对比 |
| **可维护性** | 命名清晰；单一职责；无重复代码；关键逻辑有注释；不引入不必要的抽象 |
| **测试覆盖** | 新增/修改代码有测试；核心 service 至少 1 条测试；零测试 = 未交付（E28） |

## 八、审核结果单（强制产出）

每次审核完成必须产出结果单，未产出视为审核未完成。结果单以 PR 评论形式发布，并写回记忆系统。

```markdown

- 审核人: <姓名/GitHub ID>
- 审核时间: <YYYY-MM-DD HH:MM>
- 结论: 放行 / 打回 / 升级
- 升级对象: <如升级则填写>

### 检查项结果
- [ ] 代码风格: PASS / FAIL（详情）
- [ ] 类型检查: PASS / FAIL（详情）
- [ ] 单元测试: PASS / FAIL（详情）
- [ ] 安全检查: PASS / FAIL（详情）
- [ ] 性能检查: PASS / FAIL（详情）
- [ ] 文档更新: PASS / FAIL（详情）
- [ ] 可维护性: PASS / FAIL（详情）

### 问题清单
```

## 九、与 SAFETY GATE 的衔接

命中以下触发关键词的 PR，必须先过 SAFETY GATE 再审核：

- 删除 / 覆盖 / 重写 / restore / reset / checkout / 回退 / 外部代码替换 / 删除文件 / 重建整个文件

SAFETY GATE 要求作者先输出 5 项：
1. 修改范围
2. 风险点
3. 备份方式
4. 验证方法
5. 回滚方式

缺任一项，审核人直接打回，不进入技术审核环节。
