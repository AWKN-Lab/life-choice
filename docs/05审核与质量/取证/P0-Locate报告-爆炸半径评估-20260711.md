## 一、P0-1：UserMemory 清理暂停

### 1.1 问题位置

**文件**：`apps/api-server/src/consult/memory/memory-forget.service.ts` L98-109

**关键代码**：
```typescript
private async cleanExpired(): Promise<number> {
  const now = new Date();
  const result = await this.prisma.userMemory.deleteMany({
    where: {
      expiresAt: { lt: now },
    },
  });
  if (result.count > 0) {
    this.logger.log(`[MemoryForget] 清理过期记忆: ${result.count} 条`);
  }
  return result.count;
}
```

### 1.2 问题分析

- `UserMemory` 表使用 `userId @unique`（schema L74），每个用户**只有一条** UserMemory 记录
- 该记录聚合了：
  - 旧 4 JSON 字段：`chartHistory / consultHistory / timelineEvents / insights`
  - P2-1 扩展字段：`type / content / sourceQuote / issueId / confidence / weight / expiresAt`
- 当 `expiresAt` 过期时，`deleteMany` 会**删除整行** UserMemory
- 后果：用户的一个 P2-1 类型记忆过期 → 丢失所有历史档案（包括咨询历史、时间线、洞察）

### 1.3 修复策略

**推荐方案 A（最小改动）**：暂停 cleanExpired，改为只降权不删除
```typescript
private async cleanExpired(): Promise<number> {
  // P0-1 安全止损：不再 deleteMany，改为将过期记忆的 type/content 置空，保留历史档案
  const now = new Date();
  const result = await this.prisma.userMemory.updateMany({
    where: { expiresAt: { lt: now }, type: { not: null } },
    data: {
      type: null,
      content: null,
      sourceQuote: null,
      issueId: null,
      confidence: null,
      weight: null,
      expiresAt: null,
    },
  });
  return result.count;
}
```

**方案 B（PRD 原文"暂停"）**：直接跳过 cleanExpired
```typescript
private async cleanExpired(): Promise<number> {
  // P0-1 安全止损：暂停清理，避免删除整行 UserMemory
  this.logger.log('[MemoryForget] cleanExpired 已暂停（P0-1 安全止损）');
  return 0;
}
```

### 1.4 爆炸半径评估

| 维度 | 评估 |
|------|------|
| 影响范围 | 所有 UserMemory 表中有 expiresAt 的行 |
| 风险等级 | 🔴 高 — 可能导致用户历史档案丢失 |
| 改动半径 | 1 个方法（cleanExpired） |
| 回滚方式 | 恢复 cleanExpired 原始代码 + 重启服务（数据无法回滚，必须先备份 DB） |
| 验证方式 | 1. 在测试 DB 中创建带 expiresAt 的 UserMemory<br>2. 触发 scan()<br>3. 确认 4 JSON 字段保留 |

## 二、P0-2：Followup 认证

### 2.1 问题位置

**文件**：`apps/api-server/src/consult/followup/followup.controller.ts` L19-51

**关键代码**：
```typescript
@Controller('consult/followup')
// ❌ 无 @UseGuards(JwtAuthGuard)
export class FollowupController {
  @Post()
  async handleFollowup(@Body() dto: FollowupDto) {
    // ❌ 无 @Req() req，无 userId 提取，无所有权校验
    const result = await this.followupService.handleFollowup(
      dto.recordId, dto.question.trim(), dto.context,
    );
    return result;
  }

  @Get(':followUpId')
  async getFollowUpContext(@Param('followUpId') followUpId: string) {
    // ❌ 无 @Req() req，无 userId 提取，无所有权校验
    return this.followupService.getFollowUpContext(followUpId);
  }
}
```

### 2.2 问题分析

- Controller 整个类**未启用** `@UseGuards(JwtAuthGuard)`
- 两个接口（POST / 和 GET /:followUpId）均无认证
- 任何人知道 `recordId` 都可以发起追问（消耗 LLM tokens）
- 任何人知道 `followUpId` 都可以查询他人的 followup 上下文

### 2.3 修复策略

**Controller 修改**：
```typescript
import { UseGuards, Req, ForbiddenException } from '@nestjs/common';
import { JwtAuthGuard } from '../../auth/guards/jwt-auth.guard';

@Controller('consult/followup')
@UseGuards(JwtAuthGuard)  // ✅ 启用 Guard
export class FollowupController {
  @Post()
  async handleFollowup(@Body() dto: FollowupDto, @Req() req: any) {
    const userId = req.user?.id;  // ✅ 提取 userId
    // 所有权校验下沉到 service
    return this.followupService.handleFollowup(dto.recordId, dto.question.trim(), dto.context, userId);
  }

  @Get(':followUpId')
  async getFollowUpContext(@Param('followUpId') followUpId: string, @Req() req: any) {
    const userId = req.user?.id;
    return this.followupService.getFollowUpContext(followUpId, userId);
  }
}
```

**Service 修改**（followup.service.ts）：
- `handleFollowup(recordId, question, context, userId)` 增加 userId 参数
- 查询 record 后校验 `record.userId === userId`（或 record.userId 为该 userId 所属）
- `getFollowUpContext(followUpId, userId)` 增加 userId 参数
- 查询 followUp 后校验 `followUp.userId === userId`

|------|------|

| 风险等级 | 🟡 中 — 前端已传 JWT（client.ts L116-121），无需改动 |

## 五、P0-5：迁移验证（ConsultDialogue + MemoryEmbedding）

**文件**：`apps/api-server/prisma/schema.prisma`

**关键发现**：

### 5.2 问题分析（已修正）

`memory-embedding.service.ts` L104, L110, L119, L141, L162 都引用了 `this.prisma.memoryEmbedding`，但 schema.prisma 中找不到 `model MemoryEmbedding` 定义。

**Grep 验证结果**（2026-07-11）：
- ✅ Migration 文件存在：`prisma/migrations/20260703184000_add_memory_embedding/migration.sql`
- ✅ Migration SQL 已定义表结构（id/memoryId/userId/content/embedding/dim/createdAt + 2 索引）
- ❌ schema.prisma 中**缺失** `model MemoryEmbedding` 定义

**真实状态判定**：
1. 生产 DB **可能已有** MemoryEmbedding 表（如果 migrate deploy 执行过）
2. 但 schema.prisma 缺失 model → `npx prisma generate` 不会为该表生成 Prisma Client 方法
3. `this.prisma.memoryEmbedding` 在 TypeScript 类型层面为 undefined，运行时可能报错

**结论**：这是 schema 与 migration 不同步的问题。需要在 schema.prisma 中补全 model 定义，然后 `npx prisma generate` 重新生成 client。

### 5.3 修复策略（已修正）

**Step 1**：SSH 到服务器检查生产 DB 是否已有 MemoryEmbedding 表
```bash

ssh root@8.148.245.29 "sqlite3 /opt/awkn-life/awkn-life-backend/apps/api-server/prisma/prod.db '.schema MemoryEmbedding'"
```

**Step 2**：在本地 schema.prisma 中补全 model 定义（对齐 migration.sql 字段）
```prisma
model MemoryEmbedding {
  id        String   @id @default(uuid())
  memoryId  String
  userId    String
  content   String
  embedding String   // JSON number[]
  dim       Int      @default(256)
  createdAt DateTime @default(now())

  @@index([memoryId])
  @@index([userId])
}
```

**Step 3**：本地执行 `npx prisma generate` 验证 client 类型生成

**Step 4**：如生产 DB 无表，在服务器执行 `npx prisma db push` 同步（有则跳过）

**注意**：db push 会比较 schema 与 DB 差异，只新增缺失的表/字段，不会删除已有数据。但执行前仍需备份 DB。
