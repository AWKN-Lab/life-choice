## 三、发现的问题

### 3.1 配置错位（pre-existing，本轮未修）

**问题**：`.env` 的 `DATABASE_URL="file:./prisma/dev.db"`，但服务器有 4 个 DB 文件：

| DB 文件 | 大小 | User 数 | 说明 |
|---------|------|---------|------|
| apps/api-server/prisma/dev.db | 1.1M | 18 | **生产实际使用**（bootstrap 强制修正） |
| apps/api-server/prisma/prisma/dev.db | 2.1M | 1 | Prisma CLI 解析路径（db push 会用这个） |
| prisma/dev.db | 420K | ? | 根目录 |
| prisma/prisma/prod.db | 388K | 1 | 历史遗留（之前 P0-6 盘点查的这个） |

**bootstrap 修正逻辑**（在 error log 中发现）：
```
[bootstrap] DATABASE_URL 已强制修正: file:./prisma/prod.db → file:/opt/awkn-life/awkn-life-backend/apps/api-server/prisma/dev.db
```

**影响**：
- `prisma db push` 会 push 到错误的 DB（apps/api-server/prisma/prisma/dev.db）
- 运行时 Prisma Client 连接正确的 DB（bootstrap 修正后）
- 所以本轮用手动 sqlite3 CREATE TABLE 代替 db push

**建议**（P1 修复）：
1. 统一 .env 的 DATABASE_URL 为绝对路径
2. 清理多余的 DB 文件
3. 移除 bootstrap 的强制修正逻辑（治标不治本）

### 3.2 lastAccessedAt 字段缺失（pre-existing）

**问题**：migration `20260703183500_add_memory_last_accessed_at` 存在，但 schema.prisma 未同步字段定义

**影响**：applyDecay/archiveStale/markAccessed 方法引用不存在的字段，TS 编译报错

**本轮处理**：Option B — 三个方法改 no-op

**建议**（P1 修复）：
1. schema.prisma 补全 `lastAccessedAt DateTime?` 字段定义
2. prisma generate 同步类型
3. 恢复 applyDecay/archiveStale/markAccessed 方法逻辑

### 3.3 端口配置

- .env PORT=30001
- 实际监听端口=30000（netstat 确认）
- 可能在 main.ts 或 ecosystem.config.js 中覆盖
