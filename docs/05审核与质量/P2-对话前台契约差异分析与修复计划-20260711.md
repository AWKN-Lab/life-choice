## 1｜背景

V1 准入条件第 2 项："P2 对话前台契约对齐"

批判性审查发现 ConsultPage ↔ FrontdeskChat 之间存在 3 处契约差异。经深入代码分析，这 3 处差异的实质是 **V1→V2 架构迁移的过渡状态**，非代码 bug。

---

## 2｜架构关系分析

### 2.1 组件关系

```
ConsultPage（容器页面）
  ├── mode='naming' → 渲染 FrontdeskChat（新对话式前台）
  ├── mode='question' → 渲染 FrontdeskChat 或自有逻辑
  ├── liuren 路由 → ConsultPage 自有跳转逻辑（旧架构）
  ├── ziping 路由 → ConsultPage 自有跳转逻辑（旧架构）
  └── 其他路由 → ConsultPage 直接跳转结果页
```

### 2.2 两套架构并存

| 架构 | 入口 | 特征 | 状态 |
|------|------|------|------|
| V1 旧架构 | ConsultPage 直接跳转 | analyze→根据 routeRes 跳转 | 仍在使用（liuren/ziping） |
| V2 新架构 | FrontdeskChat 对话引导 | 对话内采集信息→analyze→更新 phase | 已实装（naming/question） |

**结论**：两者是父子关系（ConsultPage 是容器，FrontdeskChat 是子组件），非并列关系。3 处差异是迁移未完成的过渡状态。

## 3｜3 处差异详细分析

### 差异 1：响应字段处理

| 项 | 值 |
|---|---|
| 位置 | ConsultPage.tsx L132-190 / FrontdeskChat.tsx L683-745 |
| ConsultPage 行为 | 调用 `analyzeQuestion` 获得 `routeRes`，根据 `routeRes.next_step` 和 `route_type` 决定跳转 |
| FrontdeskChat 行为 | 调用 `consultApi.analyze`，在内部处理返回值并更新 `phase` 状态 |
| 实质 | **组件分工不同**：ConsultPage 是路由分发器，FrontdeskChat 是对话处理器。两者各自处理返回值是合理的 |
| 是否 bug | ❌ 不是 bug，是架构分工 |
| 修复需求 | 补契约文档说明两者分工；无需代码修改 |

### 差异 2：状态机同步

| 项 | 值 |
|---|---|
| 位置 | FrontdeskChat.tsx L179（phase 状态） |
| ConsultPage 行为 | 不与 FrontdeskChat 的 phase 交互 |
| FrontdeskChat 行为 | phase 在内部完整控制（input→clarify→submitting→preview→liuren_ask_time→ziping_profile_check） |
| 实质 | **组件封装**：phase 是 FrontdeskChat 的内部状态，不需要 ConsultPage 干预。这是正确的 React 组件设计 |
| 是否 bug | ❌ 不是 bug，是正确的组件封装 |
| 修复需求 | 无需修改；如需 ConsultPage 感知状态，通过 onPhaseChange 回调通知（增强项，非必修） |

### 差异 3：提交协议（liuren/ziping）

| 项 | 值 |
|---|---|
| 位置 | ConsultPage.tsx L102-176 / FrontdeskChat.tsx L536-595, L683-745 |
| ConsultPage 行为 | liuren→handleLiurenSubmit（保存信息→生成记录ID→跳转结果页）；ziping→handleSubmit（有档案直接跳转，无档案跳档案页） |
| FrontdeskChat 行为 | liuren→liuren_ask_time 阶段（对话内引导填时间）；ziping→ziping_profile_check 阶段（对话内引导检查档案） |
| 实质 | **V1→V2 迁移未完成**：ConsultPage 的直接跳转是旧架构，FrontdeskChat 的对话引导是新架构。两者并存导致用户流程不一致 |
| 是否 bug | ⚠️ 不是 bug，是迁移过渡状态 |
| 修复需求 | 需要代码修改：ConsultPage 的 liuren/ziping 改为走 FrontdeskChat 对话引导 |

## 4｜修复计划

### 4.1 修复策略

| 差异 | 策略 | 风险 | 优先级 |
|------|------|------|--------|
| 差异 1 | 补契约文档 | 低 | P2（文档） |
| 差异 2 | 无需修改（正确的组件封装） | 无 | 无 |
| 差异 3 | 代码修改：ConsultPage liuren/ziping 改走 FrontdeskChat | **中-高** | P1（代码） |

### 4.2 差异 3 修复方案

**目标**：ConsultPage 的 liuren/ziping 路由改为走 FrontdeskChat 对话引导，统一用户流程。

**修改文件**：
- `apps/AWKN-LABlife/app/src/pages/ConsultPage.tsx`

**修改内容**：
1. 移除 ConsultPage 中 liuren/ziping 的直接跳转逻辑（L102-176）
2. 改为渲染 FrontdeskChat 并传入 mode='question' + routeType='liuren'/'ziping'
3. FrontdeskChat 接管完整的对话流程（ask_time→analyze→结果）

**风险评估**：
- **用户流程变更**：从直接跳转→对话引导，用户需要多 1-2 步交互
- **回归风险**：现有 liuren/ziping 用户可能习惯直接跳转
- **测试需求**：需要前端测试环境验证完整流程
- **依赖**：FrontdeskChat 的 liuren_ask_time 和 ziping_profile_check 阶段必须已稳定

**回滚方式**：`git checkout -- ConsultPage.tsx`

### 4.3 执行时机

| 时机 | 条件 | 动作 |
|------|------|------|
| **现在不执行** | 无前端测试环境 + 无用户验收 + P0 未完成 | 仅产出本计划 |
| P0 完成后 | PRD-C01 P0 安全止损 8 项完成 | 启动差异 3 修复 |
