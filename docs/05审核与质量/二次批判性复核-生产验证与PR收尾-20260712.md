# 二次批判性复核：生产验证与 PR 收尾

## 一、总判断

原文抓到了一个关键问题：**本地测试通过、提交完成、文档齐全，均不能替代生产验证。**

原文随后出现了五个过度推断：

1. 把“生产尚未部署”写成“修改完全无效”。
2. 把“生产版本落后”写成“两套完全不同实现”。
3. 把“向量覆盖不足”写成“58.3% 知识用户搜不到”。
4. 把“WIP 提交混乱”扩展为“独立 commit 没有价值”。
5. 批评生产验证不足，却没有继续审查 v3 评估方法本身。

因此，这份文档适合作为**风险预警稿**，不适合作为最终决策稿。原结论需要降级为：

> 生产 knowledge-service 尚未接入 PR-C 的 v2/v3 切换能力；生产向量数据与全量语料存在版本差；PR-A、PR-B、PR-C 当前尚未形成生产效果。下一步先完成生产代码、数据、调用链的证据闭环，再决定 v2 全量补齐、v3 灰度或项目归档。

## 三、原文最重要的五个误判

## 3.1 “两套完全不同实现”缺少证据

原文依据：

- 生产 `main.py` 356 行。
- 本地 `main.py` 含 `_EMBED_VERSION`。
- 生产文件开头出现 `keyword_match`。

这组证据无法支持“完全不同实现”。

本地当前 `main.py` 同样具备以下结构：

```text
version="2026-05-v1"
loader.load_all()
keyword_match()
/retrieve
_vector_search()
/health-v2
/embed_search
/hybrid_search
```

本地 Git 历史进一步表明：

| commit | main.py 行数 | 能力 |
|---|---:|---|
| `6a9e50a7` | 317 | 关键词 + 向量 + hybrid_search |
| `13afc5e0` | 370 | 关键词 + 向量 + hybrid_search |
| `459dc113` | 394 | 关键词 + 向量 + hybrid_search |
| `7edddc72` | 424 | 增加 v2/v3 环境变量切换 |

生产 356 行很可能对应同一架构的中间版本。`/health-v2` 能返回 `vector_count`，也证明生产代码包含向量路径。

更准确的判断：

> 生产运行的是同一知识服务架构的旧版本，缺少 PR-C 的 v3 切换代码和最新数据制品。

需要补的证据：

```bash
sha256sum /opt/awkn-life/services/knowledge-service/main.py
git hash-object apps/AWKN-LABlife/services/knowledge-service/main.py
git diff <生产快照> -- apps/AWKN-LABlife/services/knowledge-service/main.py
```

文件路径差异属于部署目录差异，不能直接证明代码体系分裂。

## 3.2 “58.3% 用户搜不到”结论过度

生产记录显示：

```text
passageCount = 329577
loadedItems = 329577
vector_count = 137337
items_count = 137337
```

可以确认：

- 关键词语料池加载 329577 条。
- 向量语料池加载 137337 条。
- 192240 条语料缺少向量表示。

当前后端调用链默认走：

```text
/hybrid_search
→ 向量检索 + 关键词检索
→ hybrid 失败时回退 /retrieve
```

关键词路径使用 `DATA.items` 与 `DATA.by_system`，理论上可以覆盖 329577 条。因此，原文的“58.3% 知识无法被用户检索”不成立。

准确风险描述应为：

> 58.3% 的语料没有进入语义向量召回，只能依赖关键词召回；同义表达、隐含语义、跨术语查询的召回质量可能显著下降。

风险等级仍然较高，性质属于**语义召回覆盖缺口**，暂时没有证据支持“完全不可访问”。

还需确认：

1. 生产 `hybrid_search` 是否默认启用。
2. `USE_HYBRID_SEARCH` 生产值。
3. 329577 条是否全部进入 `DATA.by_system`。
4. 关键词检索 3 秒超时下能否扫描全量语料。
5. 新增的 192240 条在真实问法中的命中率。

## 3.3 “PR-A 无价值”混淆了运行代码与制品生成工具

PR-A 修复：

```text
scripts/embed_classics_v3.py
```

该脚本属于离线数据生成链，职责是生成：

- `embeddings_v3.npy`
- `_embed_meta_v3.json`
- 进度与完整性结果

生产常驻服务本来就不应持续运行该脚本。它的生产价值通过“生成合格制品 → 上传 → 校验 → 切换”实现。

因此：

- “生产不运行此脚本”不能证明 PR-A 无价值。
- “PR-A 尚未形成生产效果”成立。
- PR-A 仍需要独立 commit，方便重跑、审计和回滚生成链。

PR-B 也属于数据质量链。NULL bytes 清洗会影响后续索引和 embedding 生成，价值同样不以生产直接执行脚本为前提。

PR-C 才属于运行时切换能力，生产是否部署直接决定用户效果。

三者应分开定义：

| PR | 工程性质 | 完成标准 |
|---|---|---|
| PR-A | 制品生成工具 | 脚本测试通过，制品可重复生成，meta 完整 |
| PR-B | 数据清洗与索引质量 | NULL bytes 清零，重建后行数与哈希可核验 |
| PR-C | 运行时版本切换 | staging/生产可按变量切换，健康接口和回滚验证通过 |

## 3.4 “独立 commit 是形式主义”判断错误

真正的问题集中在 `7edddc72`：

- 187 个文件。
- 28229 行变化。
- 产品代码、知识数据、治理文档、部署脚本混在一个 WIP 提交。

这类提交无法安全评审，也无法精确回滚。

原子提交可以直接支持：

- 只部署 PR-C。
- 单独回滚 PR-B 数据修复。
- 对 PR-A 运行专属测试。
- 审计某个生产制品由哪次代码生成。
- 将低风险修复 cherry-pick 到干净分支。

因此应该停止的是：

> 在脏工作区里用 reset、强拆历史、一次性重写 187 文件。

应该保留的是：

> 在新 worktree 或干净分支中，把 PR-A、PR-B、PR-C 重新组织成可验证的原子提交。

建议路径：

```text
建立干净 worktree
→ cherry-pick PR-A
→ 从 WIP 中提取 PR-B 文件
→ 从 WIP 中提取 PR-C 文件
→ 每批独立测试
→ 生成 staging 部署包
```

## 3.5 v3 评估方法本身不具备生产决策强度

原文批评生产没有闭环，却接受了 `v3切换评估.md` 的核心指标。评估脚本存在四个关键缺陷。

### 缺陷 1：v2 与 v3 候选集不一致

v2 基线通过：

```python
main.EmbedSearchRequest(
    question=...,
    systemType=query["systemType"]
)
```

生产 `_vector_search` 会按 `system_type` 过滤。

v3 全量评估脚本直接执行：

```python
sims = embeddings_v3 @ qv
top_indices = ...
```

脚本没有按 `systemType` 过滤。v2 在分类池内检索，v3 在全库检索，比较条件不一致。

### 缺陷 2：相关性标签过宽

判定逻辑：

```python
任意 1 个关键词出现在 text 中 → relevant
```

示例：

```text
相术面部五官
keywords = ["面", "五官", "相"]
```

“相”是高频汉字，会把大量无关文本标为相关。`MRR=1.0` 和 `P@10≈1.0` 很可能存在严重虚高。

### 缺陷 3：查询规模过小

- 仅 12 个查询。
- 每个体系 1—2 个查询。
- 没有真实用户问题。
- 没有困难负样本。
- 没有跨术语、口语、错别字、隐喻表达。

`+5.0%` 只相当于 Top-10 结果中少量标签变化，统计稳定性不足。

### 缺陷 4：脚本判定与报告判定不一致

脚本只看：

```text
v3 avg_precision >= v2 avg_precision
```

即可输出 `V3_SUPERIOR`。

报告又额外引入：

```text
MRR 退化超过 -5% → No-Go
```

最终人工改成 `Conditional Go`。决策规则没有统一进入代码，报告存在事后解释空间。

因此，当前 `Conditional Go` 应降级为：

> 技术可行性初测通过，检索质量结论无效，禁止据此进入生产灰度。

验收：形成唯一生产快照，任何后续结论均引用该快照。

## P1｜v2 生产一致性修复

先处理现网已有能力：

1. 明确 137337 对应哪一版语料。
2. 解释 329577 关键词池何时进入生产。
3. 生成 329577 条 v2 embeddings 或回退语料池到同一版本。
4. 保证 `len(index) == embeddings.shape[0]`。
5. 增加启动闸门，数量不一致时拒绝向量初始化并报警。
6. 对 hybrid_search 做真实查询回归。

验收：

```text
passageCount == loadedItems
vector_count == items_count
向量索引版本与语料版本一致
hybrid_search 无静默降级
```

## P2｜重做检索质量评估

建立 50—100 条真实问题集，覆盖：

- 八字、六壬、奇门、紫微、六爻、周易、风水、相术。
- 专业问法、口语问法、错别字、同义词、模糊表达。
- 明确负样本和跨体系干扰样本。

每条 Top-10 由人工标注：

```text
2 = 直接回答问题
1 = 有帮助但不充分
0 = 无关
```

指标：

- nDCG@10
- Recall@10
- MRR@10
- 无结果率
- 跨体系误召回率
- p95 延迟
- 内存峰值

v2 与 v3 必须：

- 使用同一语料。
- 使用同一 system_type 过滤。
- 使用同一查询集。
- 使用同一相关性标签。
- 使用同一 Top-K 和后处理规则。

## P3｜v3 staging 灰度

前置条件：P0、P1、P2 全部通过。

执行：

1. 独立 staging 进程与端口。
2. 上传 v3 embeddings、meta、模型缓存。
3. `KNOWLEDGE_EMBED_VERSION=v3`。
4. 跑功能、延迟、内存和召回回归。
5. 影子流量对比 v2/v3。
6. 达标后再讨论生产切换。

回滚标准：

- 进程级蓝绿切换。
- v2 与 v3 独立数据目录。
- 回滚经过实际演练。

“修改变量 + 重启”会产生短暂服务中断，不能写成零停机。
