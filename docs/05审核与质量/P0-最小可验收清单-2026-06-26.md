## 1｜清单设计原则

1. **只覆盖 P0 已验收项**：不包含 P1+ 的性能/并发/压测
2. **轻量级**：仅用 curl + grep，不依赖 jq/pytest
3. **可重复执行**：每次部署后 5 分钟内一键验证
4. **fail-fast**：任一 FAIL 即 exit 1，阻断后续发布
5. **降级非致命**：WARN 不阻断，但提示前端读 degradations 数组

## 4｜检查项详解

### 检查 1：就绪探针 /api/v1/health/ready

**对应 P0-3 Step5**：构建产物完整性 + 降级标志位

**通过条件**：
- HTTP 200
- `status` 字段为 `ok` 或 `degraded`（不能是 `down`）

**降级项提示**：
- 若 `degradations[]` 非空，输出 WARN（非致命）
- 当前降级项：`["assets", "pythonCli"]`
  - `assets`：knowledge-base/bazi 缺失（服务器无 symlink）
  - `pythonCli`：ZIWEI_CLI_PATH 未设置（ziwei-agent 降级到 iztro JS 库）

**失败排查**：
- 503 → preflight 失败，查 `pm2 logs awkn-life-backend | grep [preflight]`
- 404 → 路由未注册，确认全局前缀 `/api/v1` + HealthController 已加载

### 检查 2：llmProvider 配置

**对应 P0-1**：LLM 供应链稳定化

**通过条件**：`checks.llmProvider.status = "ok"`

**逻辑**：按 `DEFAULT_LLM_PROVIDER` 动态校验对应 API Key
- `deepseek-direct` → `DEEPSEEK_DIRECT_API_KEY`
- `sensenova` → `SENSENOVA_API_KEY`
- `doubao` → `DOUBAO_API_KEY`
- 其他 → 检查任意已配置的 LLM key

**失败排查**：
- 确认 `.env.prod` 含 `DEFAULT_LLM_PROVIDER=deepseek-direct`
- 确认 `DEEPSEEK_DIRECT_API_KEY` 非空

### 检查 3：LLM provider 链路

**对应 P0-1**：LLM provider 链路（deepseek-direct 主 + sensenova 备）

**通过条件**：`/api/v1/health/llm` 返回 200 且 body 含 `"deepseek-direct"`

**说明**：此端点返回 LLM 健康统计（成功率、熔断器状态、限流配额），验证 provider 链路已注册

### 检查 4：问事链可达

**对应 P0-2**：问事链 E2E 验收（轻量级）

**通过条件**：`/api/v1/consult/celebrity-cases` 返回 200

**说明**：celebrity-cases 是公开端点（无需鉴权），验证 consult 模块已加载

### 检查 5：K线链可达

**对应 P0-2**：命运K线链 E2E 验收（轻量级）

**通过条件**：`/api/v1/kline-tide/bars` 返回 200 或 401

**说明**：
- 200 = 已登录用户可访问
- 401 = 端点已注册但需鉴权（也算可达）
- 404 = 端点未注册（FAIL）

## 6｜与现有 smoke-test.sh 的关系

| 脚本 | 范围 | 用途 |
|------|------|------|
| `smoke-test.sh` | 5 个基础端点（health/db/consult/payment/root） | 部署前置冒烟，覆盖面广但浅 |
| `p0-acceptance-check.sh` | 5 个 P0 专项检查（health/ready + LLM + 三主链） | P0 验收，聚焦 LLM 供应链 + 构建产物完整性 |

**建议**：两者叠加使用
1. 部署前：`smoke-test.sh`（基础冒烟）
2. 部署后：`p0-acceptance-check.sh`（P0 专项验收）
