## Chapter 0：宪法引用

本PRD遵循项目宪法约束（硬约束清单见 project_memory.md），重点：
- 积分扣减必须用乐观锁 `where: { creditBalance: { gte: cost } }`
- 解锁操作必须用 `creditLedger` 幂等检查
- 后端定价必须与前端 `i18n/membership.json` 一致
- 所有 middleware 必须用 async/await
- TypeScript 必须 `npx tsc --noEmit` 通过

## Chapter 1：核心需求

### 1.1 解决什么问题

当前项目"能跑主流程但未达产品闭环"。三大卡点：
1. **稳定性卡点**：LLM供应链不稳定（doubao 403/minimax 429），深度推演不可控
2. **可信度卡点**：命运K线是金融模拟数据层，零命理算法，专家感不足
3. **聚焦卡点**：问事/取名对话前台未统一，残余弹窗式步骤破坏体验

### 1.2 为谁解决

- **终端用户**：付费用户期望"高质量推演+稳定体验"，当前常遇到LLM降级返回兜底文案
- **产品方**：需要"可卖的闭环"才能放量，当前主链路虽通但不可持续收费

### 1.3 成功标准（可量化）

| 指标 | 当前 | 目标 | 验证方式 |
|------|------|------|----------|
| 问事深度推演成功率 | 未测（doubao 403/minimax 429频发） | ≥90% (连续10次) | 端到端测试 |
| LLM单次超时 | 60s/180s硬编码 | ≤30s自动切备用 | 日志+监控 |
| K线三线评分 | DIM_SEED模拟 | 接入BaZiProfile命理算法骨架 | 评分可解释 |
| 问事全流程弹窗数 | 多处表单分支 | 0（全对话内完成） | 端到端走查 |
| 三主链路回归测试 | 无 | 全绿 | `npm test` |

## Chapter 3：用户故事

### Epic 1：LLM稳定性（P0）

**US1.1 HTTP状态码感知路由**
> As 系统运维者，I want LLM调用按HTTP状态码分流策略，So that 403立即切+冷却、429读Retry-After重试同provider、5xx重试、超时重试1次再切。

验收标准：
- [ ] 403触发立即切备用+标记provider冷却10分钟
- [ ] 429读取Retry-After头，无则指数退避重试同provider 3次
- [ ] 5xx/网络错误重试同provider 2次
- [ ] 超时重试同provider 1次后切
- [ ] 冷却期内provider不参与fallback链

**US1.2 指数退避重试**
> As 系统运维者，I want 同provider失败后指数退避重试，So that 429瞬时错误不立即烧光备用配额。

验收标准：
- [ ] 退避公式 base×2^n + jitter（base=500ms，n=重试次数）
- [ ] 最大重试次数可配置（默认3）
- [ ] 重试间隔有抖动避免惊群
- [ ] 重试次数耗尽才切备用provider

**US1.3 熔断器状态机**
> As 系统运维者，I want 连续失败provider被熔断摘流，So that 故障provider不会持续拖慢响应。

验收标准：
- [ ] 状态机：Closed→Open（连续失败≥5）→Half-Open（冷却60s后）→Closed（探测成功）
- [ ] Open状态provider不参与fallback
- [ ] Half-Open放1个探测请求
- [ ] `/health/llm` 暴露各provider熔断状态

**US1.4 限流前置防线**
> As 系统运维者，I want 按provider限流，So that 主动避免触发429。

验收标准：
- [ ] 令牌桶限流（按provider RPM配置）
- [ ] 超限请求排队或快速失败（可配置）
- [ ] 限流阈值从环境变量读取

### Epic 2：命运K线命理化骨架（P1）

**US2.1 BaZiProfile数据源接入**
> As 用户，I want K线评分来自我的真实八字，So that 不是模拟数据。

验收标准：
- [ ] KlineBar写入时从BaZiProfile读取四柱+十神+用神
- [ ] DIM_SEED仅作为"无八字档案"兜底
- [ ] 评分计算有命理学注释来源

**US2.2 三线命理算法骨架**
> As 用户，I want 事业/财富/情感三线有命理依据，So that 评分可解释。

验收标准：
- [ ] 事业线：基于官星旺衰+日主强弱
- [ ] 财富线：基于财星旺衰+食伤生财
- [ ] 情感线：基于日主配偶宫+桃花神煞
- [ ] 算法有单元测试

**US2.3 免费预览+会员分层**
> As 未登录用户，I want 看到K线预览，So that 判断是否值得付费解锁。

验收标准：
- [ ] 未登录看到3个关键节点预览+解锁引导
- [ ] 会员看到完整K线+窗口解释
- [ ] `unlockStatus`字段贯穿前后端

**US2.4 节点解释LLM化**
> As 用户，I want 节点有解释和行动建议，So that 不是纯数据点。

验收标准：
- [ ] 关键节点4字段：窗口类型/原因/风险/行动建议
- [ ] LLM生成有命理兜底模板
- [ ] LLM失败不空白

### Epic 3：问事对话闭环骨架（P2）

**US3.1 liuren起卦时间迁入对话**
> As 用户，I want 在对话里确认起卦时间，So that 不弹窗不跳转。

验收标准：
- [ ] 新增phase: `liuren_ask_time`/`liuren_ask_location`
- [ ] 对话内渲染datetime-local+CityQuickInput
- [ ] 提交后走`consultApi.analyze`带askTime/askLocation

**US3.2 ziping档案引导迁入对话**
> As 用户，I want 在对话里确认档案，So that 不跳转ProfilePage。

验收标准：
- [ ] 新增phase: `ziping_profile_check`/`ziping_profile_choice`
- [ ] 有档案→对话内确认开始
- [ ] 无档案→对话内提供"去填写/跳过"选项

**US3.3 跨模块契约对齐**
> As 开发者，I want 跳转目标统一，So that 迁移不破坏现有契约。

验收标准：
- [ ] ResultPage兼容`/result`和`/result/{id}`
- [ ] 档案填写入口统一（/profile或/kline-intro二选一）
- [ ] saveConsultData字段集合对齐

## Chapter 4：非功能需求

- **性能**：LLM单次调用≤30s超时；K线评分计算≤500ms
- **可观测性**：`/health/llm`暴露熔断状态/连续失败数/错误码分布
- **稳定性**：LLM熔断后冷却60s自动恢复；K线LLM失败有兜底
- **兼容性**：不破坏现有三主链路；前端构建通过；后端tsc通过
- **安全**：所有LLM apiKey不进前端不进仓库；env权威来源唯一

## Chapter 5：依赖与风险

### 5.1 依赖

- P0-LLM稳定性是P1-T2.4和P2-T3.5的前置（质量提升依赖稳定）
- P1-T2.1数据源接入是T2.2算法的前置
- P2-T3.1契约对齐是T3.2/T3.3的前置

### 5.2 风险

| 风险 | 概率 | 影响 | 缓解 |
|------|------|------|------|
| LLM供应商配额不足 | 高 | P0阻塞 | 验证6家现有配额；必要时引入新供应商 |
| K线命理算法2周做不完 | 高 | P1不达标 | 只做骨架，完整排v0.2 |
| ConsultPage迁移破坏现有链路 | 中 | P2阻塞 | 先对齐契约再改；每步可回滚 |
| 熔断器误摘流 | 中 | 可用性下降 | Half-Open探测+冷却60s自动恢复 |
