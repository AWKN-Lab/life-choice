## 0. 当前判断

问事已拥有完整的前端入口、意图路由、资料补齐、确定性计算、多术数 Agent、张半山调度、规则匹配、证据合成、知识检索、结果页、会员解锁、历史、回访和记忆代码。

当前问题集中在主链归口：

1. `/question`、首页弹层和 `/consult` 同时承接问事，流程状态与数据路径存在分叉。
2. 前端路由、后端路由、张半山调度均参与术数选择，最终真源不够清楚。
3. `FrontdeskChat` 已有 11 个问事阶段，后端还有 NodeStateMachine、UnifiedStateMachine，状态字典尚未统一。
4. 已登录路径会调用真实 `analyze`，部分异常路径仍使用临时 recordId 和草稿结果进入 ResultPage。
5. 结果结构同时存在三段式、五层、六段降级、14 段骨架和模块化结果，前台需要大量兼容逻辑。
6. `ConsultDialogueTurn`、`MemoryEmbedding` 代码存在，2026-07-07 生产基线中对应表尚未落地。
7. GenerationRun、KnowledgeHit 的数据沉淀尚未形成稳定生产证据。
8. 知识向量与混合检索延迟会直接影响完整问事链路。

下一阶段只做一条主链：

```text
用户说事
→ 系统补齐必要信息
→ 后端决定路线
→ 生成真实事项记录
→ 返回有依据的判断
→ 同一事项继续深推、追问、回访和复盘
```

## 1. 产品定义

### 1.1 一句话定位

> 问事帮助用户把一件复杂的事说清楚、看清当前局势、识别风险与代价，并拿到下一步行动。

### 1.2 用户获得的结果

一次有效问事必须交付：

```text
一句明确判断
判断成立的前提
当前最大风险或代价
最小可执行动作
适合观察或行动的时间窗口
可追溯的证据摘要
后续追问方向
```

### 1.3 使用边界

问事提供决策参考和行动整理，以下领域必须加强风险提示：

```text
医疗
法律
投资
人身安全
自伤与他伤
未成年人高风险事项
```

高风险问题进入 Guardrails 和 HighRiskDetector，结果中明确建议用户寻求现实专业支持。

### 1.4 北极星子指标

> 完成一次真实问事后，7 日内围绕同一事项继续追问、深推、回访或复盘的用户数。

一级指标：

```text
问事入口到提交率
首次分析完成率
真实recordId生成率
结果读取率
追问率
深推转化率
回访完成率
7日同事项复访率
```

质量指标：

```text
澄清中断率
临时结果占比
fallback占比
知识检索超时率
结果字段缺失率
证据引用缺失率
高风险误放行率
```

## 3. 目标用户与事项类型

### 3.1 模糊困惑型

用户表达：

```text
我最近很乱，不知道该怎么选。
```

系统任务：先提炼事项、对象、目标和时间边界，再判断是否需要出生信息或起念时间。

### 3.2 明确选择型

用户表达：

```text
这个工作机会要不要接？
这次合作能不能推进？
```

系统任务：识别选择项、代价、现实约束和时间窗口。

### 3.3 关系与人物型

用户表达：

```text
这段关系还有没有继续的必要？
这个人是否适合长期合作？
```

系统任务：绑定 PersonProfile，保留关系和事项边界，避免把人物判断写成永久标签。

### 3.4 长期趋势型

用户表达：

```text
今年事业怎么走？
未来两年的财务节奏如何？
```

系统任务：优先调用出生档案、K线/潮汐和子平路线，输出阶段与窗口。

### 3.5 高风险型

用户表达涉及医疗、法律、重大投资、人身安全时：

```text
先做风险分类
限制结论强度
给现实行动建议
提示专业支持
记录安全处理
```

## 4. 标准用户主流程

### 4.1 新用户首问

```text
进入 /question
→ 输入自然语言问题
→ 前端只做基础格式校验
→ POST /consult/route 或统一会话入口
→ 后端返回所需槽位
→ 对话中逐项补齐
→ POST /consult/analyze
→ 立即生成真实 ConsultRecord
→ 返回 recordId + generationStatus
→ ResultPage 读取或订阅结果
→ 展示判断、依据、风险、行动和窗口
→ 保存、深推、追问或设置回访
```

### 4.2 已有档案用户

```text
输入问题
→ 加载 BaZiProfile / UserMemory / PersonProfile
→ 用户确认使用的档案和人物
→ 后端路由
→ 生成事项记录
→ 返回结果
```

### 4.3 六壬等起念路线

```text
识别需要 askTime
→ 默认当前时间并允许修改
→ 收集 askLocation
→ 真太阳时与起课
→ 张半山融合
→ 结果返回
```

### 4.4 深推

```text
用户点击深入推演
→ 检查权益
→ 解锁 recordId + moduleId
→ 复用原输入、计算结果、证据和上下文
→ 运行 deep_consult
→ 原地更新模块状态
→ ResultPage 增量展示
```

### 4.5 追问

```text
用户围绕原事项继续提问
→ 创建或恢复 dialogueId
→ 写入 ConsultDialogueTurn
→ 读取原 recordId、EvidencePacket 和有限历史
→ 回复
→ 更新对话和必要记忆
```

### 4.6 回访与闭环

```text
到达回访节点
→ 用户确认实际发生情况
→ 写入 closed-loop
→ 更新 ConsultFollowUp
→ 形成预测—行动—结果—复盘
→ 后续判断可引用该闭环事实
```

## 5. 统一状态机

### 5.1 业务状态

后端统一使用：

```text
draft             已输入，未完成必要资料
clarifying        正在补齐信息
ready             已具备分析条件
queued            已创建记录，等待处理
calculating       确定性计算
retrieving        规则与知识检索
reasoning         Agent与张半山融合
generating        结果表达
completed         结果可读
partial           基础结果可读，深层模块处理中
failed_retryable  可原地重试
failed_terminal   无法继续
followup          追问或回访中
closed_loop       已完成现实复盘
```

### 5.2 前端映射

| 前端阶段 | 后端状态 |
|---|---|
| input | draft |
| clarify / liuren_ask_time / liuren_ask_location / ziping_profile_* | clarifying |
| submitting | ready / queued / calculating |
| preview | completed / partial |
| deepening | retrieving / reasoning / generating |
| followup | followup |
| error_retry | failed_retryable |

前端不得自行把临时状态转成“分析完成”。

### 5.3 状态原则

1. 状态变化由后端事实驱动。
2. 每次状态变化记录时间和原因。
3. 重试沿用原 `recordId` 和 `moduleId`。
4. 页面刷新后可从后端恢复。
5. WebSocket 只用于加速更新，HTTP 读取仍能恢复最终状态。

```text

```

```text

```

### 6.3 补问规则

1. 每轮最多提出两个关键问题。
2. 已有档案不得重复索取。
3. 信息缺失影响可信度时必须说明。
4. 用户可跳过非必要信息。
5. 跳过后降低结论强度并写入 uncertainty。
6. 用户显式选择术数时可以保留，但系统要判断输入是否满足。

### 6.4 前端路由职责

前端只负责：

```text

```

```text

所需槽位
主次 Agent
工具组合
安全判断
分析模式
```

### 7.2 快读与深推

目标：快速交付最小有效判断。

包含：

```text

关键计算
少量规则
核心判断

```

目标：交付完整证据、冲突仲裁和行动路径。


## 8. 统一结果契约

### 8.1 ResultEnvelope

```ts
interface ConsultResultEnvelope {

    sourceId?: string;

  }>;
  risks: Array<{
    level: 'low' | 'medium' | 'high';

    response?: string;
  }>;
  actions: Array<{
    priority: number;
    text: string;
    timing?: string;
  }>;
  timeWindows: Array<{
    label: string;
    start?: string;
    end?: string;
    type: 'opportunity' | 'risk' | 'observe';
  }>;
  modules: Array<{
    moduleId: string;
    title: string;
    status: 'free' | 'locked' | 'processing' | 'completed' | 'failed_retryable';
    content?: unknown;
  }>;
  followUp: {
    suggestedQuestions: string[];
    recommendedAt?: string;
  };
  audit: {
    evidencePacketId?: string;
    generationRunId?: string;
    knowledgeHitCount: number;
    fallback: boolean;
    sourceVersion?: string;
  };
}
```

### 8.2 首屏结果

固定顺序：

```text
判断
前提
代价
最小行动
时间窗口
```

证据、命盘和完整推演进入折叠或模块区。

### 8.3 降级结果

降级必须明确：

```text
哪些能力未完成
当前结果依据什么
哪些结论暂时不能给
用户下一步怎么做
```

禁止用静态完整报告伪装真实分析。

## 9. 连续对话、记忆与人物

### 9.1 事项主键

同一事件使用同一个 `recordId`。

```text
首问
深推
模块重试
追问
回访
闭环结果
```

### 9.2 对话主键

`dialogueId` 负责同一事项中的连续轮次，`ConsultDialogueTurn` 保存每轮内容和元数据。

### 9.3 人物档案

涉及他人时：

1. 用户确认人物身份和关系。
2. 记录稳定资料和当前关系。
3. 事项结论写入 ConsultRecord。
4. 禁止把单次判断永久写成人物事实。

### 9.4 记忆写入

可写入：

```text
稳定偏好
长期目标
明确关系
用户确认的事实
重复出现的问题模式
```

禁止自动写入：

```text
未验证的术数结论
高风险推断
他人敏感标签
临时情绪
```

用户应能查看、修正和删除记忆。

1. `/question` 成为唯一公开问事入口。
2. `/consult` 只保留兼容跳转和旧链接承接。
3. 删除生产主链的临时 recordId、静态草稿和 Mock 完整结果。
4. 后端成为最终 routeType 真源。
5. 统一前后端状态机。
6. 定义并落地 ConsultResultEnvelope。
7. 完成生产 DialogueTurn、MemoryEmbedding 迁移。
8. 确保每次分析创建真实 ConsultRecord。
9. 失败重试沿用原 recordId。

## P1｜证据与质量

1. 统一 KnowledgeRetriever 契约。
2. 每次完整分析写入 EvidencePacket、GenerationRun、KnowledgeHit。
3. 结果页显示简化证据和可信度。
4. 建立 quick_read 与 deep_consult 明确范围。
5. 知识检索性能进入主链门槛。
6. 高风险链路完成自动化测试。
7. 结果结构减少兼容分支。

## P2｜连续服务

1. 追问完整写入 DialogueTurn。
2. 用户可查看和管理记忆。
3. 人物档案与事项记录联动。
4. 回访、闭环和编年史贯通。
5. 历史按人物—事项—时间组织。
6. 同一事项多次判断可对比。

## P3｜经营增长

1. 深推商品和权益统一。
2. 追问次数与会员层级统一。
3. 回访提醒形成复购触点。
4. 优质闭环案例进入人工审核池。
5. 运营看板可追踪一次问事的成本、质量和收入。

## 14. 验收标准

### 14.1 产品验收

- [ ] 用户可直接说事，无需先选术数。
- [ ] 必要信息在对话中补齐。
- [ ] 首次提交生成真实 recordId。
- [ ] 结果首屏包含判断、前提、代价、行动和窗口。
- [ ] 深推、追问、回访围绕原事项继续。
- [ ] 页面刷新后流程可恢复。

### 14.2 工程验收

- [ ] 前后端使用同一状态字典。
- [ ] `/consult/preview` 不在生产主链中调用。
- [ ] 临时草稿不能进入正式历史。
- [ ] DialogueTurn、MemoryEmbedding 在生产存在。
- [ ] ResultEnvelope 有 Schema、类型和兼容适配层。
- [ ] 所有 retry 不重复扣费。
- [ ] WebSocket 断开后可通过 HTTP 恢复。

### 14.3 数据验收

- [ ] ConsultRecord、EvidencePacket、GenerationRun、KnowledgeHit 能形成完整链路。
- [ ] 每轮追问有 dialogueId 和 turn 记录。
- [ ] 人物资料与事项结论分开存储。
- [ ] closed-loop 可查询。
- [ ] 用户可删除咨询和相关记忆。

### 14.4 质量验收

- [ ] 结论强度与证据强度匹配。
- [ ] 经典引用含 sourceId。
- [ ] 规则结论含 ruleCode。
- [ ] fallback 有明确标记。
- [ ] 高风险问题被正确识别。
- [ ] Golden Cases 覆盖主要事项类型。

### 14.5 经营验收

- [ ] 首问、结果、深推、追问、回访漏斗可统计。
- [ ] 解锁绑定 recordId 和 moduleId。
- [ ] 7日同事项复访率可查询。
- [ ] 单次生成成本可追踪。
- [ ] 失败、退款、重试可审计。
