## Ch0 文档元信息

| 术语 | 定义 |
|------|------|

## Ch2 用户画像与场景

### 2.1 用户画像

| 角色 | 特征 | 核心诉求 | 当前痛点 |
|------|------|---------|---------|
| **AI 协作代理（天火）** | 每次会话需要快速定位上下文 | 单一真相源、可检索、可回写 | 三层体系互不引用，找不到权威信息 |
| **项目负责人（用户）** | 跨项目决策、版本评审 | 路线图、复盘、经验可追溯 | 路线图无迭代评审、复盘不沉淀 |
| **未来新成员** | 首次接触项目 | 入职文档、Tutorial | 无独立 Tutorial 分类 |

### 2.2 核心场景

**场景 1：AI 协作启动**
- 触发：新会话开始
- 动作：AI 读取 KNOWLEDGE-MAP.md → 定位当前任务相关文档 → 执行
- 期望：≤30 秒内找到权威信息源

**场景 2：版本里程碑评审**
- 触发：V1 阶段结束
- 动作：执行 Sprint Retrospective → 产出复盘 → 回写路线图 + 沉淀经验
- 期望：复盘有模板、回写有规则、经验有编号

**场景 3：新文档创建**
- 触发：开发过程中产生新文档
- 动作：写入对应目录 → 更新文档索引 → 更新 KNOWLEDGE-MAP.md → CI 检查通过
- 期望：文档不游离、引用不失效

**场景 4：会话记忆归档**
- 触发：每日自动 / 手动触发
- 动作：>7 天的 session 文件移至 04-backups/ → 更新 _index.md
- 期望：03-sessions/ 保持 ≤7 天数据量

## Ch11 工程哲学

### 11.1 治理哲学

**原则 1：单一真相源优先于数量丰富**
- 每类信息只有一个权威来源
- 其他位置仅引用不复制
- 当信息冲突时，以权威来源为准

**原则 2：可持续治理优先于一次性整理**
- 治理机制必须自动化（CI 检查、归档脚本）
- 治理规则必须可执行（pre-commit hook）
- 治理责任必须可追溯（文档有 owner）

**原则 3：闭环优先于完美**
- 梳理方案必须闭环（即使有差异）
