## 3. PRD 本身的批判性审视

PRD 诊断准确，但作为工程执行文档，存在以下问题需要批判性审视：

### 3.1 PRD 的优点（先肯定）

1. **诊断基于真实代码审计** — 6/6 准确，不是凭空想象
2. **闸门机制严格** — G0-G7 每阶段有明确闸门，未通过不得继续
3. **非目标清单清晰** — 第 3 节明确列出 8 个"不做"，防止范围蔓延
4. **执行约束明确** — 第 8 节 8 条约束，特别是"禁止以 passages 数量代替质量验收"
5. **完成标准可验收** — 第 2 节 8 条完成标准，每条都可判定
6. **交付物清单完整** — 第 7 节 16 项交付物，每项都有明确产出

### 3.2 PRD 的过度设计风险

**风险1: 17 个分类体系过度理想化**

PRD FR-09 要求 17 个分类，但当前书籍实际只覆盖 9 个术数体系。`western_astrology`、`tarot`、`rune` 三个分类可能根本无对应书籍。

**问题**:
- 为不存在的分类建空分类，增加维护成本
- 17 个分类的规则、置信度、复核状态，工作量被低估

**建议**: 先建当前有的 9 个分类 + 3 个确凿缺失的（ziwei/quming/daoism）= 12 个。`taiyi`/`western_astrology`/`tarot`/`rune` 等待有书籍时再加。

**风险2: UUIDv5 确定性 ID 体系过重**

PRD FR-04 要求：
```
work_id = UUIDv5(标准书名 + 作者 + 作品类型)
edition_id = UUIDv5(work_id + 版本/卷册)
source_id = SHA256(原始文件)
```
+ 6 种关系（same_work/different_edition/volume_of/ocr_version_of/duplicate_binary/derived_text_of）

**问题**:
- 这是一套完整的图书情报学本体模型
- 585 本书的去重和版本关系梳理，工作量远超 PRD 估算
- "标准书名"本身就需要人工判定（如"三命通会 ([明]万明英 撰  陈明  王胜恩 注释)"如何标准化？）

**建议**: 先用 `source_id = SHA256(原始文件)` 做基础去重，UUIDv5 体系延后。版本关系只做 `duplicate_binary` 和 `derived_text_of` 两种。

**风险3: v3 混合检索的四层架构过重**

PRD FR-10 要求 v3 由四层构成：
```
FTS/BM25 + 中文语义向量 + 元数据过滤 + 重排
```

**问题**:
- "中文语义向量"需要选型 + 部署 + 137337 条全量 embed，成本高
- "重排"需要 reranker 模型，又是一层基础设施
- 当前 TF-IDF 兜底虽有缺陷，但对精确词面匹配（经典原文）反而更准
- PRD 没有评估 TF-IDF 实际效果就直接判定需要语义向量

**建议**: 
- 先修复 v2 的 6 个问题，让现有 TF-IDF 真正可用
- 跑 recall@k / precision@k 量化 TF-IDF 效果
- 效果不达标再加语义向量（BM25 + 语义向量两层足够，重排可延后）

**风险4: 60GB 外部空间要求可能不必要**

PRD G0 要求"准备至少 60GB 外部可用空间"，但当前 C 盘剩 42GB。

**问题**:
- 60GB 的用途未细化（备份 .git 8.8GB + v3 索引产物 + PDF 恢复中间产物？）
- 如果只做 G1（检索底座修复），不需要 60GB
- 60GB 是全量 G0-G7 的空间需求，但可以分阶段申请

**建议**: 按阶段申请空间，G1 只需要 < 1GB。

### 3.3 PRD 的执行顺序问题

**问题1: G1 应该优先于 G0**

PRD 要求 G0（资产保护）→ G1（检索修复），但：
- G1 的 6 个问题是**当前用户受影响的最高优先级**
- G0 的资产保护是**预防性的**，不修复也能运行
- 用户当前访问的 `/retrieve` 返回 0 条，这是**正在发生的故障**

**建议**: 调整为 G1（检索修复）→ G0（资产保护）→ G2-G7。先修当前故障，再做预防性保护。

**问题2: G3 和 G4 可以并行**

PRD 要求 G3（585 语料治理）→ G4（589 恢复库治理），但：
- 两个库是独立的（585 在 manifest，589 在 metaphysics.db）
- 治理逻辑相似但数据不同
- 串行执行浪费时间

**建议**: G3 和 G4 可并行，但 G4 的"接入生产"必须等 G3 完成后评估。

**问题3: G5 PDF 恢复的优先级可能被高估**

PRD 把 PDF 恢复列为 G5，但：
- 1639 个 PDF 中有多少是核心术数资料？未评估
- 如果已有文本版本覆盖了核心内容，PDF 恢复的边际收益低
- OCR 成本高、质量难保证

**建议**: G5 降级为"按需恢复"，不作为闸门必经阶段。

## 4. 当前项目架构的批判性分析

### 4.1 知识服务的架构缺陷

当前 `knowledge-service/main.py` 存在**根本性架构问题**：

**问题1: 双重数据源混乱**
- v1 关键词检索：用 `loader.py` 加载 `knowledge-base/*.json`（路径错误，实际为空）
- v2 向量检索：用 `classics_index.jsonl + embeddings.npy`（路径正确，137337 条）
- 两套数据源不统一，`/hybrid_search` 混合时关键词通道为空

**问题2: 全局变量 + 惰性初始化**
- `_loaded_items`、`_loaded_embeddings` 是全局变量
- `_init_chroma()` 是惰性初始化，首次调用才加载
- 多线程并发时可能有竞态条件

**问题3: 向量范数每次重算**
- `_vector_search` 每次调用都算 `np.linalg.norm(_loaded_embeddings, axis=1)`
- 137337×1024 矩阵的范数计算，每次约 50-100ms
- 应该在 `_init_chroma` 时预计算并缓存

**问题4: 内存占用无控制**
- `_loaded_embeddings` 全量加载 536MB 到内存
- 服务器只有 755MB 可用内存
- `_loaded_items` 还要存 137337 条文本（截断到 500 字后约 70MB）
- 总计 ~600MB，接近内存极限

### 4.2 知识库 ingest 流程的缺陷

`knowledge_ingest.py` 的分类逻辑：

```python
# 当前逻辑（推断）
system_type = 'bazi' if 'bazi' in source_name else 'liuren'
```

这是**二分类**逻辑（bazi 或 liuren），而 manifest 的 `by_system` 有 9 个分类，说明分类逻辑有更新但未对齐。

**问题**:
- 紫微资料被归入 bazi（因含"八字"关键词？）
- 取名资料被归入 bazi（因含"命理"关键词？）
- 道教资料被归入 bazi（因含"道"关键词？）

### 4.3 前后端集成的问题

知识服务运行在 `127.0.0.1:8701`，但：
- 生产 Nginx 配置中没有 `/knowledge/` 的反向代理
- 后端 `orchestrator.service.ts` 调用知识服务的方式未确认
- 验证报告显示 `hybrid_search failed: This operation was aborted`（超时或连接失败）

**问题**: 知识服务可能根本没有被生产正确调用，或者调用路径有问题。
