## 1. 卡点（Blockers）

### 1.1 P0 阻断卡点（3 项）

#### P0-1: L2 Pipeline 超时风险（150s + 5 层校验失败兜底）
- **证据**: 前序验证报告 §5.4，LiurenAgent 单轮 26960ms + Validation + ReAct 累计 ~45s
- **风险**: 生产环境单次 deep_consult 可能在 LLM 高负载时突破 150s 超时；5 层校验失败的兜底机制是否合理尚未独立验证
- **影响**: 用户感知"卡死"或返回不完整结果
- **处置策略**: 部署前在预发环境跑 10 次真实 deep_consult，统计 P95/P99 耗时；超过 120s 即触发 LLM 降级

#### P0-2: nest build 不拷贝非 JS 资源（prompts/*.md）
- **证据**: 本次启动日志 `ENOENT: no such file or directory 'dist/liuren-agent/prompts/liuren-system-prompt.md'`
- **影响**: 所有 LLM Agent 的中文 systemPrompt 加载失败，回退到代码内默认 prompt（质量下降）
- **当前状态**: 已在 dist 中手动缺失，运行时降级，非阻断但质量受损
- **修复路径**: 在 `nest-cli.json` 的 `compilerOptions.assets` 添加 `**/prompts/*.md`，重新 build 验证

#### P0-3: Phase 3 主链路切换待生产灰度验证
- **证据**: Phase3-5+G4-7 最终结果单 §6 遗留事项 #3：Phase 3 主链路生产灰度验证待执行
- **风险**: Phase 3 状态机统一标注的改动在生产流量下未验证，可能引入状态机死锁/回退
- **影响**: 生产用户进入异常状态后无法恢复
- **处置策略**: 部署后开启 5% 流量灰度 24 小时，监控状态机异常率与回退日志

### 1.2 P1 高风险卡点（8 项）

#### P1-1: P0 装甲命中 0 条规则
- **证据**: 前序报告 §5.5：生产环境 evidencePackage 命中 0 条规则，完整度 0.3
- **根因**: RuleMatcher 规则集覆盖不足，或规则与生产真实问题分布不匹配
- **影响**: P0 装甲实际未生效，重大决策场景缺乏规则兜底
- **修复**: 用近 30 天生产咨询日志反向匹配规则集，识别规则盲区并补齐

#### P1-2: KnowledgeRetrieverService 占位实现
- **证据**: 审计报告批判性分析指出 `KnowledgeRetriever` 在 L2 Pipeline 中是占位实现
- **影响**: 知识检索通道实际未参与 L2 推理融合，TriMethodFusion 引用典籍数始终 ≤1
- **修复**: 接入真实 KnowledgeRetrieverService（v3 索引完成后）

#### P1-3: AgentRunLogger 未持久化
- **证据**: 审计报告批判性分析指出 ReAct Engine 的运行日志仅在内存中
- **影响**: 无法事后追溯 ReAct 决策链，难以定位 L2 异常
- **修复**: 新增 `AgentRunLog` 表，持久化每轮 ReAct 的 thought/action/observation

#### P1-4: G6 召回率 recall@10 = 0.473 < 0.7 阈值
- **证据**: Phase3-5+G4-7 最终结果单 §6 遗留事项 #1：G6-1/G6-2 v3 索引延期，当前 TF-IDF 兜底召回率不达标
- **影响**: 知识检索召回不足，影响 L2 引用典籍质量
- **修复**: 部署后启动 v3 索引重建（使用真实 embedding 模型），目标 recall@10 ≥ 0.7

#### P1-5: embeddings.npy 状态差异
- **证据**: 审计报告批判性分析指出生产环境 embeddings.npy 与本地版本存在差异
- **影响**: 生产向量检索结果与本地不一致，难以复现线上问题
- **修复**: 部署时同步 embeddings.npy，并在生产 /health 增加 embeddings sha256 上报

#### P1-6: L2 超时 150s + 5 层校验失败兜底未独立验证
- **证据**: 前序报告 §5.4 Validation passed=true score=100 retries=0，但 5 层校验全失败的兜底路径未触发
- **影响**: 兜底分支可能存在未发现的 bug
- **修复**: 在测试环境构造 5 层全失败用例，验证兜底返回是否符合预期

#### P1-7: routeType 字段在 LLM 日志中缺失
- **证据**: 本次增量验证 §3.4 byRouteType 全部 `unknown`
- **影响**: 成本看板无法按路由类型聚合，难以定位高成本路由
- **修复**: 在 LlmGateway 调用入口统一记录 routeType

#### P1-8: Phase 4 多轮对话流量为零
- **证据**: 本次增量验证 §3.4 multiTurn.totalCalls=0
- **影响**: Phase 4 多轮对话记忆系统的真实流量验证缺失，潜在 bug 未暴露
- **修复**: 部署后引导 5-10 个真实用户走多轮对话流程，监控异常

## 6. 关键根因分析

### 6.1 为什么 Phase 4/5 完成后仍有多项卡点？

**根因**: Phase 3-5 + G4-7 是"工程闭环"，不是"生产闭环"。工程闭环只保证 tsc + jest + build 通过，不保证生产流量下行为符合预期。

**证据**:
- Phase 4 多轮对话无流量（multiTurn.totalCalls=0）
- Phase 5 成本看板 routeType 全部 unknown
- P0 装甲命中 0 条规则

**进化建议**: 在 DSPBRSE 七阶段中，"Build 完成"不等于"Review 完成"。需要在 Build 阶段末尾增加"预发灰度验证"环节，强制要求至少 5 次真实流量验证。

### 6.2 为什么文档治理反复成为遗留事项？

**根因**: 缺乏"文档分层前置"机制。当前流程是"先写文档，事后梳理分层"，导致每次都积压。

**进化建议**: 在新建文档时强制要求在头部声明 `**文档分层**: HANDOFF/EXECUTION/REFERENCE/ANALYSIS/RAW/LESSON`，并按分层放入对应子目录。

### 6.3 为什么 G6 v3 索引反复延期？

**根因**: v3 索引依赖外部 embedding 模型选型，而选型决策被"先看 TF-IDF 效果"无限期推迟。

**进化建议**: 设定硬截止日期（如部署后 7 天内必须选定 embedding 模型），否则默认使用 BGE-M3 作为兜底。
