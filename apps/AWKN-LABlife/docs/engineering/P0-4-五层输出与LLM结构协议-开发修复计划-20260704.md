# P0-4 五层输出与 LLM 结构协议稳定性 - 开发与修复计划

- 日期：2026-07-04
- 规划原则：安全稳定 + 严格可执行（饭要一口口吃 v2）
- 拆解视角：数据流（LLM输出 → 截断检测 → 质量门校验 → 修复器 → 兜底 → Golden Case验证）
- 预计步数：8 步（5 个 Phase）

## A. 目标与边界

### 目标一句话
让五层输出（数术断句/半山落句/具体落点/代价提醒/下一步动作）在 LLM 截断、字段缺失时能自动检测、定向修复，Golden Case 连续通过率达 ≥90%。

### 本轮做（5项）
1. LlmResponse 接口添加 finishReason 字段 + 非流式 chat() 读取 finish_reason
2. 提升_generation-composer max_tokens 1200→3000
3. 截断检测 + 一次自动重试（finish_reason=length 触发）
4. 新建 layer-repair.service.ts 定向修复器（质量门返回缺失字段列表）
5. Golden Case 连续运行通过率验证

### 本轮不做（5项）
1. **不做** 5层校验全量启用到 zhangbanshan-scheduler 主路径（风险高，单列 P0-4.2）
2. **不做** JSON Schema 严格模式（json_schema 类型）— 需 Provider 支持，先观察 max_tokens+修复器效果
3. **不做** 兜底填充逻辑重构（保留现有 orchestrator.service.ts L620-L628 兜底）
4. **不做** 5层 marker 解析正则重写（现有正则可用）
5. **不做** 身份感校验阈值调整（独立问题，不在 P0-4 范围）

### 约束与假设（≤10）
1. 不破坏现有 PIPELINE_V2_ENABLED=true 时的行为
2. 不修改 zhangbanshan-scheduler 主路径（三段式）
3. 所有改动必须向后兼容（finishReason 可选字段）
4. 修复器失败时必须降级到现有兜底逻辑，不抛错给前端
5. max_tokens 提升不影响其他 Agent（只改 generation-composer）
6. Golden Case 验证用现有 golden-cases.json 数据
7. 截断重试只触发一次，避免无限循环
8. 修复器只针对"字段缺失"，不处理"内容质量低"
9. 生产部署需 PM2 reload + health 验证
10. 每一步必须可通过 jest 测试验证

## B. 选定拆解视角

- **刀法选择**：数据流
- **为什么选它**：P0-4 问题本质是 LLM 输出数据流中的检测和修复链路缺失。从 LLM 输出 → 截断检测 → 质量门校验 → 修复器 → 兜底 → 验证，每一步都是数据流的一个节点，按数据流拆解能清晰定位每个缺口。

## C. 最小闭环（MVP-0）

- **MVP-0 定义**：LLM 输出 → 读取 finish_reason → 若截断则重试一次 → 质量门校验 → 若缺字段则调修复器 → 通过或兜底
- **MVP-0 的"临时项"清单**：
  - 临时：修复器只用简单 prompt 补全，不使用 JSON Schema 严格模式
  - 临时：Golden Case 验证只跑 5 条（非全量 20 条）
  - 移除条件：Phase 5 完成后，Golden Case 全量 20 条通过率 ≥90%

## D. 分步清单（8 步）

### Step 1｜LlmResponse 接口添加 finishReason 字段
- **动作**：修改 `llm-providers.service.ts` 的 LlmResponse 接口，添加 `finishReason?: string` 可选字段
- **产出**：接口扩展，向后兼容
- **验收标准**：
  - 通过：tsc --noEmit 通过，现有测试全过
  - 失败：tsc 报错或现有测试失败
- **验证方法**：`npx tsc --noEmit && npx jest --testPathPattern="llm-providers" --no-coverage`
- **回滚方式**：`git checkout HEAD -- apps/api-server/src/llm-providers/llm-providers.service.ts`
- **风险标记**：低
- **Plan B**：无（纯接口扩展，无副作用）

### Step 2｜非流式 chat() 读取 finish_reason 并传递
- **动作**：修改 `llm-providers.service.ts` 的 `chat()` 方法（L432-L450），从 response 中读取 `choices[0].finish_reason`，写入 LlmResponse.finishReason
- **产出**：非流式调用支持截断信号传递
- **验收标准**：
  - 通过：mock LLM 返回 finish_reason=length 时，chat() 返回的 finishReason='length'
  - 失败：finishReason 字段为 undefined
- **验证方法**：新增单元测试 `llm-providers.spec.ts`，mock fetch 返回 finish_reason=length，断言 finishReason
- **回滚方式**：`git checkout HEAD -- apps/api-server/src/llm-providers/llm-providers.service.ts`
- **风险标记**：低
- **Plan B**：无

### Step 3｜提升 generation-composer max_tokens 1200→3000
- **动作**：修改 `generation-composer.service.ts` L134 和 L170 的 maxTokens 从 1200 提升到 3000
- **产出**：5层输出生成有足够 token 空间
- **验收标准**：
  - 通过：tsc 通过，generation-composer 测试全过
  - 失败：tsc 报错或测试失败
- **验证方法**：`npx tsc --noEmit && npx jest --testPathPattern="generation-composer" --no-coverage`
- **回滚方式**：`git checkout HEAD -- apps/api-server/src/consult/orchestrator/generation-composer.service.ts`
- **风险标记**：低（仅配置调整）
- **Plan B**：若 3000 仍截断，后续可提升到 4000（与 mvp0-runner 一致）

### Step 4｜截断检测 + 一次自动重试
- **动作**：在 `generation-composer.service.ts` 的 5 层生成调用处，检测 LlmResponse.finishReason === 'length'，若是则用提升后的 max_tokens（4000）重试一次
- **产出**：截断自动恢复机制
- **验收标准**：
  - 通过：mock 第一次 finishReason=length，第二次 finishReason=stop，最终拿到完整输出
  - 失败：截断时不重试，或重试后仍截断不降级
- **验证方法**：新增测试 `truncation-retry.spec.ts`，mock LLM 第一次返回 length，第二次返回 stop
- **回滚方式**：`git checkout HEAD -- apps/api-server/src/consult/orchestrator/generation-composer.service.ts`
- **风险标记**：中
- **Plan B**：重试后仍截断 → 记录 warn 日志，继续走质量门（不阻断）

### Step 5｜新建 layer-repair.service.ts 定向修复器
- **动作**：新建 `layer-repair.service.ts`，提供 `repairMissingLayers(missingLayers: string[], existingLayers: Partial<FiveLayerOutput>, question: string)` 方法，用 LLM 针对性补全缺失字段
- **产出**：定向修复器服务
- **验收标准**：
  - 通过：传入 missingLayers=['clause'] + existingLayers（含其他4层），返回完整 5 层
  - 失败：修复器抛错或返回空
- **验证方法**：新增测试 `layer-repair.spec.ts`，mock LLM 返回缺失字段内容
- **回滚方式**：删除 layer-repair.service.ts 和测试文件
- **风险标记**：中
- **Plan B**：修复器 LLM 调用失败 → 返回 existingLayers（不阻断，交给兜底）

### Step 6｜质量门返回缺失字段列表 + 调用修复器
- **动作**：
  1. 修改 `quality-gate.service.ts`，evaluateFiveLayers 不再直接抛 BadRequestException，改为返回 `{ passed: false, missingLayers: [...], repairable: true }`
  2. 修改 `orchestrator.service.ts`，质量门失败时调用 layerRepair.repairMissingLayers()，修复后再过一次质量门
- **产出**：质量门 + 修复器联动
- **验收标准**：
  - 通过：mock 5 层缺 clause → 质量门返回 missingLayers=['clause'] → 修复器补全 → 质量门通过
  - 失败：质量门仍直接抛错，或修复器不被调用
- **验证方法**：新增集成测试 `quality-gate-repair.spec.ts`
- **回滚方式**：`git checkout HEAD -- quality-gate.service.ts orchestrator.service.ts`
- **风险标记**：高（修改质量门行为）
- **Plan B**：修复器调用失败 → 降级到现有 orchestrator.service.ts L620-L628 兜底填充（不抛错给前端）

### Step 7｜Golden Case 连续运行验证
- **动作**：用 `mvp0-runner.ts` 跑 golden-cases.json 中 5 条核心 case，每条跑 3 次，统计通过率
- **产出**：Golden Case 通过率报告
- **验收标准**：
  - 通过：5 条 case × 3 次 = 15 次运行，通过率 ≥80%（12/15）
  - 失败：通过率 <80%
- **验证方法**：`node mvp0-runner.ts --case=gc-001,gc-005,gc-010,gc-015,gc-020 --repeat=3`
- **回滚方式**：无（验证步骤，不修改代码）
- **风险标记**：低
- **Plan B**：通过率 <80% → 分析失败 case，调整 max_tokens 或修复器 prompt

### Step 8｜生产部署 + 端到端验证
- **动作**：SCP 修改的文件到生产，build，资源恢复，PM2 reload，验证 health + 日志
- **产出**：生产部署完成
- **验收标准**：
  - 通过：PM2 online + health 200 + dist 中包含 finishReason/layer-repair 字段
  - 失败：PM2 errored 或 health 非 200
- **验证方法**：`ssh ... 'pm2 reload awkn-life-backend && curl health && grep finishReason dist/...'`
- **回滚方式**：`cp -r dist.old-p04/* dist/ && pm2 reload awkn-life-backend`
- **风险标记**：中
- **Plan B**：PM2 errored → 从 dist.old-p04 恢复资源目录 + reload

## E. 高风险清单（自动标红）

- **Step 6**：改质量门行为（原直接抛错 → 改为返回缺失字段+调用修复器）— 高风险
  - 缓解：修复器失败时降级到现有兜底，不抛错给前端
- **Step 4**：截断重试可能增加 LLM 调用延迟 — 中风险
  - 缓解：只重试一次，warn 日志监控
- **Step 8**：生产部署 — 中风险
  - 缓解：dist.old-p04 备份 + PM2 reload 回滚

## H. 执行顺序与依赖关系

```
Step 1 (接口) → Step 2 (chat读取) → Step 3 (max_tokens) → Step 4 (截断重试)
                                                              ↓
Step 5 (修复器) → Step 6 (质量门联动) → Step 7 (Golden Case) → Step 8 (生产部署)
```

- Step 1-2 是基础设施，必须先做
- Step 3-4 是截断处理，依赖 Step 1-2
- Step 5-6 是修复器，可与 Step 3-4 并行但建议串行（降低风险）
- Step 7-8 是验证和部署，依赖前 6 步

## I. 风险兜底总结

| 风险场景 | 兜底方案 |
|---------|---------|
| 截断重试后仍截断 | warn 日志，继续走质量门 |
| 修复器 LLM 调用失败 | 返回 existingLayers，交给 orchestrator 兜底 |
| 修复器补全后质量门仍失败 | 降级到 orchestrator.service.ts L620-L628 兜底填充 |
| 兜底填充后仍不完整 | 标记 llm_fallback=true，返回给前端（不抛错） |
| 生产部署 PM2 errored | 从 dist.old-p04 恢复 + reload |
| Golden Case 通过率 <80% | 分析失败 case，调整 max_tokens 或延后 JSON Schema |
