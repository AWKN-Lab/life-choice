## 2. 方法论审视

### 2.1 审计标准选择问题

报告隐含使用「Git 全量解析完整性」作为唯一审计标准，但**未声明标准选择依据**。

**问题**：
- 生产知识库的目标是什么？是「Git 资产 100% 数字化」还是「支撑 LLM 检索可用性」？
- 若是前者，审计标准合理；若是后者，审计标准偏严且偏离业务目标
- 报告把「未接入生产」「未完成清洗」「未使用语义向量」全部判为 FAIL，等同于把**设计决策**当成**失败**

**独立判断**：审计标准应区分「事实判断」与「价值判断」。例如：
- 事实：589 本恢复库未接入 → 这是事实
- 价值：未接入 = FAIL → 这是价值判断（可能是有意暂缓）

### 2.2 审计维度遗漏

报告**只做静态分析**（manifest、.git 对象、脚本复算），**缺少动态验证**：

| 遗漏维度 | 说明 | 影响 |
|---|---|---|
| 检索效果实测 | 未跑 recall@k / precision@k | 无法判断现有索引是否够用 |
| 用户场景测试 | 未模拟真实查询 | 不知道漏收的 22 本是否影响用户体验 |
| 运行时表现 | 未测向量检索延迟、降级率 | 不知道 TF-IDF 兜底是否拖慢响应 |
| LLM 实际引用质量 | 未统计 Agent 引用 sourceId 分布 | 不知道哪些书真被用到 |
| 对比基线 | 未对比行业/竞品 | 不知道 3.6% 漏收率算高还是低 |

### 2.3 审计方法局限

- **静态取证**：只能证明「有什么」，不能证明「能用什么」
- **脚本复算**：`knowledge_ingest.py` 规则复算的 607 候选，依赖规则正确性，但报告未验证规则本身
- **无 A/B 对比**：没有「修复前 vs 修复后」的效果对比，无法量化收益

## 3. 证据链逐条审视

### 证据1：Git 对象库远大于当前索引

> .git 约 8.8GB；43245 个悬空 blob，约 9413MB；PDF 1639 个 490MB、ZIP/DOCX 等 532 个 136MB

**证据强度**：中（数据真实，但推理有跳跃）

**问题**：
1. **悬空 blob ≠ 书籍内容**：8.8GB .git 包含代码历史、二进制资源、备份快照、依赖快照。把「9413MB 悬空 blob」暗示为「未解析书籍」是推理跳跃
2. **未去重**：同一本书的 PDF/DOCX/EPUB 可能被重复计数。《推背图》可能有 5 个版本，但本质是 1 本书
3. **未过滤相关性**：1639 个 PDF 中可能有大量与术数无关的资料（开发文档、依赖包、截图等）
4. **「大对象」≠「未入库」**：83MB 的 PDF 可能已经解析入库，只是源文件还在 .git 里

**反证可能性**：8.8GB .git 中真正「未入库的相关书籍」可能远少于报告暗示的数量。报告没有建立 `Git SHA → 原始书名 → 解析状态` 的总账，这条最关键的证据链**实际上缺失**（报告自己也承认：「目前没有完整的总账」）。

**独立判断**：这条证据**只能证明「需要进一步排查」**，不能证明「Git 中有大量未解析书籍」。报告把它列为第一证据，但实际是最弱的一条。

### 证据2：候选文本源 607 vs 已入库 585，漏收 22

**证据强度**：高（硬数据，可复算）

**问题**：
1. **漏收率 3.6%**（22/607）在工程上属于可接受范围，但报告未给出基准
2. **漏收书籍权重未评估**：《推背图》《千里命稿卷十七下》是核心经典还是边缘资料？若是核心，3.6% 也严重；若是边缘，可延后
3. **「因书名重复被跳过 5 本」**：这可能是去重逻辑，不是 bug。报告未深究

**独立判断**：这是最可信的证据，但影响规模被高估。22 本漏收应修复，但不构成「知识库不可用」的结论。

### 证据3：预切分文件 6 个全部失效

**证据强度**：高（100% 失败率，确凿）

**问题**：
1. **6 个文件占总预切分的比例未说明**：若预切分总共 6 个，那是设计失败；若总共 1000 个，6 个失效可接受
2. **「JSON/编码错误 4 个 + dict 根节点 2 个」**：两种不同类型的错误，可能是不同原因
3. **回退到 Markdown 自动切分**：报告承认有兜底，但未评估兜底质量

**独立判断**：100% 失败率是确凿的设计缺陷，应优先修复。但「全部失效」不等于「全部内容丢失」——回退到自动切分后内容仍在索引中，只是切分质量下降。

### 证据4：部分大书只切 1 条 passage

**证据强度**：中（数据真实，但解读偏严）

**问题**：
1. **未区分「应多切却只切 1 条」vs「本就该 1 条」**：31-83KB 的书切 1 条确实异常，但若某些书本身就是短文，1 条合理
2. **《康熙字典》261KB 切 1 条**：这个例子有力，因为字典类工具书应按字头切分
3. **《吕文艺-八字命理全集》1.30MB 切 1 条**：这个例子也有力，1.3MB 应切出至少几十条

**独立判断**：21 本 1 条 + 32 本 <5 条中，**至少 10 本是确凿的切分缺陷**（大书切 1 条）。但报告把所有 53 本都算作问题，可能高估。

### 证据5：分类错误（紫微/取名/道教归八字）

**证据强度**：高（确凿的设计缺陷）

**问题**：
1. **影响范围未量化**：归错类的 passage 在检索时是否真的被错误使用？TF-IDF 检索不依赖分类标签，只看词面匹配
2. **「manifest 没有紫微类别，但最大书目中存在多部紫微资料」**：这说明分类体系本身不完整，不只是「归错类」

**独立判断**：确凿缺陷，应修复。但实际影响可能小于报告暗示——因为检索层不严格依赖分类。

### 证据6：当前向量是 TF-IDF 兜底

**证据强度**：高（`plan_b_used: true` 确凿）

**问题**：
1. **TF-IDF ≠ 完全不可用**：对于精确词面匹配（如经典原文引用、专有名词），TF-IDF 反而比语义 embedding 更准确
2. **「高质量中文语义 embedding」替代方案未评估**：
   - 成本：137337 条 × 1024 维 embedding 的 API 调用费用
   - 收益：检索质量提升多少？没有 baseline 对比
   - 部署：本地模型 vs API？延迟？冷启动？
3. **「plan_b_used」可能是临时降级**：报告未确认这是永久状态还是临时兜底

**独立判断**：这是事实，但「FAIL」判定偏严。应改为「PARTIAL — TF-IDF 兜底可用，语义 embedding 升级待评估」。

### 证据7：589 本恢复库未接入生产

**证据强度**：高（确凿未接入）

**问题**：
1. **589 vs 585 = 多 4 本，但 passages 897370 vs 137337 = 多 6.5 倍**：说明恢复库切分粒度更细，但不一定更好（可能过切）
2. **恢复库质量问题严重**（标题长度≤3 的 36 个、空白标题 4 个）：这恰恰说明「不接入」是正确决策
3. **「未接入」是设计决策**：在库未清洗完成前不接入生产，是负责任的做法，不是失败

**独立判断**：把「设计决策」判为「FAIL」是价值判断越界。应改为「PARTIAL — 恢复库已识别，清洗未完成，按计划暂不接入」。

## 4. 结论严谨性审视

### 4.1 推理跳跃

报告最关键的推理跳跃：

> Git 有 8.8GB + 43245 悬空 blob + 1639 PDF → 因此 Git 中有大量未解析书籍

这个推理链**没有建立**。报告自己也承认：「目前没有完整的 `Git SHA → 原始书名 → 解析文本 → passage → 向量行号 → 生产状态` 总账」。

**没有总账，就无法证明「未解析书籍」的数量**。报告用「.git 很大」暗示「未解析很多」，这是暗示而非证据。

### 4.2 价值判断伪装成事实判断

| 报告判定 | 实际性质 | 应改为 |
|---|---|---|
| Git 书籍全量解析 FAIL | 证据不足（无总账） | PARTIAL — 待建立总账后评估 |
| 589 本恢复库接入生产 FAIL | 设计决策（库未清洗） | PARTIAL — 按计划暂缓接入 |
| 高质量语义向量化 FAIL | 技术选型（TF-IDF 兜底） | PARTIAL — 兜底可用，升级待评估 |

### 4.3 最终判定的措辞问题

报告结论：
> 现有知识库可以称为：585 个文本源、137337 条 passages 的阶段性运行索引。
> 目前不能称为：Git 中全部相关书籍已经完整解析、正确分类、可靠切分并接入大宗师知识检索。

**问题**：
- 「不能称为 Git 中全部相关书籍已经完整解析」— 这个否定句永远成立，因为「全部」是无穷标准
- 任何知识库都可以被判定为「没有全部解析」，这个标准不可证伪
- 审计应该回答的是「**够不够用**」，而不是「**全不全**」
