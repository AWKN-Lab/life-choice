# LanceDB vs 当前方案对比 - 20260705

> 用户问："lancedb 和你这个对标下"
> "你这个" 指当前项目的 v2(生产) + v3(评估中) embedding 检索方案

---

## 一、当前方案（v2 生产 + v3 评估）

### v2 生产（TF-IDF + numpy）
- **存储**：`embeddings.npy`（357,359 × 1024 × float32 = 1.4GB）+ `classics_index.jsonl`（255MB）
- **加载**：`np.load(mmap_mode='r')`，内存占用几乎为 0（磁盘映射）
- **查询**：`sims = embeddings @ query_vec`（纯 numpy 矩阵乘法）
- **检索**：`np.argpartition(-sims, k)[:k]` 取 Top-K
- **过滤**：先按 `system_type` 过滤索引，再做向量检索
- **混合搜索**：有 `/hybrid_search` 接口（TF-IDF + BM25 关键词）

### v3 评估（BGE-small-zh-v1.5）
- **模型**：bge-small-zh-v1.5（512 维）
- **评估结论**：V3_PARITY（与 v2 持平，暂不替代）
- **阻塞**：服务器内存 483MB 不足，无法加载 BGE 模型推理

### 当前方案痛点
1. **全量加载**：每次查询都要与 357,359 个向量做点积，无 IVF 索引
2. **无持久化索引**：重启后需要重新 mmap 加载
3. **扩展性差**：passages 增长到 100 万+ 时，查询延迟线性增长
4. **无增量更新**：新增 passages 需要重新生成全量 embeddings.npy
5. **过滤效率低**：先过滤再检索，无法在向量空间中直接过滤
6. **无元数据管理**：passage 元数据在 jsonl，与向量分离

## 二、LanceDB 方案

### 核心特性
- **Serverless 嵌入式**：无需独立服务器进程，SDK 直接嵌入应用
- **磁盘扩展**：基于 Lance 列式格式，不占内存（vs FAISS/Chroma 内存优先）
- **多模态 lakehouse**：向量 + 文本 + 元数据 + 图像/视频/音频 同表存储
- **混合搜索**：向量 + 全文（BM25）+ 重排序 + SQL 过滤
- **索引**：IVF + PQ + HNSW，支持 ANN 近似检索
- **版本控制**：表级版本，支持 time travel
- **SDK**：Python / TypeScript / Rust / Java

### 部署模式
- **OSS**：嵌入式库，本地磁盘存储，免费开源（Apache 2.0）
- **Enterprise**：分布式，petabyte 规模，对象存储后端

### 在本项目的潜在用法
```python
import lancedb

# 1. 创建/打开数据库（磁盘文件，零内存）
db = lancedb.connect("/opt/awkn-life/knowledge/lancedb")

# 2. 创建表（向量 + 元数据同表）
db.create_table("passages", data=[
    {"passage_id": "xxx", "text": "...", "vector": [...], 
     "system_type": "bazi", "book": "滴天髓", "chapter": "..."}
])

# 3. 创建向量索引（IVF + PQ，加速查询）
db.open_table("passages").create_index(
    metric="L2",
    vector_column_name="vector",
    num_partitions=256,
    num_sub_vectors=16
)

# 4. 混合搜索（向量 + 过滤 + 全文）
results = (
    db.open_table("passages")
    .search(query_vector)
    .where("system_type = 'bazi'")  # 元数据过滤
    .limit(10)
    .to_pandas()
)

# 5. 全文搜索（Tantivy 引擎）
results = db.open_table("passages").search("日主身弱", text_column="text").limit(10)
```

## 四、关键差异：为什么 LanceDB 可能更适合

### 4.1 解决服务器扩容死结
- **当前 v3 阻塞**：BGE 模型推理需 2GB 内存，服务器只有 483MB
- **LanceDB 方案**：
  - embedding 生成仍需 BGE（可在本地/其他机器离线生成）
  - **检索时零内存**（磁盘扩展，IVF 索引）
  - 服务器只需 ~50MB 内存即可跑检索服务
  - **不需要扩容**

### 4.2 查询性能跃升
- **当前**：357k 全量点积 ~100ms（线性扫描）
- **LanceDB**：IVF 索引 ~5-20ms（对数级）
- **100 万+ passages 时差距更大**

### 4.3 增量更新能力
- **当前**：新增 15 本书需要重新生成 1.4GB embeddings.npy
- **LanceDB**：`table.add([new_data])` 单条插入，索引自动更新

### 4.4 混合搜索内置
- **当前**：自实现 `/hybrid_search`（TF-IDF + BM25 手动拼接）
- **LanceDB**：内置 `hybrid_search`，支持 rerank（Cross-Encoder 重排序）

### 4.5 元数据过滤效率
- **当前**：先按 system_type 过滤索引，再做向量检索（两步）
- **LanceDB**：`WHERE system_type = 'bazi'` 在向量空间内直接过滤（一步，更准）

## 五、LanceDB 的劣势和风险

### 5.1 迁移成本
- 需要把 357k passages 从 jsonl + npy 迁移到 LanceDB 表
- 需要改写 `loader.py` 和 `main.py` 的检索逻辑
- 预估工作量：2-3 天

### 5.2 Embedding 生成仍是问题
- LanceDB 只解决"存储+检索"，不解决"embedding 生成"
- BGE 模型推理仍需在本地/其他机器离线完成
- 或者用 Embedding API（OpenAI text-embedding-3-large）

### 5.3 学习成本
- 团队需要学习 LanceDB 的 API 和索引调优
- IVF/PQ 参数需要根据数据量调整

### 5.4 生态成熟度
- LanceDB 是 2023 年新项目，生态不如 FAISS/Milvus 成熟
- 但已用于 Runway、Midjourney 等 AI 公司

## 六、方案对比（硬约束：不使用 API embedding，数据不出境）

### 硬约束（用户明确要求）
- ❌ 不使用 OpenAI / Anthropic / 任何第三方 Embedding API
- ❌ 不把 passages / 向量数据外露给任何第三方
- ✅ 所有 embedding 生成必须在本地/自建机器完成
- ✅ 数据主权 100% 自控

### 批判性拆解：Embedding 生成的位置

**关键洞察**：embedding 分两类，位置可以不同

| 类型 | 频率 | 延迟要求 | 位置选择 |
|------|------|----------|----------|
| **文档 embedding**（357k passages） | 一次性 | 无 | 本地离线 ✅ |
| **查询 embedding**（用户问题） | 每次查询 | <100ms | **这才是关键** |

**之前的盲点**：假设"查询 embedding 必须在服务器做" → 导致"服务器必须加载 BGE 模型" → 导致"服务器必须扩容"

**批判性质疑**：查询 embedding 为什么不能在本地做？

### 方案矩阵（修正后）

| 方案 | 文档 embedding | 查询 embedding | 服务器内存 | 延迟 | 数据出境 |
|------|---------------|---------------|-----------|------|----------|
| **X1 保持 v2** | TF-IDF（本地） | TF-IDF（服务器） | ~0MB | 100ms | 否 |
| **X2 v3 BGE+numpy** | BGE（本地） | BGE（**服务器**） | **+1.5GB** | 150ms | 否 |
| **X3a LanceDB + 本地BGE离线** | BGE（本地） | BGE（**服务器**） | **+1.5GB** | 60ms | 否 |
| **X3b LanceDB + 本地Embedding Service** ⭐ | BGE（本地） | BGE（**本地**） | **~50MB** | 200-500ms | **否**（查询文本临时传输） |
| **X3c 完全本地化检索** | BGE（本地） | BGE（本地） | **~0MB**（仅转发） | 300-600ms | 否 |

### 方案 X3b：本地 Embedding Service + 服务器 LanceDB（推荐）

**核心思路**：把 BGE 模型留在本地，服务器只跑 LanceDB 检索

```
本地开发机（常开，BGE Embedding Service）
  ├─ BGE-large 模型（本地内存充足）
  ├─ FastAPI /embed 接口
  └─ 输入: query 文本 → 输出: query vector

服务器（483MB 内存，零扩容）
  ├─ LanceDB 表（357k passages，磁盘扩展，~50MB 内存）
  ├─ /retrieve?query=xxx
  │   ├─ POST 本地 /embed {text: query} → query_vector
  │   ├─ LanceDB.search(query_vector) → top_k passages
  │   └─ 返回结果
  └─ 无需加载 BGE 模型
```

**数据流**：
```
用户查询 → 服务器 → 本地/embed(query) → query_vector 回传 → 服务器 LanceDB 检索 → passages → LLM
         ↑                          ↑
         不含敏感数据              查询文本临时传输，不存储
```

**优势**：
- ✅ 服务器**真正零扩容**（只跑 LanceDB，50MB 内存）
- ✅ 数据 100% 不出境（查询文本在本地临时编码后丢弃，不存储）
- ✅ 查询性能跃升（LanceDB IVF 索引 5-20ms）
- ✅ 增量更新极简（本地编码新 passages → 追加 LanceDB 表）
- ✅ BGE 模型在本地，内存无压力

**劣势**：
- 本地机器必须常开（可用云函数/备用机/内网穿透）
- 网络延迟（公网 200-500ms，同地域内网 ~50-100ms）
- 查询文本会从服务器发到本地（但本地不存储，临时编码即丢弃）

### 方案 X3c：完全本地化检索（极端方案）

**核心思路**：所有重活都在本地，服务器只做 API 网关

```
本地开发机（常开，完整检索服务）
  ├─ BGE-large 模型
  ├─ LanceDB 表（357k passages）
  ├─ FastAPI /retrieve /embed_search /hybrid_search
  └─ 完整知识检索能力

服务器（483MB 内存，零资源）
  ├─ API 网关
  ├─ consult 路由 → 转发本地 /retrieve
  └─ 返回结果给前端
```

**优势**：
- 服务器**完全零资源**（只转发）
- 本地内存充足（BGE + LanceDB 无压力）
- 数据 100% 不出境
- 增量更新极简（本地直接改 LanceDB）

**劣势**：
- 本地机器必须常开
- 所有检索流量过本地（带宽压力）
- 公网延迟较高（300-600ms）

### 方案 X3a：LanceDB + 本地 BGE 离线（之前推荐，现降级）

**核心思路**：文档 embedding 本地离线生成，查询 embedding 服务器做

**问题**：服务器仍需加载 BGE 模型 → 仍需扩容 +1.5GB

**结论**：不符合"服务器零扩容"目标，降级为备选

## 八、决策点（数据不出境约束下）

### 第一层决策：是否真的需要 Embedding？

**批判性质疑**：本项目的查询特征真的需要语义检索吗？

| 查询类型 | 占比（预估） | 示例 | 适合的检索方式 |
|---------|-------------|------|---------------|
| 专业术语查询 | 80% | "日主身弱如何取用神" | **关键词检索（FTS5/BM25）** |
| 模糊描述查询 | 15% | "我最近运气不好怎么办" | Embedding |
| 跨分类查询 | 5% | "身弱"（八字+六壬） | Embedding |

**结论**：80% 查询用关键词检索就够了，只有 20% 才需要 Embedding

### 第二层决策：先做关键词检索，还是直接上 Embedding？

| 方案 | 工作量 | 召回率（预估） | 风险 |

| **方案 X3b：LanceDB + 本地BGE** | 2-3 天 | 0.6-0.7（混合） | 中 |
| **混合方案** | 3-4 天 | 0.8+（全覆盖） | 中 |

**推荐**：先做 FTS5（0.5 天），评估召回率。若达标（≥0.7），Embedding 可以不做。

### 第三层决策（若需 Embedding）：位置选择

## 九、最终结论（批判性思维修正后）

### 核心洞察

**用户的两个问题揭示了根本盲点**：
1. "为什么在本地推理" → 质疑"推理必须发生"
2. "为什么要 Embedding 生成" → 质疑"Embedding 是必需的"

**真相**：
- 检索不一定要 Embedding
- 推理不一定要发生
- 80% 的查询用关键词检索就够了

### 推荐路径（修正后）

**Step 1：先做 SQLite FTS5（0.5 天）** ⭐⭐⭐
- 零推理，零 embedding
- 服务器零扩容（FTS5 索引 ~10MB）
- 召回率预估 0.7-0.9（关键词查询）
- 用现有 12 个查询评估
- 若达标（≥0.7），Embedding 可以不做

**Step 2（可选）：若 FTS5 召回率不足，再考虑 Embedding**
- 先分析失败查询类型
- 若是"关键词不匹配"问题 → 优化分词/同义词
- 若是"语义模糊"问题 → 才上 Embedding

**Step 3（可选）：若决定上 Embedding**
- 选 X3b（本地 Embedding Service + 服务器 LanceDB）
- 服务器零扩容
- 数据不出境

### 与之前推荐的差异

| 之前推荐 | 修正后推荐 |
|---------|-----------|
| LanceDB + BGE-large | **SQLite FTS5 先行** |

| 服务器需加载 LanceDB | 服务器零新增依赖 |

**批判性思维的价值**：用户的两个问题让我跳出"Embedding 是必需的"思维定式，发现更简单更优的方案。

## 十、方案 Z：SQLite FTS5 + sqlite-vec（与 LanceDB 完整对标）

### 关键发现：SQLite 也能做向量检索

**sqlite-vec**（SQLite 向量搜索扩展）+ **FTS5**（全文搜索）= 与 LanceDB 完全对标的混合搜索能力

| 能力 | LanceDB | SQLite FTS5 + sqlite-vec |
|------|---------|--------------------------|
| 全文搜索（BM25） | ✅ Tantivy 引擎 | ✅ FTS5（内置） |
| 向量检索（ANN） | ✅ IVF/PQ/HNSW | ✅ vec0 虚拟表 |
| 混合搜索 | ✅ 内置 | ✅ SQL JOIN 拼接 |
| 元数据过滤 | ✅ WHERE | ✅ WHERE（SQL 原生） |
| 高亮/snippet | ✅ | ✅ highlight()/snippet() |
| 增量更新 | ✅ 单条插入 | ✅ INSERT |
| 事务一致性 | ✅ | ✅ ACID（更强） |
| 嵌入式部署 | ✅ | ✅（SQLite 更轻） |

### 架构
```
服务器（483MB 内存，零扩容）
  ├─ SQLite + FTS5 + sqlite-vec（全嵌入式）
  ├─ passages_fts 表（FTS5 全文索引，~10MB）
  ├─ passages_vec 表（vec0 向量索引，可选用 BGE 离线向量）
  ├─ passages_meta 表（普通表，元数据）
  │
  ├─ /retrieve?query=日主身弱
  │   ├─ 方案 Z1（纯关键词）：SELECT ... FROM passages_fts MATCH '日主 身弱'
  │   ├─ 方案 Z2（纯向量）：SELECT ... FROM passages_vec WHERE embedding MATCH ? ORDER BY distance
  │   └─ 方案 Z3（混合）：FTS5 + vec0 JOIN + rerank
  │
  └─ 零推理（向量离线生成），零 API 调用
```

### 完整对标的方案矩阵

| 子方案 | 全文搜索 | 向量检索 | Embedding 生成 | 服务器内存 | 工作量 |
|--------|----------|----------|---------------|-----------|--------|
| **Z1：纯 FTS5** | ✅ FTS5 | ❌ | 不需要 | ~10MB | 0.5 天 |
| **Z2：纯向量** | ❌ | ✅ vec0 | 本地 BGE 离线 | ~50MB | 1 天 |
| **Z3：混合搜索** ⭐ | ✅ FTS5 | ✅ vec0 | 本地 BGE 离线 | ~60MB | 1.5 天 |

### 方案 Z3：混合搜索（与 LanceDB 完整对标）

**核心思路**：FTS5（关键词）+ sqlite-vec（向量）+ SQL JOIN（融合）+ rerank

```sql
-- 1. 创建 FTS5 全文索引表
CREATE VIRTUAL TABLE passages_fts USING fts5(
    passage_id, text, system_type, book, chapter,
    tokenize='unicode61'  -- 或 jieba 自定义分词器
);

-- 2. 创建 vec0 向量索引表（可选，向量离线生成）
CREATE VIRTUAL TABLE passages_vec USING vec0(
    passage_id TEXT PRIMARY KEY,
    embedding FLOAT[1024]  -- BGE-large 维度
);

-- 3. 元数据表
CREATE TABLE passages_meta (
    passage_id TEXT PRIMARY KEY,
    text TEXT, system_type TEXT, book TEXT, chapter TEXT,
    char_count INTEGER, keywords_tag TEXT
);

-- 4. 混合搜索（FTS5 + 向量 + 过滤 + rerank）
WITH fts_results AS (
    SELECT passage_id, bm25(passages_fts) AS fts_score
    FROM passages_fts
    WHERE passages_fts MATCH '日主 身弱 用神'
      AND system_type = 'bazi'
    LIMIT 50
),
vec_results AS (
    SELECT passage_id, distance AS vec_distance
    FROM passages_vec
    WHERE embedding MATCH ?  -- query_vector（本地 BGE 离线生成）
    ORDER BY distance
    LIMIT 50
)
SELECT m.passage_id, m.text, m.book, m.chapter,
       f.fts_score, v.vec_distance,
       (-- rerank 融合分数：BM25 + 向量相似度
        COALESCE(1.0 / (1.0 + f.fts_score), 0) * 0.5 +
        COALESCE(1.0 / (1.0 + v.vec_distance), 0) * 0.5
       ) AS hybrid_score
FROM passages_meta m
LEFT JOIN fts_results f ON m.passage_id = f.passage_id
LEFT JOIN vec_results v ON m.passage_id = v.passage_id
WHERE f.passage_id IS NOT NULL OR v.passage_id IS NOT NULL
ORDER BY hybrid_score DESC
LIMIT 10;
```

### 实施步骤（1.5 天）

#### Step 1：FTS5 全文索引（0.5 天）
1. 创建 FTS5 表，从 classics_index.jsonl 导入 357k passages
2. 中文分词优化（unicode61 或 jieba 自定义 tokenizer）
3. 改写 `loader.py` 和 `main.py` 检索逻辑
4. 用 12 个查询评估召回率

#### Step 2：sqlite-vec 向量索引（0.5 天，可选）
1. 安装 sqlite-vec 扩展（pip install sqlite-vec）
2. 创建 vec0 表，导入本地 BGE 离线生成的 embeddings
3. 实现 `/embed_search` 接口（纯向量检索）

#### Step 3：混合搜索融合（0.5 天）
1. 实现 FTS5 + vec0 JOIN 查询
2. 调优 rerank 融合权重（BM25 vs 向量）
3. 实现 `/hybrid_search` 接口
4. 用 12 个查询评估混合召回率

### SQLite 方案 vs LanceDB 全维度对标

| 维度 | LanceDB | SQLite FTS5 + sqlite-vec | 优势方 |
|------|---------|--------------------------|--------|
| **内存占用** | ~50MB（嵌入式） | **~10-60MB**（更轻） | SQLite |
| **磁盘占用** | ~1.5GB（含向量） | ~1.5GB（含向量） | 平 |
| **查询性能（关键词）** | Tantivy ~10ms | **FTS5 ~1-5ms** | SQLite |
| **查询性能（向量）** | IVF ~5-20ms | vec0 ~10-30ms | LanceDB |
| **查询性能（混合）** | 内置 ~20ms | SQL JOIN ~30ms | LanceDB |
| **扩展性（100万+）** | IVF 对数级 | FTS5 对数级，vec0 线性 | LanceDB |
| **增量更新** | ✅ 单条插入 | ✅ INSERT（ACID 事务） | SQLite |
| **元数据过滤** | ✅ WHERE | ✅ WHERE（SQL 原生） | 平 |
| **混合搜索** | ✅ 内置 | ✅ SQL JOIN 拼接 | 平 |
| **高亮/snippet** | ✅ | ✅ highlight()/snippet() | 平 |
| **事务一致性** | ❌ 无 | ✅ ACID | **SQLite** |
| **版本控制** | ✅ time travel | ❌（需自建） | LanceDB |
| **多模态** | ✅ 图像/视频/音频 | ❌ 仅文本+向量 | LanceDB |
| **部署复杂度** | 低（pip install） | **极低**（已内置 FTS5） | SQLite |
| **依赖** | lancedb | **sqlite-vec（仅 1 个扩展）** | SQLite |
| **数据主权** | ✅ 本地 | ✅ 本地 | 平 |
| **服务器扩容** | 不需要 | **不需要** | 平 |
| **学习成本** | 中（新 API） | **低**（SQL 语法） | SQLite |
| **生态成熟度** | 2023 年新项目 | **SQLite（20+ 年）** | SQLite |

### SQLite 方案的核心优势

1. **零新增依赖**：FTS5 是 SQLite 内置，Python/Node 默认带 SQLite
2. **ACID 事务**：passages 增删改有事务保护，LanceDB 没有
3. **SQL 原生**：团队熟悉 SQL，学习成本最低
4. **极低内存**：FTS5 索引 ~10MB，服务器零压力
5. **关键词检索更快**：FTS5 1-5ms vs LanceDB Tantivy 10ms
6. **混合搜索灵活**：SQL JOIN 可以任意组合 FTS5 + vec0 + 元数据过滤

### SQLite 方案的劣势

1. **向量检索性能略差**：vec0 线性扫描，LanceDB IVF 对数级
2. **无版本控制**：需要自建（但可用 Git 管理 .db 文件）
3. **无多模态**：仅文本+向量（本项目不需要多模态）
4. **无内置 rerank**：需 SQL 手动融合（但灵活度更高）

### 风险与应对

| 风险 | 应对 |
|------|------|
| FTS5 中文分词不佳 | 用 jieba 预处理 + simple tokenizer 插件 |
| vec0 向量检索慢 | 先做 FTS5 过滤，再对 Top-100 做向量 rerank |
| sqlite-vec 扩展兼容性 | 先验证 Python sqlite3 能加载 vec0 |
| 混合搜索调优 | 用 12 个查询评估，调优 BM25/向量权重 |

### 备选方案

- 若 sqlite-vec 不可用：纯 FTS5（方案 Z1），召回率预估 0.7-0.9
- 若 FTS5 中文支持不足：LanceDB Tantivy（方案 X3b）
- 若混合搜索不达标：加 Cross-Encoder rerank（本地推理）

## 十一、最终推荐（与 LanceDB 对标后）

### 推荐路径：方案 Z3（SQLite FTS5 + sqlite-vec 混合搜索）

**理由**：
1. **能力对标 LanceDB**：全文搜索 + 向量检索 + 混合搜索 + 元数据过滤
2. **更轻量**：零新增依赖（FTS5 内置），sqlite-vec 仅 1 个扩展
3. **更可靠**：ACID 事务，LanceDB 没有
4. **更省资源**：服务器内存 ~10-60MB vs LanceDB 50MB
5. **更低成本**：工作量 1.5 天 vs LanceDB 2-3 天
6. **数据不出境**：全本地，零 API 调用

### 实施顺序

**Phase 1：FTS5 先行（0.5 天）** ⭐ 立即可做
- 创建 FTS5 表，评估召回率
- 若达标（≥0.7），先上生产，替换 v2

**Phase 2：sqlite-vec 补充（0.5 天）** 可选
- 本地 BGE 离线生成向量
- 导入 vec0 表，实现向量检索

**Phase 3：混合搜索（0.5 天）** 可选
- FTS5 + vec0 JOIN 融合
- 调优 rerank 权重

### 决策点

1. **立即启动 FTS5 评估？**
   - 是：0.5 天验证召回率（推荐）
   - 否：保持 v2，等后续

2. **是否需要向量检索？**
   - 若 FTS5 召回率 ≥0.7 → 不需要（方案 Z1 足够）
   - 若 FTS5 召回率 <0.7 → 加 sqlite-vec（方案 Z3）

3. **BGE 模型获取？**
   - 用户手动下载（huggingface.co）
   - 在能联网的机器上自动下载后传输
